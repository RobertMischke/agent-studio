# Commit / Push Doctrine

## Headline

**The platform owns the commit boundary. Models execute work; the platform records it.** Every coding agent that runs under Agent Software Studio produces a working tree, never a commit. The runner decides when work is "done enough to record", composes the commit message, stamps the resulting SHA onto the job, and (where configured) pushes. The CLI never speaks for itself in git history. That separation is the difference between a workbench and a hopeful prompt.

## Why

- **One state machine, one author of git history.** Letting the CLI commit splits authority over the same tree between the CLI's internal heuristics and the runner's lifecycle policy. Two writers, one branch: drift is guaranteed.
- **The commit must align with the lifecycle transition.** A commit only makes sense at `3-progress -> 4-auto-review`, when the runner has *also* decided this run reached review. A CLI committing mid-run, on its own clock, breaks that alignment.
- **The recorded SHA must be the one stamped on the job.** `JobInfo.Commit` (Sha, message, file list, timestamp) is the durable evidence the detail view, the run timeline, and the per-run change set all read. If the CLI commits and the runner later commits an empty diff, the stamp lands on the wrong SHA.
- **The product runs on `main`, not on branches.** Per ADR-0001 there is no branch orchestration: a CLI that "tidies up" by branching, switching, or amending breaks the assumption every other layer was written against.
- **Auditability for the user.** The commit message is generated by a deterministic Haiku call against the diff (see `prompts/runtime/commit-message.md`); the user sees the exact same shape regardless of which CLI did the work. Per-CLI commit conventions would defeat that.
- **Clean separation for marketing and onboarding.** "Models do work, the platform records work" is one sentence a new user can repeat back. Anything more nuanced is a leaky abstraction.

## How it works

The commit and push flow today lives in `JobTransitionService.MoveAsync` ([backend/Services/Jobs/JobTransitionService.cs](../backend/Services/Jobs/JobTransitionService.cs)):

1. The runner finishes a CLI execution. `RunCompletionPolicy.ShouldMoveToReview(execution.Status)` ([backend/Services/Runner/RunCompletionPolicy.cs](../backend/Services/Runner/RunCompletionPolicy.cs)) returns `true` only when the status is `completed`.
2. `ProjectRunner.OnCliFinished` (see [backend/Services/Runner/ProjectRunner.cs](../backend/Services/Runner/ProjectRunner.cs) around the `RunCompletionPolicy.ShouldMoveToReview` call) invokes `_transitions.MoveAsync(jobId, JobStates.AutoReview, ...)`.
3. Inside `JobTransitionService.MoveAsync`, the auto-commit guard fires only when **all three** are true: the job is leaving `3-progress`, entering `4-auto-review`, and the project's `ProjectSettings.AutoCommit` flag is on.
4. `GitService.AutoCommitAsync` ([backend/Services/GitService.cs](../backend/Services/GitService.cs)) runs:
   - `git status --porcelain` -> if clean, returns "nothing to commit" (soft skip, no error).
   - `GenerateCommitMessageAsync` shells `claude` (Haiku, configurable model) with `prompts/runtime/commit-message.md` rendered against the working-tree diff.
   - Falls back to `chore: snapshot for review (<N> files changed)` if the LLM hiccups.
   - `git add -A` then `git commit -F -` (multi-line message via stdin to avoid shell escaping).
5. The folder is moved to `4-auto-review` and the resulting SHA, message, file list, and timestamp are stamped onto `JobInfo.Commit` / `JobInfo.Commits` via `_mutations.SetJobCommitOnFolder`. The detail pane and run-timeline endpoints read this stamp.
6. Per-project `AutoCommit` is a boolean setting ([backend/Services/ProjectSettingsService.cs](../backend/Services/ProjectSettingsService.cs), `PUT /api/projects/{name}/auto-commit`) so a user who would rather stage commits manually can keep the rest of the lifecycle automatic.
7. Per-project `AutoPushStrategy` controls when stamped commits are pushed:
   - `never`: the operator pushes manually.
   - `on-completed` (default): push only after a job reaches `6-completed`, meaning it has passed review.
   - `always-immediate`: push immediately after auto-commit and again on completed as an idempotent backstop. This is available for low-risk projects but carries review-rewrite risk.
8. Completed pushes use `GitService.PushShaAsync`, which runs `git push origin <sha>:refs/heads/main`. It first checks whether the SHA is already an ancestor of `origin/main`, skips if so, and relies on normal git fast-forward rules. It never force-pushes.
9. `CompletedPushBackstopHostedService` sweeps `6-completed` every 15 minutes and retries completed-job SHAs that are not on the remote. This covers missed transition triggers and backend restarts.

The commit-message template is editable in [prompts/runtime/commit-message.md](../prompts/runtime/commit-message.md) and is the single source of voice for every commit the platform produces, regardless of which CLI did the work.

## Why not branches

The product runs each project on a **single branch**, typically `main`. ADR-0001 ("Sequential per-project, parallel across projects") makes branch orchestration explicitly out of scope; [AGENTS.md](../AGENTS.md) Out-of-scope list calls out **"Branch creation, switching, merging, or worktree management by the app."** A doctrine that says "the platform owns the commit boundary" therefore also implies: the platform owns the *single* boundary, on the user's working branch. There is no per-task branch, no fan-out branch, no PR gate inside the platform.

If the user wants PR-shaped review for an external project, they do that in their own checkout, against their own remote, after a batch of jobs has landed. The platform does not synthesise PRs.

## What models / CLIs are NOT allowed to do

A run inside Agent Software Studio must not, under any circumstance:

- Run `git commit` (or `git commit --amend`).
- Run `git push` or any remote-mutating operation.
- Run `git reset --hard`, `git restore`, `git clean`, or anything that destroys uncommitted work the runner is about to capture.
- Run `git checkout <branch>`, `git switch`, `git branch -D`, or any branch-mutating operation. The product is single-branch per project.
- Touch `.git/HEAD`, `.git/index`, or any internal git plumbing.
- Author a tag, stash, or note that ends up in history.

If you observe a CLI doing any of the above, **it is a regression**. Raise an issue. The fix is in the CLI driver / runtime prompt, not in the doctrine.

Today these prohibitions are enforced primarily by **convention plus runtime prompt scope**: the runner's prompt frames ([prompts/runtime/runner-fresh-start.md](../prompts/runtime/runner-fresh-start.md), `runner-resume-*.md`, `runner-recovery-*.md`) tell the CLI to inspect with `git status` / `git diff` but do not invite it to commit. They do not yet *forbid* commits in so many words; that is a documented follow-up below. There is no in-process `git` allowlist; we rely on the published doctrine, the prompts, and (for new failure modes) regression tests.

## What the orchestrator does

The orchestrator (the per-project supervisory Claude session that wraps a project's pipeline; see [ADR-0017](architecture-decisions.md#adr-0017---supervisor-as-advisory-layer-above-the-deterministic-orchestrator-2026-05-04)) is a **supervisor over the runner, not a second author of git history**. Its role with respect to commits and pushes:

- **Supervise**, do not commit. The orchestrator may *check* whether the runner committed, whether the working tree was clean, whether the SHA stamped on the job exists - and it may emit a `STEER` follow-up that asks the runner to retry or asks the worker CLI to re-run if the commit step skipped due to a fixable cause. It must not run `git commit` itself.
- **Supervise**, do not push. When push is wired (see "Future / known gaps"), the orchestrator may verify that the local SHA reached the remote and surface a typed advisory if it did not. The push call itself is the runner's.
- **Speak through typed messages.** Per ADR-0002, the orchestrator's voice in the activity log is `OrchestratorChatLog` ([backend/Services/Runner/OrchestratorChatLog.cs](../backend/Services/Runner/OrchestratorChatLog.cs)) entries (`decision`, `reissue`, `heuristic`, `giveup`). A commit-supervision verdict is one of those; it is not a side-channel git invocation.

Why not let the orchestrator commit when the runner skipped? Because the runner skipping is data: either the working tree was clean, or AutoCommit was off, or the run did not reach review. Each of those has a deliberate meaning. An LLM "fixing" the skip by committing anyway would launder a state-machine signal into a silent write, which is the failure mode ADR-0002 was written to prevent.

## Future / known gaps

The doctrine above describes today's commit and completed-push path. Remaining gaps are prompt hardening and richer push observability.

- **No commit/push prohibition in the runtime prompts.** [prompts/runtime/runner-fresh-start.md](../prompts/runtime/runner-fresh-start.md) tells the CLI it may run `git status` / `git diff`, but does not say "you may not run `git commit` / `git push`". A CLI that follows its own instinct to "wrap up by committing" would not be told otherwise by the prompt today. This is the first follow-up below.
- **No regression test asserting the CLI did not commit.** There is no spec that fails when a worker CLI's spawned scope makes a `git commit` call. The deterministic check is straightforward (compare HEAD before/after the spawned process scope, separately from the runner's own commit) but does not exist.
- **No regression test for the `JobInfo.Commit` stamp.** The auto-commit path is exercised through manual review; no unit or integration test asserts that `JobInfo.Commit.Sha` is set after a successful `3-progress -> 4-auto-review` transition with `AutoCommit = true`.
- **No persisted push outcome on the job yet.** The backend logs push success / skip / rejection, but `job.json` does not yet carry a `push` block next to `commit`. The project-level git hygiene surface still answers push-pending at repository scope.

## Suggested follow-ups

These are concrete, scoped coding tasks discovered during this analysis. The user will queue them as separate jobs.

- **Persist push outcome beside `JobInfo.Commit`.** Stamp the push outcome (success / already-remote / remote-rejected / no-remote-configured) onto a new `JobInfo.Push` field so the detail view can render it next to `JobInfo.Commit`. Single branch, no upstream-tracking magic.
- **Add the orchestrator's "did push happen?" supervision step.** After the runner reports a successful completed push, the orchestrator (per-project session) should `git fetch` and verify the SHA reached the remote. If not, emit an `OrchestratorChatLog` `decision` advisory and (in auto mode) a STEER that asks the runner to retry. Implementation lives behind `Supervisor:AutoInterventionEnabled` per ADR-0017.
- **Update runtime prompts to forbid commit/push explicitly.** Add a "what the platform does, what you do" block to [prompts/runtime/runner-fresh-start.md](../prompts/runtime/runner-fresh-start.md), `runner-resume-interrupted.md`, `runner-resume-restart.md`, and `runner-recovery-continuation.md`: "Do not run `git commit`, `git push`, `git amend`, `git checkout`, or any branch-mutating command. The platform records the commit and (when configured) pushes after this run finishes." Treat as a prompt-template change per ADR-0004; live-probe with `claude-hello-world.spec.ts` after editing.
- **Backend regression test: no `git commit` from inside the CLI's spawned scope.** Add a test that wraps a fake CLI driver, captures the working-tree HEAD before the spawned process is launched and again immediately after the process exits (i.e. *before* the runner's own `MoveAsync`/`AutoCommitAsync`), and asserts the SHA did not change. Catches a future driver / prompt regression that lets the CLI commit on its own.
- **Backend regression test: `JobInfo.Commit` is set after a successful Progress -> Review transition.** Drive `JobTransitionService.MoveAsync` with a fake `GitService` that returns a fixed SHA and assert the moved `JobInfo.Commit.Sha` equals that fixed SHA, the `Files` list is populated, and the timestamp is recent. The test pins the stamping path so a future refactor of `MoveAsync` cannot silently drop it.
- **Per-CLI confirmation in the CLI driver tests.** For each CLI driver test (`ClaudeQuotaProbeTests`, `CodexModelDiscoveryTests`, the Copilot integration tests, `GeminiCliServiceTests`), add or extend a test that asserts the driver's command-list builder never includes `commit`, `push`, `amend`, `checkout`, `branch`, or `reset --hard` as an argv item. A defensive guard against a future helper that would silently shell out.
- **Settings UI: surface AutoCommit (and the future AutoPush) per project.** Today AutoCommit is a `PUT /api/projects/{name}/auto-commit` REST call with no UI. After the push follow-up lands, add a small two-toggle row in the project header so the user can see and flip both flags without curling the API.
