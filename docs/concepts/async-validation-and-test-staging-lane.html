Async Validation & the Test Staging Lane

Should test suites stop running for every card individually, and instead run batched on a dedicated test-integration branch, fed by a staging lane for "done, not yet integrated" work? The idea is plausible — but the AGT data says something uncomfortable: in money it barely pays off. Where it pays off is throughput. This plan separates the two questions cleanly and derives what should be built, and what should not.

As of: 2026-07-25 Data: 847 AGT tasks with pipeline-execution.json, 2,396 pipeline attempts Related: where-does-pipeline-time-go.html · parallel-task-execution.md · QS-28 (skip-if-fresh) Status: Concept — not yet scheduled

TL;DR — the verdict up front

Test gates eat 16.6% of pipeline step time (82 CPU-hours over the corpus) but 0 tokens. Against the token spend of the same tasks (roughly ~$8,400), that CPU costs ~$4 in the cloud and effectively $0 on owned hardware — about 0.05%. As a cost-saver the concept therefore barely pays off: you would be optimizing the cheapest resource. The real finding is elsewhere: 84.3% of test time is retries, and the machine-wide gate lock (BuildTestGateRunner.MachineGateLockPath) serializes them. So the gain is throughput on the shared runner, not cost. And most retries are the intended quality loop (see §3), not waste — which narrows the avoidable slice to redundant re-testing. Consequence: no LLM-based test selection (it burns the expensive resource to save the cheapest one), but deterministic scoping plus batching that removes the redundant re-runs.

§1The idea in three building blocks

The proposal has three separable parts. They are usually thought of together, but they have very different cost/benefit profiles — so here they are split:

1a — Test scoping: only run what is affected

Instead of running the full suite for every card, run only new tests and tests that touch the changed module. The catch you named yourself: "decide smartly" quickly means LLM tokens — and those are expensive. Central question of this plan: can the scoping be made deterministic (no model)?

1b — Staging lane: "done, not yet integrated"

A new lane collects tasks whose coding + review are finished. They move forward batched once all their changes pass the test gates together — rather than forcing every card through the gate individually and synchronously.

1c — Test-integration branch

A dedicated branch where the batched test run happens — decoupled from the coding worktree. Your open question: merge onward from there to develop, or integrate straight into develop and skip the test branch? (→ §7)

§3What "retry" means here (and what it is not)

Definition

An attempt is one full pipeline execution of a task, recorded in pipeline-execution.json; a retry is any attempt after the first (archived in previousAttempts). A new attempt is opened only when the runner re-picks-up the card after a prior run already crossed the core/post boundary (EnsureAgentRunStart → HasReachedAgentRunBoundary).

Crucially, a retry is not the same thing as an in-run steering. The three cases:

EventNew attempt?What it is
In-run steering / continueno A message injected into the running CLI. Stays inside the same core-agent-run step and reuses the record — it never increments the counter.
Orchestrator quality reissueyes The orchestrator judges the result not good enough, emits a Steer/SoftIntervention message, writes an adapted prompt (orchestrator-follow-up-history/<ts>-reissue.md) and reopens the card. The dominant cause.
Technical rerunyes A non-clean run end (abort-review, ADR-0054) or a failed post-step — e.g. a test-gate timeout.

Most retries are the quality loop, not waste

Across the corpus the orchestrator wrote 978 adapted reissue prompts over 437 tasks (avg 2.24, max 16), and 78% of post-processing outcomes are findings-added (the review found something to fix) versus 9% failed-post-processing (almost entirely test-gate timeouts). So the bulk of retries are the intended quality iteration — a feature. The avoidable slice is narrower: re-running an unchanged suite on a quality reissue, plus the ~560 technical test-gate timeouts. That is what this plan targets — not the quality loop itself. See the companion analysis for the full cause taxonomy.

§4The economic reality check: tokens ≫ CPU

You suspected it — the data confirms it clearly. Over the same corpus:

* Illustrative order of magnitude, not a bill: token price roughly blended (in $3/M, cache-read $0.30/M, cache-create $3.75/M, out $15/M). The point is the ratio, not the absolute value.

The ratio is ~2000×

In money, test CPU costs about 0.05% of what the same tasks burn in tokens. Any optimization that spends even a little extra token to save test CPU is a net loss. That disqualifies building block 1a in its LLM variant: asking a model "which tests are relevant?" trades the expensive resource for the cheapest one.

§5Where the real lever is: retry serialization

If money is not the argument, what is? Throughput and latency on the shared runner. Two structural facts:

  • The gate lock serializes machine-wide. BuildTestGateRunner takes %TEMP%\agentstudio-build-test-gate.lock. While one task tests, every other waits. 82 CPU-hours serialized are 82 hours the runner is not free for other tasks.
  • Much of that time is redundant. Retries run the same suite against barely-changed code. A batched run that tests N finished tasks once together replaces N×(1+retries) individual runs.

The actual bet

Not "tests are expensive" (they are not), but: the shared runner spends too much wall-clock in the serialized gate, most of it in repeats. The staging lane + batched test run target exactly that — they lower the number of gate runs, not the duration of a single one.

§6Design sketch: staging lane + test branch

Deterministic scoping instead of LLM (building block 1a, rescued)

Scoping must work without tokens. Feasible via static signals already on hand:

  • Changed files → affected test projects via a maintained project/folder mapping (e.g. a change in backend/Features/Pipeline/** ⇒ backend.Tests filtered to Pipeline*). Pure git diff + mapping, 0 tokens.
  • New test files always run (A status in the diff).
  • Full-suite fallback when the batch spans modules — often the case in a batch anyway, which makes scoping less critical in batch mode than for a single task.

Note: the pattern already exists in part — QS-28 ("skip-if-fresh") deterministically skips unchanged review units via hashes. The same idea, applied to tests.

§7The open question: integrating toward develop

Your question mark. Two paths, with a clear trade-off:

OptionUpsidePrice
A — straight to develop
(no test branch)		 Simple, no new branch, develop is always the source of truth. Gate stays per task — the 84% retry lever is not pulled. Effectively the status quo.
B — batch on integration/test, then FF to develop One suite run per batch → pulls the throughput lever. Red batches keep develop clean. Blame assignment on a red batch: which of the N tasks was it? Needs bisection or single-task fallback.

The hidden cost of option B

That very bisection case can eat the gain again: if a 5-task batch goes red, in the worst case you need up to 5 more individual runs to find the culprit — at which point you were slower than testing per task immediately. B's net gain hinges directly on the batch green rate. With a high green rate (tasks are already review-green individually) B wins clearly; with many red batches it loses. That is the one number to measure before building.

§8Recommendation & slicing

Reject  LLM-based test selection (1a in its model variant). Anti-economical: expensive tokens for cheap CPU. Pursue only the deterministic diff→project mapping.

Measure first  Staging lane + test branch (1b/1c, option B). Pays off only if the batch green rate is high. Before building: estimate the hypothetical batch green rate from existing data (how often would N review-green tasks have been test-green together?).

Pays off regardless  Stop re-running the full suite on retries. The 84% block is the single largest lever and needs no new lane: cache the gate result per commit SHA; skip unchanged test scopes on a reissue. Small change, biggest effect.

Proposed order

  1. Measure (research task): from the pipeline data, quantify the batch green rate and the retry redundancy (same SHA, re-tested). Decides whether option B gets built. 1 card
  2. SHA gate cache: bind the test-gate result to the tested tree SHA; identical SHA ⇒ skip. Removes most of the 84% block without an architectural rebuild. 1 card
  3. Deterministic scoping: diff→test-project mapping as a gate filter, 0 tokens. 1 card
  4. Staging lane + integration/test: only if step 1 gives a green light. conditional

§9Open questions

  • Batch green rate: how often are N individually review-green tasks test-green together? (Blocker for option B.)
  • SHA stability: how often is exactly the same tree re-tested on a reissue? That is the real ceiling on the cache gain — estimate: high, given 3.65 runs/task.
  • Scope-mapping upkeep: who keeps the file/folder→test-project mapping current? A stale mapping = falsely-green gates. Possibly hang it on the PipelineSteps config.
  • Cross-module batches: batches often span modules → scoping barely helps then. Is the batch gain large enough without scoping?
  • Lock granularity: does the machine-wide lock stay, or does it get finer per integration/test branch? Finer = more real parallelism, but more resource pressure.
