Decision memo · AGT-2276

Hosting the Agent Studio Wiki

Host the complete networked Studio control plane on the existing public Hetzner VM. The Wiki then stays a live Studio capability instead of becoming a second product, while agent-runner-01 remains an independently supervised execution host.

Status: recommended Date: 2026-07-23 Decision owner: Robert First visibility: authenticated viewer access Implementation: excluded from this planning run
01 · Decision

Choose the full networked Studio, with separate control and execution hosts

Recommended · Option A

Hetzner control-plane VM

Run Caddy, the production Angular Studio, the Studio API/BFF with the existing Wiki routes, and the Task Server on the existing public VM. Serve all browser traffic from one HTTPS origin and use the shipped networked security profile. Keep the Runner daemon on agent-runner-01, connected outbound with its own scoped service identity.

  • The Wiki remains live, searchable, history-aware, and part of Studio.
  • Authentication, authorization, TLS, audit, backup, and recovery have one owner.
  • No temporary Wiki-only backend or export pipeline has to be retired later.
Placement rule

Do not put the control plane on the Runner by default

Co-locating everything on agent-runner-01 would work technically, but it couples the public control plane to build load, Runner maintenance, and host loss. The existing public VM is the better first control-plane home. The Runner stays a replaceable execution client.

Primary need A live, remotely reachable project Wiki, not an anonymous documentation portal.
Visibility at first release Owner, operator, and viewer accounts. Anonymous access is not a hidden exception.
Published revision The accepted integration or release revision, never whichever task branch happens to be active.

03 · Options

What each option buys, and what it leaves behind

A · Full Studio 87 / 100

Networked Studio on the control-plane VM

The Wiki arrives as part of the real product surface. It keeps live APIs, navigation, search, history, Pulse, and future dynamic features.

  • Strength: directly advances the declared remote target.
  • Cost: larger first deployment and operational blast radius.
  • Visibility: authenticated by default; viewer role is read-only.
B · Wiki service 55 / 100

Read-only API slice plus Wiki frontend

A smaller public service can remain live, but it creates a second deployable, a second authorization boundary, and a second release path around a subset of Studio.

  • Strength: live data and an intentionally narrow public surface.
  • Cost: route extraction, separate hardening, versioning, and UI packaging.
  • Residue: likely retired or folded back once full Studio is hosted.
C · Static export 67 / 100

Rendered Wiki snapshot on the existing VM

Static files are the fastest and safest anonymous publication boundary, but they are a publication product, not the live Studio Wiki.

  • Strength: lowest runtime risk and simplest Caddy operation.
  • Cost: snapshot lag and a new renderer/export pipeline.
  • Loss: no live history, Pulse, read counters, ratings, or server search.

Formula: sum of criterion weight × score, divided by the maximum score of five. Static export ranks second because it is operationally cheap, not because it satisfies the live-Wiki target.

Target compatibility · 30%

Option A is the only path that directly completes the "everything remotely reachable" target without a disposable service. B duplicates a subset of Studio. C is a durable publishing mechanism only if a separate public-docs product is actually wanted.

Operational effort · 20%

The VM, Caddy pattern, systemd units, networked profile, TLS runbook, and Task Server service boundary already exist. A still has the largest data, backup, and cutover surface. B looks small but creates another independently secured application. C is simplest.

Freshness · 20%

A and B can render the current published repository revision. A must still add a controlled revision-sync path; merely copying the backend does not make its checkout current. C is intentionally a snapshot and inherits build or deployment lag.

Authentication and visibility · 15%

A reuses owner, operator, viewer, secure sessions, CSRF, project membership, and audit. B needs a new anonymous route allowlist and must prove that no write or private project data leaks through search, assets, history, or HTML. C has the cleanest anonymous boundary.

Time to usable · 15%

C wins if "usable" means a public snapshot. For the requested live Wiki, A can reuse shipped deployment contracts but still needs a real hosted cutover. B requires extraction work before it has anything safe to expose, so it is not the shortcut its process count suggests.

Reversibility

A can be rolled back by leaving the current local Studio intact until the hosted acceptance gate passes. Its data and published checkout need explicit rollback. B is reversible in isolation but leaves code to delete. C is trivially reversible but does not advance the product runtime.

05 · Live revision contract

“Live” means accepted changes appear without copying files by hand

The current Wiki API reads the physical docs/ tree and Git metadata from a repository checkout. A hosted backend therefore needs one explicit publication contract. The recommended SLO is that an accepted documentation revision becomes visible within five minutes.

01 · ACCEPT

Choose the source revision

Use the accepted integration branch or a release SHA. Never publish an active task branch implicitly.

02 · VERIFY

Fetch and validate

Resolve the exact commit, validate the docs tree and assets, and keep credentials out of logs.

03 · PROMOTE

Switch atomically

Promote a complete checkout so readers never see a mixed or half-updated documentation tree.

04 · OBSERVE

Refresh and record

Refresh Wiki caches, expose the published SHA, retain the previous revision, and emit deployment evidence.

06 · Risks and guardrails

The recommended path is larger, so its boundaries must stay explicit

Correlated host failure

Putting Studio, Task Server, and Runner on agent-runner-01 would turn Runner maintenance or build pressure into control-plane downtime.

Guardrail: use the existing public VM for the control plane and keep the Runner separate.

Deployment checkout becomes a writer

The current Wiki includes commit-backed editing routes. A production publication checkout must not accept an accidental edit that bypasses branch review.

Guardrail: first release is read-only for viewers; operator editing follows the explicit Wiki branch policy.

“Live” checkout silently goes stale

A running API can remain healthy while its repository checkout is weeks behind.

Guardrail: record and expose the published SHA, enforce the five-minute SLO, and alert on failed promotion.

Anonymous access leaks more than pages

Search, history, assets, HTML, Pulse, project names, and future dynamic data widen a public read surface far beyond one Markdown file.

Guardrail: no anonymous exception in phase one. Reopen the decision if public access is a hard requirement.
