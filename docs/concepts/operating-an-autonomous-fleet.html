Operating an Autonomous Fleet

A self-running fleet of coding agents does not fail loudly. There is no exception on a screen, no paged operator, no user who complains — there is only a feed that stops moving. This is the engineering account of eleven ways such a system stalled in production over two weeks, what each one actually was underneath the identical symptom, and the small set of principles that turn a quiet stall into a visible, self-healing event.

1 · The quiet-failure problem

Six unrelated faults arrived under one sentence: “it looks stalled”

When a person runs the pipeline, faults announce themselves: a red test, a stack trace, an angry ticket. When the pipeline runs itself, the failure surface collapses. The board keeps rendering the last known state, the queue keeps its last depth, and the only signal is the absence of new events. Over a two-week window, at least six causally distinct faults produced the same operator observation — “the system appears stalled” — and each one needed a different fix.

The trap

Absence is not an event

Monitoring built around things that happen cannot see a thing that stopped happening. A dead control loop emits nothing, and nothing is exactly what the dashboard was built to ignore.

The amplifier

One shared resource, whole-fleet blast radius

A shared account, a single-reader queue, a roaming control host — each turns a local defect into a fleet outage, because every worker depends on the one thing that broke.

The work

Resilience is making the quiet visible

Most of these fixes are not clever recoveries. They are the far duller act of surfacing a state that was already true: a closed gate, a paused breaker, a stale binary.

The recurring shape.

Nearly every fix in this document is one of two moves. Either make the quiet visible — give the closed gate a reason, the paused breaker a cause, the delivered card an honest live-check — or take the mover out of the session — move the logic that advances work off an ephemeral process and onto the platform, where it cannot die when a terminal closes.

2 · The control loop

A card travels a loop, and it can stall at any station

The fleet runs a closed loop. A coding run delivers a commit; a gate builds and tests it; a review judges it; an integrate step merges it; an accept step closes the card. A separate deploy makes the result live — integration is not deployment. Beneath the loop sit two load-bearing layers: the control plane that connects the orchestrator to the execution host, and the substrate of processes, shims, accounts, and the operating system underneath.

DeliverAgent edits a worktree; the platform commits and fences the result.
GateBuild and test against the integration head; a build-profile gate fails closed.
ReviewNamed aspects and a grade; a single-reader queue feeds the reviewers.
IntegrateMerge into the integration branch; git ancestry, not a badge, decides.
AcceptAn acceptance rail advances integrated cards; humans read verdicts.
DeployA separate release. Only here does “integrated” become “live”.
Control plane. A reverse tunnel from the orchestrator host to the execution host, plus the session cron and supervision that keep the loop ticking. If the host sleeps or roams, the tunnel dies and both planes stall silently.
Substrate. The long-lived API process, the CLI shims agents are launched through, the shared provider account they all authenticate with, and the operating system whose path limits and missing files surface as “environmental” flakes.

Every failure family below strikes at exactly one station or one substrate layer. Locating the strike is most of the diagnosis; the symptom, being always the same, tells you almost nothing.

3 · Failure families

Eleven faults, seven families

Grouped by mechanism rather than by symptom. The card identifiers and host specifics live in the internal dossier; what travels here are the mechanisms and the lessons.

3.1 · Control-plane liveness

Roaming control host

A laptop that sleeps is not a control plane

The orchestrator ran on a roaming Wi-Fi laptop. Every sleep, network roam, or update reboot tore the reverse tunnel, and both planes stalled until a human healed it — repeatedly, once for eleven hours. Three amplifiers hid the cause: a scheduled task barred from running on battery, an unguarded remote call that turned a failed connect into a silent script death, and a cleanup step that was a no-op because it lacked privilege.

Restart discipline

Quiet mistaken for dead, then killed

The orchestrator measured liveness in thirty-second windows and restarted eagerly. A normal quiet spell read as a stall; the restart then killed planes that still held live workers, orphaning their work into lease-recovery requeues. Lease recovery alone accounted for the large majority of a month's backward card moves.

Process replacement

A restart that never replaced the process

The restart command's stop step missed the listener, so the old process kept serving. Config patches and full rollouts were hollow: a stale process from hours earlier answered every request, and once even held a lock that failed the next build while still serving. Fixes looked applied and were not live.

The lesson under all three.

Liveness of the control plane is a first-class concern, not an assumption. Guard every remote call so a failure logs and retries instead of dying silently; never restart a plane without proof of silence — no claims and no live workers; and after every restart, assert a new process start time rather than trusting the command's exit code.

3.2 · Session-bound control loops

Acceptance

The mover died with the terminal

The loop that accepts integrated cards and requeues skipped ones was bound to an ephemeral session and died with it every night. The band-aid — recreating the cron each session — failed nightly. The runner itself was healthy; work piled up only in the human-review lane, thirty-plus cards deep, because nothing was moving them out. One manual tick cleared the entire backlog in a single pass.

Supervision

Observer, not mover

The durable fix is an always-on platform service: it auto-accepts integrated cards, requeues conflict-skipped ones with bounded retry and escalation, and respects operator holds. The session orchestrator is demoted to an observer. A supervision loop, also platform-side, kills wedged workers and heals the tunnel and leases between ticks.

3.3 · Queue liveness and unbounded retry

Wedged workers

A single reader with no watchdog

For two hours, every review run returned zero operations and zero tokens — the reviewer CLI never attached — and the cancelled runs wedged a single-reader queue that had no watchdog and no run reclaim. One stuck reader starves the whole review plane. The deterministic layer beside it stayed trustworthy; the failure was purely in attach-and-reclaim.

Unbounded retry

A card whose scope exceeds any delivery

A queue of cards asked an agent to “implement all recommendations,” but one delivery carries one slice. Build and test passed every time; the requirement-fit aspect blocked every time, because the stated scope structurally exceeds a single deliverable. The result was an infinite carousel — block, requeue, re-code, same block — that kept post-processing full while the review plane itself was perfectly healthy.

Two rules fall out.

Any single-reader queue needs a watchdog and a reclaim path, or one wedged run is a plane outage. And every automatic retry must be bounded and must escalate: the same aspect blocking N rounds in a row is not a coding problem to retry, it is a scoping problem to route to a human — and open-ended cards must be cut one slice per card in the first place.

3.4 · Shared-resource single points of failure

Shared provider account

One account limit, every card fails, and failures escalate

The fleet's agents all authenticated through a single provider account. When that account hit its usage limit overnight, every agent card failed at once — and because failures escalate, a limit became an escalation storm of dozens of cards by morning, with zero successful claims for nine hours. Worse, the circuit breaker then paused with an empty halt reason and did not resume when the limit reset. The systemic fix is limit-aware behavior: detect an account-level limit, pause claims with a visible “waiting on quota” banner instead of failing and escalating, and auto-resume at reset — and make every breaker pause carry a human-readable reason.

3.5 · Integration is not deployment

Delivered but absent

A green card over a stale binary

A fix was integrated days earlier, yet its symptom returned in production — because the execution host still ran a binary from two weeks before. A verification sweep of eight recent “deliveries” found half were not live at all: some were merged but never deployed, some were conflict-skipped yet reported as delivered, some were still only proposals. “Delivered” was measuring the wrong thing.

Silent gate closure

A five-day starvation with no banner

An edit to a project's build profile reset its status, which quietly closed the auto-pickup gate for every card in that project. For five days the cards sat queued with no rejection reason and no banner; nothing surfaced why. The local validation could never pass because it ran in a workspace without the project's sources, even though the profile was proven on the host that actually runs it.

The distinction the board must hold.

A card's live state is a fact about the running system, not a lane color or a prose claim. Recompute “delivered” from what is actually deployed; when a fix touches host-side code, a deploy is due before it counts. And a gate that closes must say so — with a reason, surfaced — and must validate where the work actually runs, not in a workspace that structurally cannot pass.

3.6 · Platform defects disguised as flakes

“Environmental” failures

Six flaky tests were six real platform bugs

A flaky-test hunt found that every one of six “environmental” failures was a genuine product defect on one operating system: a path-length limit emptied review subjects; a database connection pool held a file open so backups silently failed; an atomic file writer's two-rename window dropped writes under concurrent readers; a review admission gate required a file that does not exist on that OS, so it never opened at all. Each had been dismissed as noise for weeks. Made honest, the suite settled at a stable, near-green number.

The lesson is discipline, not cleverness: a test that fails only on one platform is a claim about that platform, and “flaky” is a hypothesis to disprove, not a diagnosis to file under.

3.7 · Runtime self-healing

Vanishing tooling

The agent CLI left the path — twice

The command-line tool agents are launched through disappeared from the path a second time: an auto-update removed its executable shims while leaving the package installed. Both times a reinstall healed it. The durable answer is a runtime that detects its own missing shims, repairs them within a bounded budget, and makes the repair visible — a small instance of the same theme, applied to the toolchain the fleet stands on.

4 · Why quiet fools you

The measurement, not the machinery, is usually wrong

In most of these incidents the machinery was fine and the observation of it was broken. The window was too short, the reason field was empty, the badge lied. Three layers of truth were being conflated, and separating them is what makes an autonomous system legible.

Hard facts
Process start time, claim counts, live worker presence, deployed binary hash, gate status, breaker mode. Machine-observable, unambiguous, and the only sound basis for a restart-or-wait decision.
Observed, never inferred
Interpretation
Whether a quiet spell means a stall, whether a blocked aspect means bad code or bad scope, whether a limit is transient or terminal. Judgment over a window wide enough to be honest — fifteen minutes of proven silence, not thirty seconds.
Bounded, and it escalates
Human decision
Product acceptance, whether to override, when a repeated same-aspect block should stop retrying and reach a person. The loop advances work on its own but hands off the decisions it should not make.
Reached, not silently absorbed
What made the quiet dangerous
  • A closed auto-pickup gate with a null rejection reason.
  • A circuit breaker paused with an empty halt reason and no auto-resume.
  • A thirty-second window that read normal quiet as death.
  • A “delivered” badge computed from a lane, not from what is deployed.
  • A cron whose life was tied to a terminal that closed nightly.
What made it visible
  • Every gate closure and breaker pause carries a surfaced reason.
  • Restart decisions read hard facts: claims, live workers, aged pendings.
  • “Delivered” is recomputed from the deployed system, cross-checked live.
  • The mover is a platform service; the session only observes.
  • Retries are bounded and the same-aspect block escalates to a human.

5 · Resilience principles

Seven rules that survived the two weeks

Each is cheap to state and was expensive to learn. Together they describe an autonomous system that fails loudly enough to be caught and heals often enough not to need catching.

PrincipleWhat it preventsConcretely
Make the quiet visible Silent starvation; empty halt reasons Every closed gate and paused breaker carries a surfaced, human-readable reason.
Move the mover off the session Nightly loop death Acceptance, requeue, and supervision run as an always-on platform service; the session observes.
Bound every retry, then escalate Infinite carousels; escalation storms The same aspect blocking N rounds routes to a human instead of re-coding forever.
No restart without proven silence Killing live in-flight work Fifteen minutes of no claims and no live workers, and compare release trees before theorizing topology.
A shared resource is a single point of failure Whole-fleet outage from one limit Detect account-level limits; pause with quota-wait instead of failing and escalating.
Validate where it runs Gates that can never pass locally A profile proven on the execution host must not be blocked by a source-less local dry run.
Integration is not deployment “Delivered” lies Recompute live state from what is deployed; a host-side fix owes a deploy before it counts.
The single sentence.

An autonomous fleet is not made reliable by never failing — it fails constantly and in mundane ways. It is made reliable by refusing to fail quietly: by giving every stall a surfaced cause and every recovery a path that does not depend on a human noticing that nothing is happening.
