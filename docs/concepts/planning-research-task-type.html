Planning & Research Task Type

Sections outdated since the AGT-2407 through AGT-2412 integrations on 2026-07-29: §2, portions of §3, and the build plan describe gaps that have since shipped, including the planning spawn ledger and decision surface. The remaining product rationale is current. See Planning task lifecycle and the Pipeline domain map for implemented behavior.

A first-class task type whose deliverable is a reviewable HTML report, not merged code. The operator analyzes, gets an artifact, decides, and continues. This document describes the type model, the decide-then-continue loop, and an incremental build plan grounded in the current codebase.

1. Vision & motive

A recurring motive: analysis, research, and concept tasks whose deliverable is a small HTML report the operator looks at, then continues working from.

The shape is an iteration loop, not a one-shot job. The operator commissions some work, receives an artifact, reviews it, makes a decision, and that decision drives the next unit of work. In the operator's words: "Erarbeite etwas, dann entscheide, dann weiter."

Analyze → Artifact (HTML report) → Review → Decide → Continue

Concrete examples the operator names:

  • "Measure orchestrator input latency" → an HTML report to read.
  • "Make 5 comparison or concept proposals I can look at" → then I decide and we continue.
  • "Develop X, then resolve Y" → a worked-out artifact that drives a follow-up.

This work is fundamentally different from a coding task. It does not merge code into develop. It produces a report or a concept. The presentation must be a great wiki/HTML experience, and after reviewing it the operator wants to easily continue: spawn a follow-up task, a next slice, or a decision that drives more work. That "decide then continue" handoff is the key gap today.

Thesis

Almost all the structural plumbing already exists and is load-bearing. What is missing is the part the operator actually feels: a guaranteed reviewable HTML artifact, terminal-state semantics that are honestly different from coding, and the decide-then-continue handoff that turns a reviewed report into the next unit of work with a durable link back.

2. How it works today, and the gap

The plumbing already exists (two read-only modes)

The codebase has two orthogonal classification dimensions. Mode (coding | planning | research) drives substantial runtime behavior. TaskType (bug | feature | chore) is almost entirely display metadata. "Planning & Research" is the operator-facing product name for the two read-only modes, which are already wired into the runner:

  • Pipeline shape. PipelineCatalogue.ForMode(mode) returns a git-free ReadOnlyPipeline for planning/research, built by filtering GitStepIds out of all three sections so the two pipelines stay in lock-step. See backend/Features/Pipeline/PipelineCatalogue.cs (selector at line 355, read-only definition 615-628; the lock-step comment is at line 613). A read-only run is render prompt → run agent → produce report → status, with no commit, merge, worktree, or conflict steps.
  • Isolation. WorktreeRunPolicy.RequiresWorktree returns false for read-only modes, so the run executes in-place in the main checkout. See backend/Features/Runner/WorktreeRunPolicy.cs (lines 30-31).
  • Parallelism. ParallelSlotPolicy.ReadOnlyTask is unconditionally parallel-ok (no predicted scope, can never collide). See backend/Features/Runner/ParallelSlotPolicy.cs (lines 12-26). Read-only tasks never block coding seats by scope; they are bounded only by maxParallelism.
  • Containment. ReadOnlyContainmentPolicy.Evaluate flags any non-empty source-tree diff as a hard violation, never auto-reverted. See backend/Features/Runner/ReadOnlyContainmentPolicy.cs (line 43).
  • Prompt framing. RuntimePromptService.RenderModeFraming injects prompts/runtime/mode-framing-readonly.md ("Read-only run. Investigate and report... Capture findings under results/") and, for research with web on, prompts/runtime/mode-framing-web.md. See backend/Features/Prompts/RuntimePromptService.cs (lines 66-75).
  • Web default. AllowWebAccess defaults to true for research, false for planning/coding. See backend/Features/Tasks/TaskMutationService.cs (line 650) and backend/Shared/Models/TaskInfo.cs (lines 68-72).
Why the deliverable does not break containment

The report artifact is written to the job folder's results/ directory, which lives outside the app source repository (per docs/system/contracts/filesystem.md). Writing results/report.html therefore does not create a source-tree diff and does not trip ReadOnlyContainmentPolicy. This is what makes "produces a rich HTML report" compatible with "read-only, zero source mutation."

The gap: review, decide, continue is not closed

Three things the operator feels are missing:

  • No guaranteed HTML artifact reviewed in-studio. The mode-framing tells the agent to capture Markdown under results/, but there is no required self-contained HTML report and no task-level surface to render it. HTML rendering exists elsewhere (the wiki renders HTML pages and linked reasoning reports in a sandboxed iframe via [srcdoc]="trustedHtml()" in frontend/src/app/features/project-detail/components/project-wiki-section/project-wiki-section.html, lines 319-323 and 378-382; the analysis-report drilldown renders the Markdown body), but a read-only task has no equivalent in-studio report tab.
  • Terminal-state semantics borrowed from coding. The read-only pipeline currently reuses the coding-shaped tail. The four aspect verdicts and the evidence gate are meaningless when there is no code to grade, and there is no merge to approve. Success for a report is "reviewed," not "merged."
  • No decide-then-continue handoff. A planning task can be promoted to a coding task via GET /api/tasks/{jobId}/promote-to-coding (backend/Features/Tasks/TaskCrudEndpoints.cs, lines 201-222), but that endpoint is fire-and-forget (it copies the prompt and images and forgets the parent) and is planning-only (it rejects any non-planning mode with a BadRequest at line 205, so research has no continuation path at all). The ReviewDecisionOrchestrator only has REISSUE and ESCALATE decisions; there is no SPAWN_FOLLOW_UP kind. See backend/Features/Runner/ReviewDecisionOrchestrator.cs (ProcessBlockedAsync, lines 1249-1292).
Design groundwork that already exists

The taxonomy is reconciled in docs/concepts/planning-research-task-kinds-2026-05.md (three modes, read-only pipeline, promote flow, five pinned decisions). The decision-action pattern lives in docs/research/escalated-lane-and-decision-surface-2026-06.md (four actions on a card: discard, reissue with steer, manual, accept). The candidate-to-commitment ledger pattern is already proven in the analysis-report follow-up suggestions (frontend/src/app/models/analysis-report.model.ts). This concept synthesizes those fragments into one product feature.

3. The proposed type model

Planning & Research differs from Coding across all four axes. The table contrasts the two. reuse marks behavior already in code; new marks the seams this concept adds.

Coding vs Planning & Research (the read-only modes)

Terminal success = code merged. reuse ReadOnlyPipeline (git steps filtered out), runs in-place in the main checkout, parallel-ok. No worktree, no branch, no commit, no merge, no accept-against-develop. Terminal success = report exists, containment clean, parked as a decision. reuse terminal correction
Interaction Approve the merge, reissue, or escalate. The feedback verb is approve-merge. Read the HTML report, then decide what work it spawns. The feedback verb is spawn. A four-action surface re-skins the escalated-lane pattern: Promote/Continue, Reissue-with-steer, Log-decision, Discard. Failures and uncertainty are hoisted into a host-rendered verdict strip (sentinel + confidence chip + open-questions counter) above the report. new
Deliverable A diff merged into develop; status.md is a summary. A self-contained results/report.html (inline CSS, no network so it renders in sandbox="allow-scripts" with an opaque origin), with status.md as the structured fallback. Required regions: header (confidence + scope), body, open-questions, plus Sources (research) and a Proposed-next-steps list for the continue parser. new
Presentation Diff view, run protocol, aspect verdicts. A Report tab (default for read-only tasks) renders results/report.html in the same sandboxed iframe the wiki uses. Falls back to the existing beautiful-results Markdown renderer over status.md when no HTML exists. A publish-report post-step commits the report into docs/research/<slug>.html as the one deliberate, auditable git action, so it is durable and searchable. new

Forward link continuations[] on the source, back link derivedFrom on the child. Fan-out (N children from one report) is native. new

What terminal "Reviewed" means

A read-only run cannot merge: the pipeline has no git steps, the run is in-place, and containment guarantees a clean source tree. Its success terminal is therefore: a report exists at results/report.html, the read-only-containment check passed, and the card is parked in 5-human-review as an awaiting-decision substate (reusing the escalated-lane substate split, not a new folder lane). That landing is a decision surface, not a merge-approval gate. The operator's review is the terminal transition: choosing a next action moves the card to 6-completed. The orchestrator-decision step for a read-only task must route straight to that surface with verdict=report-ready, and must never attempt accept-to-develop and never park in 4-auto-review.

Scope decision

Keep the ReadOnlyPipeline a pure git-filter of StandardPipeline. Do not add a custom report-quality verdict step, because that breaks the lock-step invariant the code comment at PipelineCatalogue.cs:613 explicitly protects. The coding-shaped aspect verdicts simply no-op on a read-only run; report quality is enforced by the verdict strip and the prompt contract, not a pipeline step.

4. The decide-then-continue loop

The loop is closed by one handoff primitive, the Continuation, plus the host-rendered decision surface. The Continuation record is modeled on the already-proven analysis-report follow-up suggestion (candidate, then CreatedJobId once materialized) and made bidirectional and durable.

Report at results/report.html → 5-human-review (awaiting-decision) → Operator reads report → Picks typed action → Follow-up task(s) with derivedFrom

The Continuation record

  • Forward link. A continuations[] array on the source task. The source can always answer "what did I spawn?".
  • Back link. A new derivedFrom { sourceKind, sourceId, sourceRunIndex, continuationId, intent } field on the child's TaskInfo, modeled exactly on the existing EpicId field in backend/Shared/Models/TaskInfo.cs (same persistence, same boot-normalize-to-null, behavior-neutral when absent). The child can always answer "where did I come from?". Resolving the link is a pure id-join, no output scraping, consistent with ADR-0002 (deterministic over prompt-trust).
  • Why not reuse EpicId. EpicId means container membership and decomposition. A Continuation means lineage and iteration (one artifact, one chosen next step, possibly cross-mode research to coding). Keeping them separate avoids overloading the epic-decomposition path in backend/Features/Runner/ProjectRunner.cs (DecomposeEpicAndCreateSubTasks, lines 4832-4876).

The four typed actions (text-only menu items)

  1. Promote / Continue. Turn the report into the next task(s). Generalizes promote-to-coding to be intent-aware and mode-agnostic, lifting the planning-only BadRequest at TaskCrudEndpoints.cs:205 so research can promote too. Opens the existing create-task modal pre-filled (prompt body from the report, images copied byte-for-byte per the planning-research decision, intent preselected, plus an editable Steer box). On Save, childJobId is stamped and derivedFrom is written in the same atomic mutation.
  2. Reissue with steer. Re-run the same read-only task with the operator's added direction (continue endpoint, mode=steer), producing a v2 report. This is the iteration loop.
  3. Log decision and archive. Record the conclusion in the per-project decision journal (ReviewDecisionRecord, kind=Research/Planning), move to 6-completed. This captures the "I reviewed and chose direction X / chose not to continue" case as durable evidence, so a later coding task can cite "preceded by research task X."
  4. Discard. The report did not help; archive without spawning work.

Intents map onto existing pipelines

  • promote-to-coding → child mode=coding, state=1-preparation (today's promote, now linked and extended to research).
  • deeper-research → child mode=research, web on, parent report pre-seeded into the prompt.
  • next-slice → coding child carrying a sliceOrdinal, so lineage reads Slice 1, 2, 3.
  • decision-only → no child task; writes a decision-journal record plus a timeline entry.
Fan-out is native

Because the Continuation is an array, one report can spawn N children. "Make 5 comparison concepts, I pick these 3, we continue" is supported directly. Each spawned child runs its own lifecycle (a coding child gets a worktree and full pipeline; a research child stays read-only), and the Research to report to Slice 1 to Slice 2 chain is a visible, navigable lineage thread.

Human-gated by default

Spawning is an operator click, not an in-run auto-decision. A typed SPAWN_FOLLOW_UP decision kind is added to ReviewDecisionOrchestrator as a clean seam but ships default-OFF, with a depth cap and a MaxAutoContinue guard (mirroring MaxAutoReissueAttempts). This preserves "operator reviews first; 5-human-review is a WANTED gate" and avoids any overnight auto-fan-out.

5. Build plan

Incremental, each slice independently shippable. Slices 0 to 2 deliver the reviewable artifact and honest terminal state; 3 and 4 close the continue loop; 5 and 6 are optional.

  1. Slice 0 — Report contract + prompt framing Extend prompts/runtime/mode-framing-readonly.md to require a self-contained results/report.html (inline CSS, no external network) alongside status.md, with stable required regions: header (confidence + scope), body, open-questions, plus Sources (research) and a Proposed-next-steps list for the continue parser. Add a fenced confidence block (high | medium | low) the host parses deterministically. Add a structural unit test guarding the template, mirroring existing sentinel-template guards.
    No backend behavior change. The read-only pipeline already runs and writes results/.
  2. Slice 1 — Report tab + verdict strip Add a Report inspector tab on task-detail that is the default tab for read-only tasks (coding unchanged). Render results/report.html in the wiki's existing sandboxed iframe pattern (<iframe sandbox="allow-scripts" [srcdoc]="trustedHtml()"> plus DomSanitizer.bypassSecurityTrustHtml). Deliberately omit allow-same-origin. Fall back to beautiful-results over status.md when no HTML exists. Above the iframe, render a host (Angular) sticky verdict strip (sentinel banner + confidence chip or "undeclared" + open-questions counter), parsed from the sentinel and the fenced confidence block, not the HTML body.
    Reuses project-wiki-section.html rendering and the beautiful-results renderer. Only new UI: one tab plus the strip.
  3. Slice 2 — Lifecycle terminal-state correction Make the read-only orchestrator-decision step route a finished read-only task to 5-human-review with verdict=report-ready (never accept-to-develop, never park in 4-auto-review). Model the landing as an awaiting-decision substate, reusing the escalated-lane substate split, not a new folder lane. Keep the ReadOnlyPipeline a pure git-filter of StandardPipeline. Wire containment violation, empty-results, and BLOCKED/NEEDS_INPUT outcomes to the same surface with their reason summary.
    Depends on the escalated-lane substate split, or ships a minimal read-only-scoped substate flag.
  4. Slice 3 — Continuation primitive Add the behavior-neutral derivedFrom field on TaskInfo (modeled on EpicId, with boot-normalize-to-null and unit tests like the mode field had). Add the continuations[] ledger on the source (candidate, committed, resolved). Generalize the promote endpoint to be intent-aware and mode-agnostic (lift the planning-only reject at TaskCrudEndpoints.cs:205). On create, stamp childJobId and write derivedFrom atomically. Copy images byte-for-byte so children stay self-contained.
    Reuses BuildPromoteToCodingPlan in backend/Features/Tasks/TaskScannerService.cs (lines 523-546).
  5. Slice 4 — Decide-then-continue action bar + lineage UI On the decision surface (and the analysis-report drilldown), add the text-only four-action bar: Continue from this (intent picker) opening the pre-filled create modal with an editable Steer box; Reissue-with-steer; Log-decision (writes ReviewDecisionRecord); Discard. Support fan-out. Present lineage: a "Derived from" chip on the child header (modeled on the epic-link chip, click navigates to source) and a "Continued as" list on the source.
  6. Slice 5 — Typed SPAWN_FOLLOW_UP decision (default OFF) Add SPAWN_FOLLOW_UP to ReviewDecisionOrchestrator to auto-commit a single high-confidence candidate Continuation only when a project explicitly arms auto-continue. Ship default-OFF. Self-bounding: depth cap on the derivedFrom chain plus MaxAutoContinue. Never fan-out, never for research, child lands in 1-preparation (held, not auto-picked).
  7. Slice 6 — Cross-project report index (optional) Register each published report as an analysis-report record (scope.kind=Task, scope.jobId, topic=planning-and-research) so it also appears newest-first in the project-level analysis-report drilldown, giving an "all my research and concept reports" view. Markdown-is-durable fallback holds.

6. Open questions

Default tab override

For planning/research, should the Report tab replace Protokoll as the default, or just be added (coding unchanged)? Changing the default tab is a small navigation-model change. Confirm read-only tasks should open on the report rather than the run log.

5-human-review overloading

This parks reports in 5-human-review as awaiting-decision, distinct from coding's awaiting-acceptance. That needs the escalated-lane substate split first, or a minimal read-only-scoped flag. Options: (a) gate on the substate split shipping, (b) ship a minimal scoped flag now, (c) temporarily route reports to a different surface.

Research promote scope

Today promote-to-coding hard-rejects research (TaskCrudEndpoints.cs:205), and the prior design deliberately gave research no promote button. The operator vision explicitly wants research to decide and continue. Confirm research should get continuation actions, overriding the prior decision.

HTML richness vs sandbox

sandbox="allow-scripts" supports self-contained interactive reports while the omitted allow-same-origin keeps an opaque origin. Reports that need same-origin or controlled network integration belong in the Workbench viewer.

Auto-continue appetite

Slice 5 ships SPAWN_FOLLOW_UP default-OFF. Given prior overnight bulk-run incidents, do you want auto-continue at all yet, or keep the loop fully human-gated and treat Slice 5 as a future-only seam?

Wiki publish location and lifecycle

Reports publish to docs/research/<slug>.html as the one git action of a read-only task. Confirm the path convention, and whether a superseded report (after a reissue v2) should overwrite, version (v1/v2), or accumulate as separate wiki pages.

Confidence signal source of truth

The verdict-strip confidence chip is parsed from an agent-emitted fenced block; absent it shows "undeclared". Is host-parsed agent-declared confidence sufficient, or do you eventually want an independent report-quality grade, noting that adding a verdict step would diverge the ReadOnlyPipeline from the StandardPipeline lock-step we are deliberately preserving?
