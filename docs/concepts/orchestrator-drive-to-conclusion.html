1. Zielbild (the target)

The orchestrator always drives a task to a real conclusion. Every run ends in exactly one of four owned terminals, and a task can never sit in 3-progress without either a live process or a scheduled wake.

The hard requirements that this concept must satisfy:

  1. Drive the task home. The orchestrator must reliably carry a task to a real conclusion.
  2. Infra death is normal. A CLI crash, exitCode=-1, or a dead host is acceptable and expected. On an infra crash, retry at least once, up to 3 total attempts, with a cooldown step between attempts. No endless burn-in, no infinite reissue loop.
  3. No "classifier-unknown". The marker gives the operator nothing and is confusing. There must be no classifier-unknown terminal, marker, chip, or chat line anywhere.
  4. Honest human-review terminal. When the orchestrator cannot conclude after N attempts, the task goes to 5-human-review with an explicit, honest reason such as "orchestrator could not conclude after N infra retries; kept the loop, handing to human." That reason is the track. Never leave a task stranded in 3-progress.
  5. Failures stay visible. The operator wants to see that there were problems, but the goal is always: the thing gets finished.
  6. Prefer session-resume. On retry, prefer resuming the same run over a from-scratch rebuild, so good partial work is not thrown away.

The four-terminal model

Every post-run path ends in exactly one of four owned terminals. Two transient states feed them:

StateKindDestinationMeaning
Running transient 3-progress The CLI is alive.
CooldownRetry transient 3-progress An infra crash with retry budget remaining. The task is held with a visible "infra-crashed, retrying k/3 in Ns" banner and a scheduled re-pickup after a backoff delay. It is always time-bounded by a real timer (never the 60-minute boot sweep, never a busy-loop).
SteerPending transient 3-progress An auto-mode run asked a steer / NeedsInput question and released its live CLI seat. A durable start time drives the visible "Waiting for answer" timer and a bounded wake: after the configured timeout, the task either receives an unambiguous context-derived answer or reaches a blocked human escalation.
Succeeded terminal 4-auto-review Positive terminal sentinel ([[TASK_DONE]] / [[TASK_NOOP]]) or committed-partial work. The existing 3-stage review then owns 4 to 5.
NeedsReview terminal 5-human-review A non-success terminal a human must look at: a [[TASK_BLOCKED]] / [[TASK_NEEDS_INPUT]] sentinel, or a genuine logical failure (failed exit, agent text present, no sentinel, no commits). Carries a concrete reason. Absorbs everything that used to be classifier-unknown-with-text.
GaveUpToHuman terminal 5-human-review The orchestrator exhausted its infra-retry budget. Honest reason: "orchestrator could not conclude after N infra retries; kept the loop, handing to human." The explicit replacement for silent stranding.

Invariant: a run can only leave Running into one of {Succeeded, NeedsReview, GaveUpToHuman, CooldownRetry, SteerPending}. CooldownRetry and SteerPending must each terminate in one of the three terminals or schedule a concrete continuation. No path leaves a task parked in 3-progress without either a live process or a scheduled wake. The 9-day-stranding state is structurally unreachable.

2. How it works today, and the gap

A run that ends status=failed with no terminal sentinel and no commits is a structural dead-end today. Three confirmed code facts make it strand:

Fact 1: the lane never advances

TerminalRunOutcomeClassifier.Classify returns ShouldMoveToReview=false for the failed / no-sentinel / no-commits case. The commitsDuringRun > 0 case escapes via CommittedPartial; only the no-commit case strands. Unknown outcomes get ShouldMoveToReview=true only when status=="completed".

backend/Shared/Runner/TerminalRunOutcome.cs (lines 48-153; strand at 121-127, partial-escape at 111-119)

Fact 2: the marker is born, then re-issued once, then accepted

AgentOutcomeAnalyzer.ResolveIssueKind stamps RunIssueKind.ClassifierUnknown on every failed run with agent text (if (failed) return RunIssueKind.ClassifierUnknown;). RunOutcomePolicy.Decide then re-issues exactly once (MaxSoftInterventionAttempts = 1, MaxAutoReissueAttempts = 1) and on exhaustion returns NotifyUserAndAccept with the visible classifier-unknown marker, not NotifyUserAndStop.

backend/Shared/Runner/AgentOutcomeAnalyzer.cs (line 501; heuristic at 493)
backend/Features/Runner/RunOutcomePolicy.cs (lines 57-59, 341-374; meta strings at 356 and 369)
backend/Features/Runner/OrchestratorChatLog.cs (line 160, the OrchestratorMessageKind.ClassifierUnknown tag)

Fact 3: no escalation path catches it

RunIssueKind.ClassifierUnknown is absent from ProjectRunner.ShouldRouteIssueToHumanReview (which lists only PermissionBlocked, WatchdogTimeout, EnvironmentBlocker, EmptyFastExit, ContextOverflow, Quarantined, AgentGitViolation). The NotifyUserAndAccept branch never reaches the EscalateAsync call, which is gated on NotifyUserAndStop. The lane move only happens when movedToReview == true, which is computed from the false ShouldMoveToReview above.

backend/Features/Runner/ProjectRunner.cs (movedToReview at 4357; escalation gates 4493-4605; lane move 4648-4706; allow-list 4878-4885)

The gap: no lane advance and no escalation. The run is stamped classifier-unknown, re-issued once (a reissue that always rebuilds from scratch and discards in-progress work), and then accepted with a marker that moves nothing. The task stays in 3-progress indefinitely.

Why infra death looks like a logical failure

On Windows, Process.Kill hands back exitCode=-1 regardless of intent. RunStatusClassifier.Classify deliberately collapses -1 and 1 to "failed" when RunStopReason == None (any non-None reason wins and yields "stopped"). So the system today cannot tell an infra crash from an agent failure. A hard crash mid-productive run leaves a partial output buffer that the heuristic reads as a "substantial reply without a parseable verdict" and the run falls through to classifier-unknown.

backend/Shared/Runner/RunStatusClassifier.cs (lines 84-98; Windows note at 8-9)
backend/Features/Cli/Execution/CliExecutionServiceBase.cs (lines 1063-1071, where exitCode and StopReason are read)

Why no background safety net rescues it

The recovery layers exist but none moves a stranded 3-progress task during uptime:

  • HardHealthChecks.NoProgress emits a Warn advisory only; it takes no action. backend/Features/Supervisor/HardHealthChecks.cs, backend/Features/Supervisor/HardHealthCheckHostedService.cs
  • AutoInterventionHostedService is disabled by default, and even when enabled CancelRun only stops the run; it does not move the folder. backend/Features/Supervisor/AutoInterventionHostedService.cs
  • RunQuarantineBreaker counts soft no-progress failures; exitCode=-1 crashes are not in scope. backend/Features/Runner/RunQuarantineBreaker.cs
  • CrossSlugInfraCircuitBreaker dedupes by slug, so one broken job does not trip it. backend/Features/Runner/CrossSlugInfraCircuitBreaker.cs
  • RapidCrashBreaker adds exponential backoff (15s / 60s / 240s, cap 900s) but does not move the folder. backend/Features/Runner/RapidCrashBreaker.cs
  • StaleProgressArchiver would recover the task, but only at boot time and only after the stale window (default 60 minutes), not during uptime. backend/Features/Runner/StaleProgressArchiver.cs
Net effect: a hard CLI crash that produced output but no sentinel automatically re-issues (losing context), then accepts a marker that moves nothing, and no live background service rescues it. That is the ASS-1757 strand.

4. The plan

Retry + cooldown policy

Retry applies only to the infra-crash class. Logical conclusions (sentinels, real failures) never retry.

  • Budget: up to 3 total attempts per task per run-chain (attempt 1 = original run, +2 infra retries), replacing the implicit MaxAutoReissueAttempts = 1.
  • Engine: reuse the existing CompletionRetrigger (already a bounded retry-transient-abort-then-escalate engine, already counts budget per job and resets on lane exit, already logs attempt N/N and sessionResumed). Widen IsTransientAbort from watchdog-timeout-only to also accept the infra-crash kind, and bump DefaultBudget from 2 to 3. backend/Features/Runner/CompletionRetrigger.cs (lines 54, 61-62); wiring in backend/Features/Runner/ProjectRunner.cs (4524-4567)
  • Cooldown: between retries the task enters CooldownRetry for a backoff delay; reuse RapidCrashBreaker.Backoff (15s / 60s / 240s, cap 900s) awaited inside the existing re-spawn Task.Run before RunCliAsync. No burn-in, no infinite reissue. backend/Features/Runner/RapidCrashBreaker.cs; re-spawn at ProjectRunner.cs 4556-4566
  • Exhaustion: when the third attempt still infra-crashes, transition to GaveUpToHuman and escalate to 5-human-review. No fourth attempt.

Session-resume preference

Each retry uses RunIntent.UserContinue + ContinueModes.Continue so it resumes the live session first (the RunPlanner resume path) and only falls back to recovery-from-job-folder when the session is genuinely gone. That fallback consumes one attempt; it does not reset the budget. The current defect is the reverse: a reissue always sets MarkSessionChainRecovery on the continue path and rebuilds from scratch, throwing away good partial work. Making resume the default preserves work like ASS-1757's 5-slice plan.

The discriminator (infra crash vs logical conclusion)

Built only from signal already in the code (RunStopReason + exitCode + sentinel + commits):

  • Positive sentinel present → Succeeded (sentinel always wins).
  • [[TASK_BLOCKED]] / [[TASK_NEEDS_INPUT]] → NeedsReview.
  • RunStopReason in {UserStop, FollowupPause} → not terminal (existing pause/continue path, untouched).
  • RunStopReason in {Watchdog, Cancelled, QuotaCapExceeded} or (exitCode < 0/non-zero AND no agent terminal text AND no commits) → infra crash → CooldownRetry if budget remains, else GaveUpToHuman. This is the ASS-1757 path.
  • Failed exit WITH substantial agent text but no positive sentinel and no commits → NeedsReview ("failed without terminal sentinel"). No re-issue, no "unknown".
  • Failed exit WITH commits → Succeeded via CommittedPartial (unchanged).

Honest escalation wiring

Add the two new kinds (InfraCrash, OrchestratorInconclusive) to ShouldRouteIssueToHumanReview and map them in ToEscalationCategory. Add two constants in HumanReviewEscalation.cs: InfraCrashRetriesExhausted = "infra-crash-retries-exhausted" and OrchestratorInconclusive = "orchestrator-inconclusive". The existing EscalateAsync fall-through fires for both once the budget is exhausted. No failed/unclassified run may ever return NotifyUserAndAccept again; that is the structural invariant that closes the stranding gap.

Visibility (loud, but non-blocking)

Failures stay loud while the task still finishes:

5. Open questions

  • Cooldown shape. Reuse RapidCrashBreaker.Backoff as-is (15s / 60s / 240s) for zero delta, or a gentler infra-specific curve (e.g. 30s / 120s) that is cleaner semantically?
  • QuotaCapExceeded. Should it count as an infra crash (retry) or escalate immediately? A quota cap will just re-hit on an immediate retry, so it may deserve its own category rather than burning 3 attempts.
  • Inconclusive track. Does OrchestratorInconclusive deserve its own card track / reason string distinct from a plain logical NeedsReview, or is one honest reason text enough? (Affects the UI step.)
  • Budget across resume-fallback. Should a retry that had to rebuild-from-job-folder (session genuinely gone) cost the same as a clean resume, or cost extra? Current plan: counts the same.
  • Boot-time sweep. Retire the StaleProgressArchiver 60-minute sweep, or keep it as a belt-and-braces backstop once CooldownRetry guarantees a scheduled wake? Keeping it is harmless but is a second source of truth.
  • ADR. Is a full ADR warranted for the four-terminal drive-to-conclusion policy, or does this wiki page plus the run-outcome contract update suffice given ADR-0002 / 0017 / 0025 already exist?
  • StopReason coupling (risk). The discriminator depends on RunStopReason being stamped at every kill/cancel site. A path that kills a process without setting it and leaves substantial text would misclassify as NeedsReview (benign, human-visible) rather than CooldownRetry. The watchdog, sleep-detector, and cancellation sites must reliably stamp Watchdog / Cancelled.
