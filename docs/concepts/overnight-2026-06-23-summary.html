2. The big diagnosis — why tasks never complete

Fresh coding runs do 1–5 min of real work, commit nothing, then die with exit=-1 and escalate. Through controlled experiments I proved this is claude-code (2.1.186) terminating itself, NOT the orchestrator:

Ruled OUT, each with evidence:
  • Orchestrator kill — RunStatusClassifier: status=failed+exit=-1 only occurs with StopReason==None; any runner Stop() would be status=stopped.
  • Phase watchdog — budgets are 600–1200 s; deaths happen at 152–274 s.
  • Clean-context — shared context crashes identically.
  • Model — Opus and Sonnet both die.
  • node heap OOM — stderr is captured unconditionally and was empty; a node OOM prints "FATAL ERROR … heap out of memory" to stderr.
  • Native crash — no Windows Error Reporting event. Defender — no detections. Pipe-block — stderr is drained. Memory — freeing RAM didn't change it.
Shape: a tool "started", then ~75 s of silence, then exit=-1 with no error anywhere = an external TerminateProcess (exit=-1, empty stderr, no WER) or a claude-code-internal exit(-1).

Why this matters: it redirects the investigation away from the orchestrator (where the effort was going) to the actual culprit. Next steps (CLI/OS side): capture the raw OS exit code via P/Invoke instead of the normalized -1; ProcMon/ETW trace of who calls TerminateProcess on claude.exe; try a different claude-code version; check for a Job Object on the VS Code / terminal parent.
