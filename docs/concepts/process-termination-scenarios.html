Process Termination & Abort Scenarios — Test Suite

Status: maintained living page (seeded 2026-06-23 overnight). The single re-findable specification of what must happen when a coding run is killed, crashes, or aborts — for both the Claude Code and Codex CLIs — and whether the user can see what happened. Each scenario is a repeatable test case. This is the companion spec to the hardening chronicle (incidents, invariants & sessions).

Prime directive. No matter how a run ends, the task must reach a terminal lane with an honest, visible reason. Nothing silently strands in 3-progress; nothing silently pauses. "Visible" means the feed/orchestrator-log carries the reason and the card lands in a lane a human can act on. The orchestrator's job is to keep the pipeline moving — recover automatically where it can, escalate honestly where it cannot.

1. How a run end is classified

A finished CLI run flows through three pure stages, then a routing decision:

  1. AgentOutcomeAnalyzer.Analyze(lines, status, durationSeconds, exitCode) → an AgentOutcome with a Kind (Done/Blocked/NeedsInput/Progress/NoOp/Unknown) and a typed IssueKind.
  2. RunOutcomePolicy.Decide(...) → an OutcomeAction (Accept / NotifyUserAndAccept / ReissueWithStrongerFraming / NotifyUserAndStop).
  3. ProjectRunner.OnCliFinished routes on that action: move-to-review, abort-review, completion-retrigger, route-to-human-review, or — the backstop — StrandedRunBackstop.MustEscalateStrandedRun for any genuinely failed run that no typed route claimed.

Key status facts: exitCode < 0 is the Windows Process.Kill artifact (a hard death). RunStatuses.Failed = "failed", Stopped = "stopped" (deliberate), Completed = "completed". A failed run with zero agent text is NoAgentOutput; with real text it splits into InfraCrash (exit<0) vs OrchestratorInconclusive (other).

3. Running the suite

The deterministic core is repeatable with the backend test project:

  • dotnet test backend.Tests/OrchestratorApi.Tests.csproj --filter "FullyQualifiedName~StrandedRunBackstop|FullyQualifiedName~RunOutcome|FullyQualifiedName~AgentOutcome|FullyQualifiedName~Quarantine|FullyQualifiedName~RunStatus|FullyQualifiedName~Pickup"
  • The full suite is the deploy gate (post-build-test-gate); a red invariant blocks the deploy.
  • S1–S5, S7, S8 are locked by pure/contract tests today. S6 is partly covered by CrashRecoveryServiceTests. S9–S12 are open and tracked as tasks below.

4. Open gaps → tasks

Each open/partial row becomes a task. The invariant for every one of them: red-on-violation test behind the gate, so the scenario can never silently regress.

  • S2/S10 retry-with-cooldown from 2-ready. A rapid-crash below the quarantine threshold should move the task back to 2-ready (carrying its backoff) so the retry actually fires, instead of relying on a never-re-picked 3-progress task. Today the backstop routes it straight to human-review (no strand, but no retry).
  • S11 self-healing worktree. Prune + force-recreate an orphaned worktree path before a run. Test: a pickup with an orphan dir at the target path still succeeds.
  • S12 child-process teardown. Kill the node/esbuild/dev-server tree on run end or failure. Test: after a run ends, no build child has a CWD under the run's worktree.
  • S6 abort visibility. A host-crash recovery should leave an explicit, user-visible "this run was interrupted and recovered" trace, not just a silent lane transition.
  • S9 codex silent completion. Move codex off sentinel-scraping onto the official SDK process-exit / App-Server contract (ADR-0013, AGT-833).
  • Integration kill-test harness. A deterministic ProjectRunner test that drives a fake CLI to fire OnFinished with each abort shape (exit<0, exit=1 no-output, exit=1 with-output) and asserts the resulting lane — end-to-end, not just the pure classifier.
  • CLI-unavailable loud surface. A missing CLI must HALT loudly (modal + escalation), never pause silently (AGT-1775).
