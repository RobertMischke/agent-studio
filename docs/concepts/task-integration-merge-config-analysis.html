Task Integration & Merge: Configuration Analysis

How a finished task's work reaches the integration branch, why the current behaviour is hard to reason about, and a proposed parallelism-independent Integration Policy. Audience: operator (product owner) and engineers.

1. Executive summary

Whether and when a finished task's work reaches the integration branch (normally develop) is decided almost entirely by one number: MaxParallelism on the project. The operator reads that number as a pure throughput dial ("how many tasks run at once"). In reality it silently selects between two structurally different git pipelines.

The core problem Changing MaxParallelism from 1 to >= 2 changes, all at once and with no UI that says so: where work is committed, which branch is the integration source, when the merge happens, what git command performs it (and therefore the shape of the recorded history), how conflicts are handled, and what the operator's "Accept" click actually does.

The single line that makes this decision is the guard in backend/Features/Runner/ProjectRunner.cs at the top of IntegrateWorktreeRunAsync (around line 909): it returns early unless the run is a worktree run, and "is a worktree run" is derived purely from MaxParallelism > 1. The deferred merge step (backend/Features/Pipeline/MergeIntoDevelopRunner.cs), triggered on operator acceptance in backend/Features/Tasks/TaskTransitionService.cs (around line 223), runs on every acceptance and is parallelism-independent; it simply no-ops as "already merged" when run-end integration already landed the branch.

Two of the most important integration knobs already exist in the backend but are invisible: IntegrationBranch (default develop) and IntegrationStrategy (default direct-merge) in backend/Shared/Models/ProjectSettings.cs (lines 139 and 147) have no frontend control. The pull-request strategy value is parseable but is a dead path that records as an integration failure.

Recommendation: introduce one explicit, parallelism-independent Integration Policy that owns when/where/how work merges, and demote MaxParallelism to a pure concurrency/isolation knob. Ship it phased, behaviour-preserving by default, reusing the backend plumbing that already exists. Detail in sections 4 and 5.

2. How integration works today

There is no single "merge engine." Two unrelated code paths exist, and MaxParallelism alone picks which one runs. Defaults (MaxParallelism = 1, AutoCommit = true, AutoPushStrategy = on-completed, IntegrationBranch = develop, IntegrationStrategy = direct-merge) are confirmed in backend/Shared/Models/ProjectSettings.cs (lines 6, 13, 130, 139, 147).

Aspect Sequential — MaxParallelism == 1 (default) Parallel — MaxParallelism >= 2
Where the agent runs Shared main checkout. Normally no task/<id> branch. Isolated worktree on a task/<id> branch cut from IntegrationBranch.
When work is committed On the 3-progress → 4-auto-review transition, before the lane move, via TaskTransitionService.TryAutoCommitAsync (around lines 107-114). Commits directly onto whatever HEAD points at (usually develop). At run end inside ProjectRunner.IntegrateWorktreeRunAsync (WorktreeRunCommit, around line 933), onto the task/<id> branch.
When the merge happens Deferred. Only when the operator accepts (5-human-review → 6-completed), via MergeIntoDevelopRunner.Run triggered at TaskTransitionService ~line 223. Automatic. At run end, before the task ever reaches the review lane and before any human looks at it (Worktree.Integrate, around line 992).
Merge command / history shape git merge --no-ff --no-edit — an explicit merge commit, original SHAs, a single revertable delivery (GitService.MergeBranchIntoIntegration). Rebase onto tip, then git merge --ff-only — task commits are rewritten (new SHAs), linear history, no merge commit (WorktreeTaskLifecycle.Integrate, GitService.MergeFastForward).
Serialization Implicit (single active job; one shared checkout). Explicit per-project merge-queue lock plus an integration lease (_integrateLock, around lines 944-962).
Conflict handling Abort, leave the tree clean, record the step Failed with the conflicted files; operator resolves by hand. Preserve the conflict in place and escalate to a managed Codex conflict-resolution agent that may auto-resolve and complete the merge unattended (RunConflictResolutionStepAsync).
What "Accept" means Acceptance is the gate that performs the merge. Nothing reaches the branch until a human clicks. The branch was already advanced at run end. Acceptance is post-hoc; the deferred merge step just records "already merged."
Push / durability Commit stays on the local checkout; pushed per AutoPushStrategy at accept time. task/<id> is pushed to origin at run end for portability; the advanced integration branch is not necessarily pushed at the same instant.
IntegrationBranch / IntegrationStrategy Ignored entirely. The sequential path has no per-project integration-branch concept. Both consulted: branch is the fork/merge target; strategy selects direct-merge (implemented) or pull-request (dead path).
Dead path IntegrationStrategy = pull-request parses and is selectable (IntegrationStrategies.All), and WorktreeTaskLifecycle.Integrate returns IntegrationOutcome.PushedForReview for it, but ProjectRunner.IntegrateWorktreeRunAsync has no case for that outcome. It falls into the catch-all and records "Integration failed with outcome PushedForReview." PR creation is concept-only (ADR-0052 section 8.6); it is not implemented.
Documented intent vs. code The Zielbild (the retired git-branching-integration-zielbild.md draft, superseded by docs/concepts/release-semantics.md) prescribed a three-tier model (task/<id> → develop-local → develop) with named profiles (direct / local-then-direct / local-then-mr). The code implements no develop-local intermediate tier and merges task/<id> straight into develop in both paths. ADR-0052 frames MaxParallelism == 1 as the legacy path kept byte-for-byte identical (confirmed in the MaxParallelism doc comment in backend/Shared/Models/ProjectSettings.cs).

3. The three concerns

Each concern is given as: what the operator observes, why it is a problem, the worst concrete scenario, and the steel-man counter-argument.

Concern 1: integration semantics are coupled to a throughput knob Severity: medium

What the operator observes

You raise MaxParallelism from 1 to 2 to clear a backlog. You expect the same outcomes, just faster. Nothing on the Settings page suggests anything else changed.

Why it is a problem

Flipping that one integer simultaneously changes the commit target, the merge timing and trigger, the merge command and history shape, conflict handling, and the meaning of acceptance (see section 2). The mental model "more parallelism = same result, more throughput" is false, and the two knobs that would let you reason about it (IntegrationBranch, IntegrationStrategy) are not even visible.

Worst concrete scenario A reviewer relies on "each accepted task is one merge commit I can git revert in a single step," which holds in sequential mode (git merge --no-ff). The operator bumps parallelism to 2 for speed. Now work auto-merges into develop at run end with no human gate, and history flips to rebase + --ff-only with rewritten SHAs and no merge commit. The single-commit revert that worked yesterday silently stops working, purely because the parallelism number changed.
Steel-man counter-argument The coupling is deliberate and documented (ADR-0052). The technical reasons are real: with one shared checkout you cannot have N tasks editing concurrently, so worktree isolation is only needed and only possible when max > 1. Rebase + --ff-only is the correct primitive for keeping N branches integrating cleanly through a serialized queue; --no-ff is the right primitive for a human-gated single delivery. Auto-merge at run end is arguably necessary in parallel mode so later tasks rebase onto current work. The acceptance gate still exists (CanCompleteEscalatedJob blocks completion until the commit is an ancestor of the integration branch), and the safe path is the default. The real defect is the missing UI/documentation surface, not the coupling itself.

Concern 2: merge behaviour is scattered across surfaces with no single "merge configuration" Severity: medium

What the operator observes

Project Settings shows only "Max parallelism," "Auto-commit," and "Auto-push." You reasonably conclude these govern integration. You cannot answer "which branch does my work merge into?", "when does it merge?", or "do I get a PR or a direct merge?" from that page.

Why it is a problem

What actually governs integration is spread across four disconnected places: MaxParallelism (silently flips the whole mechanism); AutoCommit + AutoPushStrategy (commit and push, under a generic settings view); IntegrationBranch + IntegrationStrategy (real backend fields, no editable UI, no write call from the frontend); and the deferred/automatic merge steps themselves (surfaced only as read-only rows in a Workflow page that defers all merge config to "after the Git concept"). The Settings page implies one project-wide merge policy; the code has two.

Worst concrete scenario The operator sets Auto-push to "On completed" and reads the hint literally: it states completed pushes use git push origin <sha>:refs/heads/main. They believe completed work pushes to the integration branch they saw mentioned (develop). In fact the on-completed push falls through to GitService.PushShaAsync, whose targetBranch defaults to main (around line 1284) and which runs git push origin <sha>:refs/heads/main (around line 1319), while the separate MergeIntoDevelopRunner merges into develop. Two different branches, neither operator-chosen, contradicting each other in the same UI.
Steel-man counter-argument This is largely by design. The team deliberately froze per-transition and MR git config behind the Git-concept decision, and the Workflow page only surfaces implemented behaviour on purpose; exposing a half-wired pull-request would be worse than hiding it. IntegrationBranch and IntegrationStrategy only matter when MaxParallelism > 1, an advanced opt-in. Commit, push, and merge genuinely are separate concerns, so splitting their controls is arguably correct factoring. The push-to-main default may be intentional for a specific release model. The unrebutted part, though, is the clarity defect: the page implies one policy while the code has two, and the surfaced auto-push hint names a branch that contradicts the merge target.

Concern 3: auto-commit on transition produces a not-clearly-defined git state Severity: medium

What the operator observes

In the default sequential mode the auto-commit on 3-progress → 4-auto-review lands directly on whatever the shared checkout's HEAD points at (in practice develop), and no task/<id> branch is created. The pipeline UI still shows a "Merge into Develop" step.

Why it is a problem

Three downstream mechanisms (the deferred merge step, the escalated-acceptance ancestor gate, and the completed-push) were written assuming a task/<id> branch exists and that the integration branch is a clean target. That assumption silently does not hold in sequential mode, so the operator cannot reliably predict which branch the work ends up on, whether the "Merge into Develop" step did anything, or which remote ref the push lands on.

Worst concrete scenario Sequential defaults. The agent runs on the shared checkout (on develop); the auto-commit lands the work directly on local develop with no branch switch. The operator accepts. The deferred MergeIntoDevelopRunner.Run tries to merge task/<id>, finds no such branch (BranchExists is false), returns NoTaskBranch, and records the step as Skipped: no task branch to merge. The operator sees a merge step that "did nothing" even though the work is already in develop, and cannot tell from the board whether their work was delivered or dropped. The merge step is decorative in this mode.
Steel-man counter-argument This is arguably correct for the solo dogfooding path. ADR-0052 states direct-merge is the solo path and already implies no review gate; in sequential mode the shared checkout is the integration branch, so committing agent work straight onto it is the intended fast path. The deferred runner returning NoTaskBranch → Skipped is fully guarded, never throws, never undoes the lane move, and is idempotent. The auto-commit scoping (session-log plus mtime) plus the "no attributable files" skip exist precisely to prevent a mis-attribution blob, with regression tests covering the cases. So the "undefined state" is really a documented divergence from a Zielbild tier (develop-local) that is not built yet, not a correctness bug in the shipped solo path.

4. Proposed target: an explicit Integration Policy

Make integration a first-class, parallelism-independent policy. The operator answers four plain questions — where work lands, when it lands, how it is recorded, and how it is handed off — and MaxParallelism becomes a pure throughput/isolation dial that provably cannot change any of those answers. Enforce that with a backend invariant test: with all Integration* fields fixed, flipping MaxParallelism between 1 and N must not change the landing branch, landing gate, merge style, conflict handling, or push target.

Setting Values Default Meaning
MaxParallelism [kept, redefined] int >= 1 (1 / 2 / 3 / 4) 1 Pure throughput and isolation only: how many runs execute concurrently, and therefore whether runs are worktree-isolated (>1) or share the main checkout (==1). Carries zero git/merge semantics after this redesign. Relabel to "Concurrency (slots)" with help text saying it does not change how, when, or where work merges. Endpoint already exists: PUT /api/projects/{name}/max-parallelism.
IntegrationBranch [surface existing] any valid branch; empty normalizes to develop develop The single integration line a completed task lands on. Used identically by the merge target and the completed-push target (this fixes the push-to-main bug, see Concern 2). Field exists in backend/Shared/Models/ProjectSettings.cs:139 with a write endpoint already present; the frontend simply never calls it. New: editable text input on a Settings "Integration" card.
IntegrationGate [new, the decoupling field] at-acceptance | at-run-end at-acceptance The single explicit control replacing the parallelism-derived merge-timing decision. at-acceptance = work reaches the branch only on 5-human-review → 6-completed (today's sequential behaviour). at-run-end = each green run folds in automatically before review (today's parallel behaviour). Both TaskTransitionService.MoveAsync (~line 223) and ProjectRunner.IntegrateWorktreeRunAsync (~line 909) consult this instead of parallelism. New PUT /api/projects/{name}/integration-gate.

Now an explicit, parallelism-independent operator choice so "every accepted task = one revertable merge commit" can be guaranteed. The merge primitive in both code paths is selected by this field.
Delivery [surface, honestly disabled] direct-merge | pull-request direct-merge How work is handed to the branch. direct-merge is the only functional path today. pull-request is a real, parseable value but a dead path (PushedForReview is unhandled and logs an integration failure). Shown on the Integration card but disabled with a "Coming soon" badge until the PR provider is wired; the dead error path is removed (route to gated acceptance, not an error). Field and endpoint already exist.
AutoCommit [kept, redefined crisply] true | false true Whether the agent's working-tree edits are captured into a scoped commit when the run finishes (3-progress → 4-auto-review; gate at TaskTransitionService ~lines 101-104, scoping via PlanAutoCommitScope). Now documented as orthogonal to where that commit later merges. Read-only modes skip it regardless. Live-read each transition. Endpoint exists: PUT /api/projects/{name}/auto-commit.
AutoPushStrategy [kept, target fixed] never | on-completed | always-immediate on-completed When committed work is published to origin. Meaning unchanged, but the target is fixed to IntegrationBranch instead of the hardcoded main default (thread IntegrationBranch through GitService.PushShaAsync; bug confirmed at ~line 1284 default and ~line 691 call site with no override). Live "what happens" summary The Integration card renders a plain-language sentence assembled from the choices, for example: "Each task lands on develop only after you accept it, as a single revertable merge commit; conflicts are flagged for you." A second sentence resolves auto-commit and auto-push into the same language so commit, push, and merge read as one story while staying distinct concerns.

5. Recommended direction and migration sketch

Adopt the explicit Integration Policy above and ship it phased, behaviour-preserving by default. The decoupling is a small, surgical cut: replace the parallelism-derived guard in ProjectRunner.IntegrateWorktreeRunAsync (~line 909) and the deferred-merge trigger in TaskTransitionService.MoveAsync (~line 223) with an explicit IntegrationGate check. Everything downstream — the merge-queue lock, MergeIntoDevelopRunner, and the CanCompleteEscalatedJob acceptance gate (~lines 119-126) — already exists and is reused unchanged. Two of the settings and their write endpoints already exist; the frontend just never calls them.

Phase 0 — UI only, zero behaviour change
  • Surface IntegrationBranch as an editable field on a new Settings "Integration" card.
  • Add the live "what happens" sentences, derived from existing fields only.
  • Fix the contradictory auto-push hint so it renders the live integration branch instead of the literal refs/heads/main.
  • Reword the Parallel-execution card to strip merge/branch language. This resolves the biggest clarity defects with no runtime-path change.
Phase 1 — introduce IntegrationGate (the real decoupling)
  • Add IntegrationGate to ProjectSettings, default at-acceptance.
  • Backfill from current behaviour so the deploy is byte-compatible: existing projects at MaxParallelism == 1 map to at-acceptance, projects at >= 2 map to at-run-end.
  • Rewire both merge paths to consult IntegrationGate instead of inferring from MaxParallelism.
  • Add the backend invariant test (fix all Integration* fields, flip parallelism, assert nothing changes).
  • Thread IntegrationBranch into the completed-push target.
Phase 2 — surface MergeStyle
  • Add MergeStyle, default merge-commit; backfill max == 1 → merge-commit (today's --no-ff), >= 2 → linear (today's rebase + ff).
  • Select the merge primitive by this field in both paths.
Phase 3 — wire the real pull-request path
  • Handle IntegrationOutcome.PushedForReview in ProjectRunner.IntegrateWorktreeRunAsync instead of treating it as an error, then enable the "Open a pull request" control. Until then it stays disabled and badged.
Why backfill makes this safe Each new field's default is chosen so the resolved behaviour equals what MaxParallelism implied before. After the one-time backfill the settings are independent. project-settings.json gains optional string fields; absent fields resolve via the parallelism-derived backfill for one release, then default to the safe value. A brand-new project (gate at-acceptance, style merge-commit, delivery direct-merge, AutoCommit = true, AutoPushStrategy = on-completed, MaxParallelism = 1) is byte-identical to today's safe sequential path.

Deliberately deferred

The "always cut task/<id> in every mode" invariant is the cleanest long-term fix for the undefined-state issues in Concern 3 (the decorative NoTaskBranch → Skipped step, the escalated accept gate with no branch to test ancestry against, mode-divergent attribution). It touches the solo fast path that ADR-0052 froze byte-identical, so it is a later slice, not a gate on the decoupling. Likewise the Zielbild develop-local intermediate tier remains future work; until it exists, at-run-end in sequential mode means committing onto the shared-checkout integration branch.

6. Open questions for the operator to decide

  1. Presets vs. four axes. One packed profile enum (direct / local-then-direct / local-then-mr, matching the Zielbild) versus four separate controls (gate / branch / merge-style / delivery)? The four-axis model is clearer per question but allows nonsensical combinations (for example AutoCommit = false with at-run-end would merge an empty branch). Do you want presets that collapse the axes, with the axes as an "advanced" expansion?
  2. Push target. Always derive the completed-push target from IntegrationBranch (recommended; fixes the contradiction), or keep a separate explicit push-target because some projects legitimately push to a release branch (main) distinct from the integration branch (develop)? We need to know whether the stable project relies on push-to-main as its release step before flipping the default.
  3. MergeStyle as a field or folded into IntegrationStrategy. A separate field is conceptually cleaner but adds a field, endpoint, and migration; folding overloads one token with two orthogonal meanings (history shape and delivery) but reuses existing plumbing.
  4. Always-branch invariant. Adopt "always cut task/<id> in every mode" to eliminate the undefined states in Concern 3, accepting the small overhead and a real behaviour change to the solo fast path that ADR-0052 kept byte-identical? Or keep the shared-checkout fast path and live with those edge states being mode-dependent?
  5. Conflict handling as a control. Conflict handling currently diverges silently by parallelism (sequential aborts and flags; parallel escalates to a managed Codex resolver). Should this become its own explicit control (abort-and-flag / auto-resolve-agent / open-pr), or stay derived for now and merely be surfaced read-only so the divergence is at least visible?
  6. develop-local tier timing. Does the Zielbild intermediate tier need to be built before at-run-end gating is offered in sequential mode, or is committing onto the shared-checkout integration branch acceptable for the solo dogfooding path in the interim?
  7. Mid-flight changes. Should changing MaxParallelism (or any Integration field) while tasks are in progress be blocked, warned, or freely allowed? In-flight changes can leave a worktree preserved-or-abandoned and the deferred merge re-attempting.
