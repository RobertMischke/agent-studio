Agent-Studio-Zielarchitektur: drei Einheiten, zwei Pools, ein Origin

Ein Produkt, drei unabhängig deploybare Rollen. Studio bedient, der Task Server ist die zentrale Konfigurations- und Wahrheitsinstanz, die Runner-Hosts führen aus — jeder mit eigener Orchestrator-Instanz. Kommunikation ist pull-basiert und ausschließlich ausgehend; Code wandert getrennt über git origin.

§1 · Haupt-Architektur

Die drei Einheiten und ihre Kanäle

Studio spricht den Task Server über eine einzige HTTPS-Origin an — gleichwertige Gegenstelle, nicht Anhängsel. Jeder Runner-Host hält dazu zwei getrennte, ausgehende Verbindungen: er pullt Tasks (Claim/Lease) und pusht Ergebnisse (Results/Artifacts) zurück — nie umgekehrt. Quelltext nimmt einen dritten, orthogonalen Weg: ausschließlich über git origin, nie über die Task-API.

§2 · Admission

Zwei Pools je Host

Die eigene Orchestrator-Instanz jedes Runner-Hosts verwaltet Kapazität als zwei getrennte Admission-Pools. Sie konkurrieren nicht: ein voller Build-Pool bremst kein Post-Processing, und umgekehrt. So bleibt der Host unter Last zeitnah lieferfähig (AGT-2222, AGT-2228).

Pool 1 Build-Slots — dynamisch

  • Was: Coding-Runs & Build/Test-Gates — die schweren, prozess- und CPU-gebundenen Slots.
  • Kapazität: on the fly änderbar; der Runner gleicht seine Slot-Zahl zyklisch gegen die zentrale Vorgabe ab — kein Daemon-Neustart.
  • Grenze: heute RUNNER_MAX_PARALLELISM pro Host; im Ziel zentral in den Task-Server-Settings gepflegt.

Pool 2 API-Lanes — Post-Processing

  • Was: API-gebundene Nacharbeit — Review-Grade, Aspect-Findings, Evidenz-Ingest, Reconcile — leicht, aber quota-/latenzgebunden.
  • Kapazität: eigene Lane-Zahl, entkoppelt vom Build-Pool, damit Post-Processing parallel und zeitnah läuft (AGT-2222).
  • Grenze: heute PostProcessing:MaxParallelism; im Ziel je Host als eigener Pool geführt.

§3 · Autonomie

Der Runner arbeitet allein weiter

≈10 min

Bounded local spool — Autonomie ist Design, nicht Zufall

Verliert ein Host den Task Server, läuft der aktuelle Run innerhalb seines Lease-Sicherheitsfensters (~10 Minuten) weiter: die Orchestrator-Instanz claimt zwar keine neue Arbeit, aber sie führt den laufenden Task zu Ende, puffert Events/Artefakt-Chunks im lokalen Spool und spielt sie beim Reconnect idempotent nach. Kein unbestätigter globaler Übergang gilt als gesettled. Der Spool ist ein Ausfallpuffer, keine lokale Task-API — er hält keinen frei mutierbaren Klon des Boards.
