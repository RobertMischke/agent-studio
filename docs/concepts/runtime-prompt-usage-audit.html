Verdict: Almost all prompts are still in use. Of 42 prompts, 41 are reachable (19 on a default/normal run path or a running hosted service, 22 genuinely used but only on opt-in, on-demand, or edge paths) and exactly 1 is orphaned and safe to consider for removal: recurring-output-pattern-review.md. Nothing is uncertain.

The audit traced each prompt from the catalog entry to its rendering call site. A prompt counts as active when its consumer runs on a normal/default run (the core opening prompt, a default-on pipeline post-step, a mapped endpoint, or a registered hosted service that is on by default). It counts as conditional when the consumer is real and wired but only fires opt-in or on demand: resume and reissue paths, epic decomposition, crash recovery, drift post-steps (off by default), on-demand report endpoints, parallel-only conflict resolution, user-triggered code-review / title / enhance actions, and the soft-reasoning hosted service which is registered but disabled by default. It counts as dead-or-orphaned only when there is no DI registration, no endpoint mapping, and no hosted or scheduled runner.

One correction was made against an earlier per-group pass: code-review-step.md (the Verdict mode of CodeReviewStepService) was provisionally flagged for removal, but it is in fact a live mapped endpoint, POST /api/tasks/{jobId}/code-review (wired at backend/Host/EndpointMapping.cs:25 via MapTaskCodeReviewEndpoints; service registered at backend/Host/Program.cs:366). It is user-triggered rather than automatic, so it is classified conditional / keep, not dead.

2. Removal candidates

Exactly one prompt has no live consumer and is a candidate for removal.

dead  recurring-output-pattern-review.md

Consumer: RecurringOutputPatternService.BuildPrompt. The prompt is never rendered on any live path. Verified:

  • NO DI registration for RecurringOutputPatternService in backend/Host/Program.cs.
  • NO endpoint mapping. The service is absent from AnalysisReportEndpoints.cs and every other *Endpoints.cs file.
  • NO hosted service and NO scheduled runner invoking it.
  • The only references anywhere are: the class definition itself, a documentation <see cref> in SteeringDocsSummaryDriftService, and the PromptUsageCatalog entry.

Recommendation: review for removal. Removing the prompt plus the orphaned service is safe; only the catalog entry and the stale <see cref> need to be cleaned up alongside it.

All other 41 prompts are recommended to keep. The 22 conditional ones are explained in section 4 so the operator can see why a prompt may look idle on a default deployment yet still be required.

4. Notes on conditional prompts

The 22 conditional prompts are not waste. Each one is wired to a real consumer but only fires under a specific trigger, so on a default deployment with a single sequential pickup you may never see it render. They fall into a handful of recognizable categories. Keeping them is correct; they back features that must work the moment the trigger occurs.

Resume, recovery and reissue (run lifecycle)

  • runner-resume-interrupted.md, runner-resume-restart.md, runner-recovery-continuation.md: only when a run is resumed, restarted on the same session, or recovered after a crash. A normal start uses runner-fresh-start.md instead.
  • runner-reissue-change.md: only inside the auto-review reissue loop when the prior run left open items.
  • epic-decomposition.md: only for epic-typed tasks on their planning run.

On-demand and user-triggered actions

  • code-review-step.md: live mapped endpoint, invoked when the operator runs a manual code review.
  • title-generate.md, prompt-enhance.md: the Generate and Enhance buttons in the Create-task dialog. No auto-invocation.
  • commit-message.md: dual path. Active because the internal auto-commit also uses it, but the user endpoint is on-demand.

Opt-in pipeline post-steps and report endpoints

  • post-abort-review.md: DefaultEnabled=false; only on a non-clean abort when the operator has enabled the step.
  • Drift dimensions (adr-code-drift.md, software-architecture-drift.md, docs-marketing-drift.md, spec-task-job-drift.md): DefaultEnabled=false post-steps, plus on-demand /api/drift/... endpoints.
  • Code-pattern drift (code-pattern-drift-review.md, code-pattern-drift-canonical-sites.md): only the optional withLlmVerdict=true enrichment renders the prompt; the rule-based analysis always runs without it.
  • Analysis reports (steering-docs-summary-and-drift.md, roadmap-alignment-review.md): on-demand /api/analysis/... endpoints, or scheduled if configured. No automatic core trigger.

Orchestrator decision and boot sub-blocks

  • Decision prompts (orchestrator-decision-oneshot.md, -resume.md and their -attachments- sub-blocks): only in auto-continuous / auto-single mode after the agent emits NEEDS_INPUT, gated on whether a session already exists and whether the task has attachments.
  • Review-decision variants (orchestrator-review-decision-fallback.md, orchestrator-reissue-followup.md, orchestrator-no-completion-signal.md): the exception-fallback, the reissue-verdict follow-up, and the no-sentinel path. The primary orchestrator-review-decision.md is active.
  • Boot sub-blocks (global-orchestrator-self-mod-note.md, global-orchestrator-task-snapshot.md): rendered inside the active global boot only for self-modification targets, or as a best-effort snapshot wrapped in try/catch.
  • orchestrator-conflict-resolution.md: parallel-mode only (maxParallelism>1) when a worktree merge conflicts. Never reached on sequential runs.

Registered but off by default

  • supervisor-soft-reasoning.md: its hosted service is registered and ticks, but the prompt only renders when Supervisor:SoftReasoningEnabled=true. Disabled by default to avoid surprise token spend. This is why it is conditional rather than active even though the service is running.
