The 123-card Review lane is real work for the browser.

Measured performance and implementation review of the Agent Studio Angular application, centered on scrolling the large Human Review lane. This report separates observed runtime evidence from static code findings and gives one bounded improvement for every finding.

Focus case

The sluggishness is measured, not anecdotal

Stable rendered all 123 Human Review cards while only 3 intersected the viewport. Two five-second repeats averaged 43.69-48.93 FPS; p95 frame time was about 34.8 ms, with gaps up to 118 ms and a 101 ms long task in one repeat.

What is already good

The Angular fundamentals are strong

All 182 production components use OnPush. All 393 @for loops have a track expression, including stable taskKey tracking for cards. The Angular 21 app is zoneless, signal-first, standalone, and already uses native CSS render skipping.

Decision

Make board refresh single-flight first

The safest evidence-backed follow-up is to coalesce concurrent board refreshes: three snapshot pairs start during bootstrap and a 61-second grouped request can overlap the next 30-second tick. True DOM windowing and one normalized snapshot are larger, separate changes. No product code is changed by this analysis.

Critical

Runtime · DOM

P1 · Review lane

Paint skipping is present, but DOM windowing is not

Every Review card remains mounted. Native content-visibility saves some off-screen layout and paint, but it does not remove Angular components, directives, menus, event bindings, or DOM nodes.

Evidence
Stable: 123 logical cards, 123 card elements at the top and bottom, only 3 visible, 9,614 Review-lane descendants, 1.19 MB of Review-lane HTML, and zero CDK viewport markers. The 860 px scroller grew from 33,956 px to about 44,500 px during traversal as intrinsic-size estimates were corrected. stable-board-performance-measurements--real.json.
Code
frontend/src/app/features/board/components/task-column/task-column.html:201 renders the full @for. task-card.component.scss:15-23 applies content-visibility:auto. The existing transcript reference uses CDK at activity-log-view.html:60-65.
Improve
Window Review cards with overscan while preserving the shared super-column scroll surface, variable heights, taskKey identity, drag auto-scroll, menus, and highlighted-card navigation.
Effort
2-4 days. This is not a safe one-line reuse of the transcript viewport.
Medium

Change detection

Quick win

A one-second clock dirties every lane

The root updates a signal every second and binds the new value to every TaskColumn, including the 123-card Review lane. Only In Progress can display the elapsed duration. This is unnecessary fan-out, but it was not the dominant measured jank source.

Evidence
frontend/src/app/app.ts:1114-1117 starts the 1 Hz timer; app.html:297-313 passes it to all lanes; task-column.ts:163-165 exits immediately outside Progress. The 70-second rAF capture showed no repeating 1 Hz gap above 25 ms; long frames instead clustered at snapshot response completion.
Improve
Bind a stable value to every non-Progress lane and keep the changing clock inside the Progress-only status path. Add a dense Review-lane regression assertion.
Effort
0.25-0.5 day. Safe cleanup, but secondary to refresh coalescing.
Medium

Runtime · DOM

Drag support

Reorder drop zones scale with card count

A reorder-enabled 123-card lane mounts one drop-zone before each card plus a trailing zone. Each zone binds dragover, dragleave, and drop handlers, even when no drag is active.

Evidence
task-column.html:202-228. At the measured size this is 124 extra elements and up to 372 listener bindings. The column already computes insertion from card midpoints at task-column.ts:741-807.
Improve
Create per-card drop zones only while that lane is an active drag target, retaining the column midpoint fallback.
Effort
0.5-1 day with drag/reorder Playwright coverage.

Critical

HTTP · snapshots

Payload and cadence

The board downloads the same task projection twice

/api/tasks and /api/tasks/grouped each return the same 145 rich TaskInfo records in different containers. Stable sent seven of each during the 97.7-second observation.

Evidence
/api/tasks: 619,142 bytes × 7. /api/tasks/grouped: 622,419 bytes × 7. Combined transfer: 8,695,127 bytes, with no content encoding. Three pairs started within the first 0.7 s, then each endpoint started about every 30 s. Mean latency was 17.65 s / 22.85 s; maxima were 32.22 s / 60.96 s.
Code
task.service.ts:278-338 starts both requests and runner status together. Backend endpoints independently rebuild the same runtime overlays at TaskCrudEndpoints.cs:69-104.
Improve
Fetch one normalized board snapshot and derive the flat jobs signal from its lane arrays client-side, preserving task objects by taskKey when content is unchanged.
Effort
1-2 days including service and mutation regression coverage.
Medium

HTTP · polling

Redundant consumers

Shared status data is requested by multiple mounted consumers

The architecture correctly uses SignalR and visibility guards in key paths, but independent components still duplicate quota and runner reads. Slow board responses can also outlive their cadence.

Evidence
Eight /api/cli/quota calls formed four near-simultaneous pairs: two bootstrap pairs, then pairs around each 60-second boundary. /api/runner/status started four times at bootstrap and then every 30 seconds; seven of eight bodies were byte-identical. All 54 observed API calls were GETs; none failed.
Code
Header quota uses setVisibleInterval at header-quota.ts:145-152, while other quota surfaces own separate timers. Task heartbeat is guarded at task.service.ts:2176-2183.
Improve
Serve quota and runner status from one shared signal store with in-flight request coalescing and one visibility-aware cadence.
Effort
1 day.

Immediate follow-up

Quick-win separation

SOFORT card: Coalesce board refreshes and prevent overlap

Problem: Stable starts three /api/tasks + /api/tasks/grouped pairs within 0.7 seconds at bootstrap. It then starts each pair every 30 seconds even when the prior grouped request is still running; the measured maximum was 60.96 seconds. Long frames cluster at snapshot completion, not on the 1 Hz clock.

Change: Make TaskService.refresh() single-flight. Coalesce callers while a read is active and schedule exactly one trailing refresh when a push or explicit user refresh arrives during that flight. Do not change payload shape or virtualization in this card.

Acceptance: One bootstrap pair maximum; never more than one in-flight request per snapshot endpoint; a push during a flight produces one trailing refresh; no update is lost; the 70-second live trace has fewer response-aligned long frames; existing optimistic-mutation suppression tests pass.

Estimate: 0.5-1 day including service tests and a real-data trace comparison.

Why not “add trackBy” or “just use CDK”? Stable card tracking already exists. True windowing must preserve a shared super-column scroll surface, variable card heights, drag/reorder positions, context-menu portals, and scroll-to-highlight. That is a separate 2-4 day card.

Reproducibility

Method, evidence, and limitations

Runtime. Read-only capture against http://localhost:4011 on 2026-07-11, using real Stable data, Chrome 150.0.7871.101 headless, viewport 1440 × 1000. The script opened the All projects board, selected the real .lane-group__lanes scroll surface, recorded a five-second requestAnimationFrame scroll, observed long tasks, long animation frames, and layout shifts, captured CDP metrics and a DevTools trace, then watched network traffic through a 70-second continuous-rAF idle window. It issued 54 GETs and no writes; there were no failed requests or console errors.

Source audit. Production components and templates under frontend/src/app were counted with specs excluded. Board rendering, timers, stores, endpoint calls, and existing CDK use were inspected at the cited paths. “Virtualized” is deliberately split into two claims: native paint/layout skipping is present; DOM/component windowing is absent.

Bundle. Dependencies were installed from the lock file, then npm --prefix frontend run build -- --stats-json produced an Angular 21.2 production graph. Raw and estimated transfer sizes come from the build output. Generated dist/ is ignored; the full stats graph is copied to task results.

Limitations. Headless Chrome ran on the same Windows host as Stable, so FPS is a repeatable local signal rather than a hardware-neutral benchmark. The 135-second request record captures bootstrap, scroll, two 60-second quota boundaries, SignalR activity, and four heartbeat starts, but not a whole workday. Some response hashes change because live timestamp fields change even when task counts do not.
