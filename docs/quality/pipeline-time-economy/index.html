Pipeline Time Economy: where time and tokens actually go

A whole-pipeline measurement over 847 tasks. It answers a simple question with an uncomfortable split - most wall time is not compute, most compute is redo, and almost all tokens sit in one step - and it keeps deterministic facts separate from derived interpretation throughout.

Decision in one paragraph

Of 798 hours of wall time, roughly 38% is waiting (no compute), 41% is redo (retries), and 21% is first-attempt work. Of the compute itself, the LLM coding step is 66.8% and carries about 98% of all tokens; the test gate is 16.6% and carries none. Most retries are the intended orchestrator quality loop - 978 adapted reissue prompts, 78% of post-processing outcomes findings-added - not dumb repeats. Therefore: optimizing compute or test time buys throughput, not money. The money lever is the coding step - fewer and shorter model re-runs. The absolute numbers drift; the ratios do not.

§1Method, sample, and evidence classes

Every task Agent Studio runs records a per-step ledger in pipeline-execution.json: a stepId, a status, a durationMs, and token counters, for the current attempt plus an archive of previousAttempts. We aggregated those fields across all attempts over projects/agent-taskboard/tasks/** - 847 tasks that carried pipeline data, out of 1,314 task folders scanned, for 2,396 total attempts.

Following the discipline of the token-economy-task-data workbench, each figure below is tagged by evidence class:

ClassMeaningExamples here
HardDeterministic, directly counted facts about recorded runs.Step durations, per-step token counters, attempt records, gate verdicts, reissue-prompt files, outcome kinds.
InterpretationDerived quantities that need an assumption.Money cost (needs pricing), the wall-time "waiting" split (wall − step-sum), the 2000× ratio.
Model-judgedReviewer-model outputs, no ground truth.Aspect verdicts and grades - used here only to count re-run causes, never to rank quality.

Two coverage caveats that shape every number below

  • Attempt archive is capped. PipelineExecutionLog keeps at most 10 previousAttempts on disk. Tasks with more re-runs are undercounted, so all attempt and retry-time figures are a conservative floor - the live API shows individual tasks reaching 22 attempts.
  • A missing field is a gap, not a zero. Absent token or duration values are coverage gaps and must not be read as "no tokens" or "no time." The one true zero is the test gate: it is a deterministic, non-LLM step, so its zero token count is a real zero, not a gap.

§2Where compute time goes Hard

Summing durationMs per stepId across all attempts (29,808 minutes of compute total) gives a clear hierarchy. The work of writing code dominates; everything downstream of review is a rounding error.

§3Wall time: waiting, redo, first work Interpretation

Compute is only part of the story. Wall time per attempt (completedAt − startedAt) minus the sum of its step durations is the interval where the pipeline was alive but not computing. Split the compute itself into first attempt and retry, and the picture inverts the usual intuition about where effort goes.

The single largest reducible quantity is redo: if every task ran exactly once, 19,871 minutes of compute (66.7% of the total, a floor given the attempt cap) would not exist. That is a bigger lever than tests, waiting, or token trimming. But "reducible" is not "waste" - §5 shows most of it is the quality loop working as designed.

§4The retry tax - and what a retry is Hard

Precision matters here, because "retry" is easy to conflate with an unrelated mechanism. An attempt is one full pipeline execution recorded in pipeline-execution.json; a retry is any attempt after the first. In the code, a new attempt opens only when the runner re-picks-up a card after a prior run already crossed the core/post boundary (EnsureAgentRunStart → HasReachedAgentRunBoundary).

An in-run steering is a different thing and is not a retry: a steer or continue injects a message into the already-running CLI, stays inside the same core-agent-run step, and reuses the same record. It never increments the attempt counter.

EventNew attempt?What it is
In-run steering / continueNoMessage injected into the running CLI; same step, same record.
Orchestrator quality reissueYesThe orchestrator judges the result insufficient, emits a Steer/SoftIntervention message, writes an adapted prompt, and reopens the card. The dominant cause (§5).
Technical rerunYesA non-clean run end (abort-review) or a failed post-step such as a test-gate timeout.

The tax is a multiplier on the whole post-step chain. The test gate ran 1,954 times across 535 tasks that had one - about 3.65 runs per task - and 84% of its total time was retries. Reviewing aspects, grading, and integration all re-run the same way.

§5Why tasks re-run: the cause taxonomy Hard Model-judged

A raw retry count hides the important question: why did the task run again? Two on-disk sources answer it deterministically. Every orchestrator reissue writes an adapted prompt to orchestrator-follow-up-history/<timestamp>-reissue.md, and every post-step records an outcome in post-processing-outcomes.jsonl.

The dominant re-run cause is quality steering with a tailored prompt

When the orchestrator finds a result insufficient it does not resend the same prompt. It writes a fresh, adapted prompt that addresses the specific findings and reopens the card. The corpus holds 978 such reissue prompts across 437 tasks (avg 2.24, up to 16). Together with 78% findings-added outcomes, this says the bulk of re-runs are the intended quality loop. The clearly-technical cause is smaller and separable: 560 failed-post-processing events, almost all test-gate timeouts. The reducible waste is therefore narrower than "66% of compute" - it is redundant re-testing of unchanged trees plus those timeouts, not the quality iteration itself.

§6Time is not money Hard Interpretation

Time and cost barely correlate here, and conflating them misdirects optimization. Tokens - the expensive resource - are a hard count, and they concentrate almost entirely in one step:

Step groupTokens (in+out)ShareClass
core-agent-run (coding)1.89 B98.1%Hard
review aspects (×4)~36 M~1.9%Hard
test gate, git, lint00%Hard (true zero)

Put a price on it and the asymmetry is stark. At a roughly blended token price the corpus is on the order of ~$8,400 in tokens; the 82 CPU-hours of test time are about $4 on a throwaway cloud vCPU and effectively $0 on owned hardware. Test CPU is therefore around 0.05% of the token spend - a ratio near 2000×.

Interpretation  The dollar figures depend on a pricing assumption (blended: in $3/M, cache-read $0.30/M, cache-create $3.75/M, out $15/M) and are an order of magnitude, not a bill. What is robust is the direction and the size of the gap, not the exact numbers.

The consequence is concrete: saving test-gate or wait time buys throughput but almost no budget. Saving money means touching the coding step - fewer and shorter coding re-runs, which loops back to §5.

§7One measurement anomaly Interpretation

post-abort-review reports 2,258 minutes over just 57 runs - about 40 minutes per run - at zero recorded tokens. For an LLM assessment step (the "intelligent abort review", ADR-0054) that combination is implausible: either the duration includes waiting on a downstream rerun, or the step's durationMs attribution is wrong. This is exactly the kind of signal the coverage rules warn about, and it should be resolved before the abort-review duration is trusted for any steering. Flagged as a follow-up probe, not a conclusion.

§8What this does and does not support

Supported (hard evidence): the per-step time hierarchy, the concentration of tokens in the coding step, the 3.65× gate-run multiplier, the retry/first-attempt split (as a floor), and the cause taxonomy from reissue-prompt and outcome counts.

Interpretation, use with the stated assumption: the money comparison, the 2000× ratio, and the wall-time "waiting" share.

Not supported: any ranking of coding-model quality, and any absolute rate for all Agent Studio tasks - this sample is conditioned on having pipeline data and is not a controlled cohort. For a rigorous model-comparison design, see the frozen-scenario plan in token-economy-task-data.

Where this leads

The one optimization that pays off in money is reducing coding re-runs, which means making the quality loop converge faster - for example, evaluating whether sharper reissue prompts reach an accepted result in fewer attempts. The one that pays off in throughput is taking redundant re-testing off the serialized gate, which is the subject of the sibling proposal Async Validation & the Test Staging Lane.
