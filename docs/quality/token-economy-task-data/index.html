Evidence Metrics Fields Reliability

Guiding question · 24 July 2026

Can we learn anything reliable?

Yes, but the reliable result is narrower than a model leaderboard. Task Server data can establish what the system recorded. It cannot rank coding-model quality while card difficulty and reviewer bias remain uncontrolled.

Decision

Use production data for operational truth and measurement coverage. Use a controlled Token Economy benchmark for model comparison.

Reliable nowGate events, failures, violations, timestamps, recorded durations, counters, attempts, and SHAs.
Not establishedAbsolute quality, or which coding model is better, cheaper, or faster.

Three evidence classes

The same raw field can support a hard factual statement and still become confounded when grouped into a coding-model comparison.

1 · Hard evidence

Recorded system facts

Deterministic events and direct counters remain factual without a baseline, provided coverage and context are stated.

  • Gate verdict, build failure, violation event
  • Timestamp, duration, attempt, token count
  • Commit, result SHA, integration ancestry
2 · Model-judged

Reviewer opinions

Grades and aspects are generated by a reviewer LLM. Ground truth and reviewer bias are unknown.

  • Relative only under the same review setup
  • Keep rubric, prompt, evidence, and reviewer fixed
  • Never call a grade absolute quality
3 · Confounded

Uncontrolled comparisons

Production cards vary in difficulty, prompt quality, environment, retry history, and pipeline configuration.

  • No grade-by-coding-model ranking
  • No cycles-to-A ranking
  • No speed or token-efficiency ranking

What would make the comparison reliable?

Spend first on the smallest controlled pair. More production rows cannot repair uncontrolled task difficulty.

Priority 1 · cheapest direct comparison

One frozen scenario, two models, three repeats

Define a medium deterministic scenario in Token Economy and run the same artifact under both coding models. The primary endpoint is the deterministic gate. This is the minimum experiment that can compare coding-model performance.

Same inputBase SHA, prompt, attachments, permissions
Same runtimeCLI version, host limits, timeout, network policy
Same scoringGate commands and expected assertions
Variance visibleRandomized order and at least three repeats
2

Inter-rater replay

Grade the same frozen deliveries with two reviewer models. Report raw agreement, a confusion matrix, and weighted Cohen's kappa. Do not mix reviewer disagreement into coding-model performance.

3

Temporal stability

Repeat the same scenario and measurement contract over time. Track coverage, median, dispersion, and drift by exact model and CLI version.

4

Broaden the benchmark set

Add scenario families and difficulty strata only after the first pair is reproducible. Keep scenario-level results visible before aggregation.

5

Public benchmark anchor

Use external results only when exact model version, tool setup, task family, scoring rule, and date are compatible. Otherwise show them as context, not normalization.

Reproduction and audit trail

The extraction is API-only, bounded, and free of task titles or filesystem paths in the committed snapshot.

Run the extractor

Defaults to the stable local Task Server, Agent Studio project, 60 cards, and eight concurrent read workers.

Selection disclosure

  • Non-archived only
  • Grade-tagged only
  • Most recently active first
  • Latest pipeline attempt for step coverage
  • All returned review versions counted

Interpretation rules

  • Missing is unknown, not zero
  • Always publish numerator and denominator
  • Keep coding model and reviewer model separate
  • Keep scenario-level rows before aggregation
  • Version rubric, prompt, gate, model, CLI, and base SHA
