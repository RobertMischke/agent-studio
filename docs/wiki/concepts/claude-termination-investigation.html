claude.exe mid-run termination — live investigation log

Goal: find why an orchestrator-spawned claude coding run terminates with exit=-1 after 2–5 min, and a working configuration so tasks complete. Updated as experiments run. Companion to runner-stability-incidents + process-termination-scenarios.

RESOLVED (2026-06-23) — ROOT CAUSE #1: the live sentinel scanner false-fired on file content. EXP-1a..1d (bash / python / .NET Process.Start, full env, worktree) ALL survived — ruling out CLI / version / env / spawn / worktree. So the orchestrator itself was the killer. Instrumenting the kill paths with a stack trace caught it on the next run: KillProcessTree ← Stop ← ProjectRunner.TryStopOnSentinel ← OnRunEventReceived ← ReadStreamAsync. TryStopOnSentinel matched [[TASK_DONE]] on EVERY raw output line — including the file content the agent READS (tool results ride the user stream). The backend's own runner code, AGENTS.md, and docs/contracts/agent-task.md are full of sentinel literals, so any run that read such a file was killed mid-work as a false "completion" (status=completed, no commit). Both claude AND codex were hit; standalone runs survived because nothing watches their output — which is exactly why it masqueraded as an "orchestrator env / CLI crash" problem for so long.

Why it looked like a regression: the code path is old, but the recent tasks worked on the runner/orchestrator code itself (the drive-to-conclusion epic, the tab/analysis tasks) — so they read the sentinel-literal files and tripped it. Earlier tasks on unrelated code did not.

Fix (deployed, tested): the live decision now lives in the pure, tested LiveSentinelScanner.HasStandaloneAgentSentinel — it drops non-agent streams (file content) and requires a STANDALONE sentinel line, not a sentinel embedded in prose or quoted code. 9 regression cases. Verified: a task that reads sentinel-containing code now runs to real work instead of false-stopping at ~14 s.

BUG #2 (still open): with #1 fixed a run got further (127 s) then died exit=-1, StopReason=None (no orchestrator kill), actively streaming, right after a Bash tool command — a claude-code Windows Bash-subprocess/stdio crash (GH #34457 / #46985) triggered by the non-shell-parent + piped stdio. EXP-1d survived using built-in Read/Grep (no Bash). Candidate fix: spawn claude via ConPTY/PTY so it has a real TTY (the handle-scrub spawner is broken — it launch-fails exit=1).
Reproducible lab: c:\Projects\agent-taskboard-devspace\crash-repro-lab\ (git repo). material/ = 137 copied .cs files (work material). scenario-prompt.txt = a work-heavy read/grep/analyze prompt. Run a standalone experiment: claude -p "$(cat scenario-prompt.txt)" --output-format stream-json --verbose --dangerously-skip-permissions --model <m> > out.ndjson 2> err.log (this is the orchestrator's exact flag set). Vary ONE thing per experiment.

What the orchestrator actually does (verified)

  • Invocation: claude -p <prompt> [-r <uuid>] --model <m> --output-format stream-json --verbose --dangerously-skip-permissions [--append-system-prompt-file <rules>].
  • Spawn: ClaudeCli:UseHandleScrub is OFF → the normal Process.Start path (NOT the handle-scrub spawner). Stdin/stdout/stderr are redirected pipes; the backend reads stdout via ReadStreamAsync (StreamReader.ReadLineAsync), transforms + persists each line.
  • The backend creates no Windows Job Object.

Eliminated (with evidence)

  • Orchestrator Stop() / watchdog — both set info.StopReason; crash had StopReason==None (status=failed) & no watchdog log.
  • Orphan reaper — "Reaped stale-orphan" appears 0× in the entire log; it never fired.
  • Handle-scrub spawner — flag OFF, 0 handle-scrub spawns logged.
  • Job Object — backend creates none.
  • node heap OOM — stderr captured unconditionally, was empty (OOM prints FATAL ERROR to stderr).
  • Native crash / Defender — no Windows Error Reporting event; no Defender detections.
  • Model / context-mode / system memory — Opus + Sonnet both die; clean + shared both die; freeing RAM didn't change it.

Leading hypotheses (ranked)

  1. Active stdout-pipe interaction. EXP-1a redirects stdout to a file (never blocks); the orchestrator reads the pipe. claude-code is documented to not flush stdout when piped non-TTY (GH #25670, #17248) and to have Windows stdio/subprocess deadlocks (#34457). A reader stall or flush gap could lead to a hang then an external kill. Test: EXP-1b.
  2. An orchestrator kill path with no StopReason + no log. Narrow (reaper ruled out), but possible. Test: instrument every kill entry point with a source log + a flag, run one task, read the trace.
  3. Web research (GH issues): exit=-1 + empty stderr + no WER = an external TerminateProcess, not a node self-crash; claude-code has no idle self-termination. So a parent terminates it. Most likely after a perceived hang from the stdout buffering issue.

Next decisive step

Let EXP-1a finish (does standalone EVER die?). If it completes clean → the orchestrator's pipe-read is implicated → run EXP-1b (pipe) + instrument the orchestrator kill paths. If EXP-1a eventually dies → it is claude-code itself → pursue claude-code workarounds (version, output mode, NODE flags) + codex fallback.
