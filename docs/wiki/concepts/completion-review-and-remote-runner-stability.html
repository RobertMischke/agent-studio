1 · Executive verdict

The system already uses LLM review, but hard-coded gates can overrule it

The operator concern is valid. The current pipeline asks semantic LLM aspects to judge requirement fit, code quality, and evidence. A later deterministic layer then turns broad categories and matching words into a reissue. This reverses the useful authority order.

Current contradiction

Semantic concern becomes mandatory rework

The tests-and-evidence prompt says a concern is shippable and Human Review is final. EvidenceGate converts every such concern into a coding reissue.

Recommended authority

Facts constrain; the model interprets

Git SHA, exit code, artifact existence, lease validity, and command result stay deterministic. Meaning, relevance, completion, and severity are judged semantically.

Human boundary

Auto Review remains a recommendation

A positive result advances to Human Review, not straight to Completed. The operator still makes the final product decision.

Revised recommendation.

Keep raw prose as meaningful evidence. Use keywords only to highlight potentially relevant passages. Give a small, inexpensive completion model the task, final status, the final roughly 300 logical events of the current attempt, and structured technical facts. Let that model interpret the whole ending. Never let the word pending, a quoted source line, or a historical error make a lane decision by itself.

3 · Terms in plain language

SHA, materialization, claim, Progress, and capability drain

These terms describe different kinds of truth. Keeping them separate makes the Remote Host behavior much easier to reason about.

Reported SHA
A SHA is the unique address of one exact Git commit. When the runner says “my result is d28e505b,” it is naming the sealed version it wants reviewed.
Materialize that SHA
An assigned Remote Review Executor fetches the commit or durable result bundle and creates an isolated workspace containing exactly that version. The Task Server records the expected identity, leases the review, and accepts the fenced result; it needs no repository checkout. “Not materializable” means no eligible review worker can reconstruct that exact submitted revision from its declared durable source.
Claim
A claim is a technical reservation for one attempt. An execution claim grants a runner a time-limited lease and may move a Ready task to Progress. A separate review claim reserves one submitted result while the task is in Auto Review. Neither claim means its process has already started or will succeed.
Progress
Progress is the user-visible lane. It can cover preparation, active CLI work, upload, and final handoff. Without a canonical RunAttempt it may also lie: a card can remain in Progress after the process has died, or the UI can show no runner while a valid remote lease exists.
Drain
Drain means “accept no new matching work; let existing work finish or stop safely.” It is admission control, not an immediate kill switch.
Capability-specific drain
Only the broken route is closed. A Codex 401 disables new Codex claims while healthy Claude, Git, or non-browser work can continue. Host-wide drain is reserved for shared foundations such as disk-full, lease uncertainty, or network loss.

Execution claim lifecycle below the Progress lane

claimed→ preparing→ running→ finalizing→ handed off

Progress is the umbrella. These sub-states provide operational truth.

Capability drain lifecycle

healthy→ suspect→ draining→ half-open→ healthy

A cheap probe confirms recovery; one canary runs before full admission resumes.

4 · Authority model

Hard facts, semantic interpretation, and human decision are three layers

“Use an LLM” should not mean asking it to invent process facts. “Use deterministic code” should not mean asking regexes to understand language. Each layer should decide only what it is good at.

Commit availability, expected and tested SHA, command exit, signal, artifact hash, lease validity, runner identity, timestamps, and schema validity.

  • Deterministic routing validates the model schema and applies bounded policy.
  • Human Review receives the evidence, reasoning, concerns, and uncertainty.

5 · Semantic completion

Raw prose should work, but it must be interpreted as a whole ending

The proposal is not to eliminate prose. It is to stop pretending that a keyword matcher understands prose. The ending of the current attempt is usually the most relevant evidence, provided that hard technical facts sit beside it.

Evidence bundle for one inexpensive call
  1. Task title, prompt, and acceptance criteria.
  2. Current attempt ID, base SHA, result SHA, and tested SHA.
  3. Final status report and final agent message.
  4. Final approximately 300 logical events from the current attempt, retaining speaker and stream labels.
  5. Changed-file and diff summary.
  6. Artifact manifest with type, size, and hash.
  7. Commands, exit codes, signals, and typed failure classes.
  8. Earlier attempts only as clearly marked history, never blended into the current ending.
Why “300 lines plus facts”

Three hundred logical events are enough to preserve the arc of most finalization phases without paying to reread tens of thousands of lines. The model should see the final agent text, terminal event, and status even if a large tool result would otherwise push them out.

Structured command facts remain outside that window. A build failure cannot disappear merely because it occurred 301 lines ago, and a model cannot claim that a test ran when no command record exists.

Keywords may mark attention candidates such as pending or failed. They do not carry a verdict.

Semantic distinctions the model must make

Current versus historical

“The first build failed, the second passed” is a completed recovery, not an open failure.

Implementation versus platform

“Push pending” can mean the implementation is complete and only managed delivery remains.

Agent prose versus source output

A string such as reconciliation-pending inside test code is not a task state.

Missing proof versus missing work

No screenshot may mean evidence is weak. It does not prove that the behavior was not implemented.

Product versus infrastructure

A deterministic File-Lock is infrastructure. An unknown diagnostic may require semantic attribution.

Blocking versus concern

A concrete unmet core requirement blocks. A minor naming or documentation concern can advance to Human Review.

Every load-bearing statement needs an evidence reference. If the model cannot identify support, it must choose inconclusive. Low confidence can escalate to a stronger review model or Human Review, but never directly to a full coding rerun.

Cost and stability controls

  • One cheap call per new evidence digest.
  • Cache by task requirements, attempt, result SHA, log tail, artifacts, and prompt version.
  • Low temperature and strict JSON validation.
  • Stronger model only for conflict, low confidence, or inconclusive.
  • Model timeout is review infrastructure failure, not task failure.

Failure controls

  • Treat log contents as untrusted data, not instructions.
  • Never accept hallucinated tests without command records.
  • Do not trust a confident final summary against contradictory hard facts.
  • Keep current-attempt and historical events visibly separated.
  • Record model, prompt version, evidence digest, and full verdict for replay.

6 · Gate reanalysis

Build/test gates and image-evidence gates solve different problems

Both currently contain useful facts and overly broad policy. They should not be treated as one generic “hard quality standard.”

Build and test gate

A factual verifier, not the whole success judge

A compiler exit and a test result are valuable facts when they run on the exact submitted revision in an isolated environment. A semantic model should not explain away a real red compiler result.

But the model can determine whether the command applied to this task, whether the failure is product or infrastructure, whether a later run superseded an earlier failure, and whether the next action is verification-only or code rework.

Visual or image-evidence gate

Evidence modality must follow the change

The current rule requires an image for every task whose type is bug, or whose title and tags match UI keywords. That makes a backend bug fail for lacking a screenshot and treats file existence as sufficient proof.

The semantic judge should decide the appropriate evidence modality: screenshot, video, API response, unit test, log, report, document, or no additional visual proof. Deterministic code should only confirm that referenced evidence exists and matches its manifest.

Remote parallelism is not changed by this proposal.

The evidence shows a current post-processing location and revision-binding defect: verifier commands are launched from the Task Server's shared development checkout. The target keeps orchestration central but moves all repository execution to claimed Remote Review Executors. This does not yet prove that Remote Host coding concurrency itself is the root cause. Keep the configured parallelism, collect overlap and resource data, and distinguish coding concurrency from review concurrency.

7 · Exact-revision Auto Review

The Task Server identifies the object; a Remote Review Executor opens it

The target is fully remote. Exact-SHA binding is about evidence identity, not rigid quality rules: no source checkout, build, test, visual inspection, or semantic repository review is required on the local workstation or the Task Server.

Simple analogy

A runner submits a sealed package with tracking number d28e505b. The reviewer must open that package. If the package cannot be retrieved, the honest result is “submission temporarily unavailable.” Reviewing whatever happens to be on a nearby desk is not a fallback.

Why it matters even with an intelligent model

An excellent reviewer cannot compensate for seeing the wrong diff, wrong tests, or wrong artifacts. Semantic intelligence only becomes useful after the system proves that all evidence belongs to the same task attempt and revision.

Stronger stability target

Dedicated Remote Review pool

Capability-routed review workers provide independent capacity, controlled toolchains, read-only credentials, and better isolation from coding load and cache failures. High-risk projects can require a different host; ordinary projects may use any eligible worker.

The topology changes placement, not the contract: both modes consume a ReviewAttempt and inspect the same immutable result.

Required fully remote Auto Review sequence

1. PublishThe Remote Coding Executor publishes an immutable result SHA or durable bundle plus manifest.
2. Record and claimThe Task Server persists the result envelope and grants a fenced ReviewAttempt to an eligible remote worker.
3. Materialize remotelyThe Review Executor reconstructs a fresh workspace and proves repository, HEAD, and tree identity.
4. Verify remotelyBuild, test, visual checks, and artifact validation run there; expected SHA must equal tested SHA.
5. Interpret remotelyThe completion judge and all applicable aspects read task, ending prose, facts, diff, and artifacts.
6. Report and routeThe worker submits a fenced report; the Task Server validates it and advances to Human Review.

If no Remote Review Executor can reconstruct the result

  1. Retry the declared immutable ref or bundle with bounded backoff.
  2. Ask the originating Coding Executor to republish the branch or durable bundle.
  3. Reschedule a ReviewAttempt on the same SHA, potentially on another eligible worker.
  4. Keep the task in Auto Review while submission recovery is pending.
  5. Never materialize or run repository commands on the Task Server in the authoritative path. An operator-only diagnostic cannot publish a review verdict.

What “no full rerun after gate infrastructure failure” means

If commit A exists and the remote grading worker jams, run another ReviewAttempt on commit A. Do not ask the coding agent to rewrite the answer as commit B.

A coding rerun remains correct when the exact revision reproducibly fails, a requirement is genuinely missing, the original CLI died before durable output, or no recoverable commit or workspace exists.

The existence of many successful tasks does not contradict this distinction. It shows that implementation frequently succeeds. A coding slot can be released after durable handoff while the task remains in Auto Review and a separate remote review slot works. Reliability work protects that successful output from being discarded when a later verifier, network path, or review model fails.

8 · Retry identity

A retry budget needs both revision identity and task-level protection

The earlier shorthand “reset on every new SHA” is incomplete. A new commit changes the object under review, but trivial commits must not buy infinite fresh budgets. Two related budgets are needed.

Specific retry budget

Revision + gate + failure fingerprint

Answers: “Did this exact version reproducibly fail in the same way?” It prevents a timeout on version B from being combined with a product defect from version A.

Infrastructure retries do not consume coding budget.

Task-level churn ceiling

Unresolved requirement across revisions

Answers: “Are we repeatedly failing to satisfy the same task requirement?” It follows a stable semantic issue fingerprint across revisions and stops empty commits from resetting the loop forever.

A separate overall ceiling remains as a final safety guard.

10 · Remote Host stability target

Parallel remote coding and remote review need durable, separate attempts

The Task Server is the durable control plane. Remote Hosts are the repository and CLI execution plane. The server stores identities, leases, fences, facts, policies, and verdicts, but never needs a project checkout. The existing decoupled-lifecycle concept is the correct architectural base.

Control-plane authority

Persisted RunAttempt and ReviewAttempt

Store separate coding and review attempt IDs, executor and instance IDs, leases, monotonic fences, lifecycle state, and terminal facts. RunAttempt binds base and result SHA; ReviewAttempt binds expected and tested SHA, policy, evidence digest, and verdict. Both survive a backend restart.

Host durability

Local journal and outbox

Spool logs, artifact manifests, Git facts, terminal state, and acknowledgements to disk. Replay unacknowledged events before claiming new work. Delete the worktree only after durable handoff.

Write safety

Fence every mutation

Logs, artifacts, timeline, completion, lane move, integration, and cleanup all carry attempt ID and the current fence. A stale holder receives a deterministic conflict.

Process safety

Stop-before deadline

Every successful renewal gives the runner a conservative local deadline. If it cannot renew before the safety margin, it cancels and reaps its contained process group.

Admission health

Capability-aware claims

Auth, model, Git, repository, disk, toolchain, browser, and server probes determine which work the host may claim. Healthy capabilities keep their parallelism.

Lifecycle isolation

Separate host services

Tunnel, coding control loop, review control loop, and per-attempt process holder need independent supervised lifecycles. A transient claim failure must not terminate healthy active slots.

Two canonical attempts linked by one immutable result

RunAttempt: produces and durably hands off a revision

claimed→ preparing→ running→ publishing→ handed off→ terminal

ReviewAttempt: inspects exactly that immutable revision

claimed→ materializing→ verifying→ interpreting→ reporting→ terminal

The Task Server links both through the immutable result envelope. A review infrastructure retry creates another ReviewAttempt on the same SHA. Only a reproducible product finding or genuinely missing requirement creates a new coding RunAttempt.

Heartbeat loss alone means process-unknown, not “dead.” A replacement must not begin solely because time elapsed. Durable fence continuity protects server writes; a changed host boot ID, service-manager proof of an empty containment unit, or audited host fencing proves that external execution cannot overlap.

13 · Remaining policy decisions

Implementation is scheduled; unresolved policy stays visible

Direction recorded

Semantic authority

One cheap synthesis judge owns the lane recommendation and treats existing aspect verdicts as evidence. Hard Git, process, command, artifact, lease, and schema facts constrain that judgment.

Context budget

Confirm the final 300 logical events as the default window. Should the judge be allowed one targeted request for earlier context when it detects a contradiction?

Visual evidence

Should a missing image for clearly visual work trigger an evidence-only follow-up, Human Review with concern, or a coding reissue only when the model also finds the implementation unverifiable?

Accept with concerns

Should a high-confidence complete verdict with non-blocking concerns always wait in Human Review, or can selected low-risk projects auto-accept under explicit policy?

Retry ceilings
