1. How this page works (the discipline)

The cheap, durable loop (not an expensive safety net, just discipline):

  1. Document the problem here (the basis). What broke, the symptom, the root cause.
  2. Derive the invariant — the rule that must always hold so this class of failure cannot recur.
  3. Write a test that goes red if the invariant is violated (see the 112 outcome-contract tests as the model).
  4. The gate enforces it — the pre-deploy post-build-test-gate blocks a deploy if any invariant test is red.

Once an incident has a test behind the gate, that regression is locked in: it cannot silently come back.

3. Open invariants that still need a test + a fix

  • Self-healing worktrees. Test: given an orphaned dir at the target path, a pickup still succeeds (prune + recreate). Fix in backend/Features/Runner/WorktreeTaskLifecycle.cs prepare path.
  • Child-process teardown. Test: after a run ends/fails, no node/esbuild process has a CWD under the run's worktree. Fix: kill the process tree (the Windows handle-scrub spawner already exists for the CLI; extend to build children).
  • CLI availability is loud + pinned. Test: with the CLI missing, the runner emits a high-severity, operator-visible error (modal) and does NOT silently flip to manual. Fix: configured absolute claude-bin + the admin CLI-onboarding surface.
  • Evidence-gate sanity. Test: a grade-A task with screenshots on disk is not reissued for "missing evidence".

Each of these, once it has a red-on-violation test behind post-build-test-gate, is locked in. That is how "es wird nicht wieder schlechter" becomes structural rather than hopeful.
