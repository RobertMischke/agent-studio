Auto-Review Reissue and the Evidence Gate

Status: analysis recorded 2026-06-22. Why every task in the human-review lane showed "Needs rework", which were justified, and how the auto-review evidence gate should change. Companion to the runner domain map and the drive-to-conclusion concept.

Contents

1. Executive summary

On 2026-06-22 all nine tasks in 5-human-review for the Agent Task Processor project displayed the red "Needs rework" badge. An audit of each task against its acceptance criteria and on-disk evidence found that only two were genuinely justified (ASS-1724, ASS-1740). Five were false positives and two were partial. The badge comes from an auto-review reissue verdict that is decoupled from the code-review grade, so grade-A work is routinely flagged. The dominant root cause is an evidence gate that judges off a truncated CLI log instead of the artifacts actually on disk.

2. How "Needs rework" is produced

  • The auto-review step (lane 4-auto-review) records a decision of kind Reissue in the decisions journal (backend/Features/Runner/ReviewDecisionRecord.cs).
  • That becomes TaskInfo.OrchestratorVerdict = "reissue" at read time (backend/Features/Tasks/TaskEndpointHelpers.cs).
  • The frontend maps orchestratorVerdict === 'reissue' to the operator-visible label "Needs rework" in buildHumanReviewBadge() (frontend/src/app/features/board/components/task-card/task-card-view-model.ts:988).
  • The code-review grade (A-D) is decoupled: "a grade is reporting evidence, never a lane gate". A grade-A task is exactly as likely to be reissued as a grade-D one.
  • Reissue is driven by three gates, with a budget of MaxAutoReissueAttempts = 2: completion (open checklist / self-reported build/test fail), evidence (a tests-and-evidence aspect concern), and solution-quality.

4. Root cause

The evidence gate over-blocks. It maps any tests-and-evidence aspect concern to a reissue while:

  • ignoring the code-review grade (a grade-A "test-backed" verdict does not soften the gate), and
  • ignoring the artifacts actually present on disk (results/*.png, test reports, changed spec files), because the aspect reviewer is fed a truncated CLI output log as its evidence basis rather than a list of the produced artifacts.

So the gate demands evidence that already exists (1731, 1733, 1752) or that is out of scope (1741 screenshots on a backend refactor). A separate fault: the completion gate read a stale "Blocked" snapshot for 1750 instead of the final status.

5. Target and plan

Operator requirements: accept-with-concerns is fine; the reasons must be clearly derivable (the operator must see exactly why); visual-evidence requirements must be configurable per project because every project differs (a backend-only project should not demand screenshots, but this is a setting, not a hardcode).
  1. Judge on a results manifest, not a truncated log. Feed the tests-and-evidence aspect a manifest of artifacts on disk (results/ files, test-report paths, changed spec files) so it reasons over facts. Skip the visual/evidence block when the demanded evidence is present.
  2. Accept-with-concerns instead of reissue on passing grades. On grade A/B with only soft concerns, route to 5-human-review as an explicit accept-with-concerns (visible, non-blocking) rather than a reissue that re-runs and risks overwriting committed work.
  3. Per-project visual-evidence configuration. Add a project setting that governs whether visual evidence (screenshots / e2e capture) is required, and scope it off backend-only or non-UI tasks by default. Configurable, not hardcoded.
  4. Traceable reasons. Every reissue / accept-with-concerns must carry a clearly derivable reason and the evidence it was based on, surfaced on the card and in the task detail, so the operator can follow the chain.
  5. Completion gate reads the final status, not a stale in-run snapshot.

Related: this is the review-side counterpart of the drive-to-conclusion concept (over-eager reissue vs. carrying a task home). Never bulk re-pickup the human-review lane; that re-runs from scratch and wipes the committed work.

6. Open questions

  • Should accept-with-concerns auto-complete on grade A, or always wait for a human in 5-human-review?
  • What is the default per-project visual-evidence policy for a new project (off, on, or inferred from task type)?
  • Should the evidence manifest be produced by a post-step at run end (so the aspect reviewer always has it), and where does it live?
