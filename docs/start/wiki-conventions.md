# Wiki conventions

Durable conventions for this wiki, consolidated here from the former
`README-aus-wiki.md` during the 2026-07 structure migration.

This wiki is the runner/orchestrator knowledge base for the agent-taskboard
project and a first-class citizen in the repository, not an afterthought. Consult
it first for runner/orchestrator behavior and known issues.

## Where knowledge lives

| Area | Purpose |
|---|---|
| [`operations/common-problems/`](../operations/common-problems/) | Known recurring problems with root-cause analysis, occurrence logs, and workarounds. **Search here first** when a familiar symptom appears. Recurring-problem folders also appear under other themes (`{theme}/common-problems/`). |
| [`operations/learnings/`](../operations/learnings/) | Per-task run learnings auto-distilled by the opt-in `post-wiki-learnings` pipeline step. One page per task; `README.md` is the generated index. Do not edit by hand. |
| [`concepts/`](../concepts/) | Hand-maintained living concept/knowledge pages: why a design exists, what the parts are, how to work with it, plus a running knowledge log. |
| [`app/`](../app/) | Code contract (schemas, in-app help, wiki config). Not knowledge; path and format change only with code. |

Add new top-level areas only when they exist as real directories with real pages.

## Problem-folder conventions

Each recurring problem lives in its own folder under
`{theme}/common-problems/<slug>/` with these files:

| File | Content |
|---|---|
| `README.md` | Executive summary with YAML frontmatter (required). What, when first seen, current status. |
| `occurrences.md` | Timeline of every observed occurrence (UTC, task ID, agent, affected path). |
| `protocol.md` | Root-cause analysis, reproducers, log excerpts. |
| `measures.md` | Fix attempts with status (tried / applied / works / failed). |
| `ideas.md` | Hypotheses, open questions, discarded approaches. |
| `related.md` | Cross-references to other problems, tasks, ADRs. |

The `common-problems/README.md` index is generated by the `post-wiki-maintenance`
pipeline step. Do not edit it by hand.

### Frontmatter (required on every problem `README.md`)

```yaml
---
id: <slug>
title: "<one-line description>"
status: open | mitigated | fixed | archived
first-seen: <ISO-8601 UTC>
last-seen: <ISO-8601 UTC>
severity: blocker | major | minor | nuisance
category: permission | filesystem | cli | runner | ui | state-machine | misc
tags: [<keyword>, ...]
affects:
  - "<path or feature>"
related-tasks: []
related-adrs: []
---
```

### Status values

- **open** - actively occurring, no reliable workaround.
- **mitigated** - workaround exists, root cause not fixed.
- **fixed** - root cause resolved. Keep for reference, then archive.
- **archived** - historical reference only.

### Lifecycle

1. Symptom appears. Search `common-problems/` for a match.
2. Match found: add an occurrence entry to `occurrences.md`, apply known measures.
3. No match: create a new problem folder.
4. When fixed: set `status: fixed`, update `last-seen`, note the fix commit in `measures.md`.
5. After a long quiet period: `git mv` the folder into an `archive/` sibling.

### Cross-linking

Use `[[slug]]` to reference other problem entries. These are plain-text markers
for grepping, not rendered links.

## Page classification

Every hand-authored knowledge page should carry a classification (type + status).
New pages are stamped with a minimal classification companion at creation
(`type` = folder default, `status = aktuell`, `analyzedAt` = creation date);
unclassified hand pages surface as a gentle warning on the Wiki Pulse dashboard.
See [wiki-document-classification.md](wiki-document-classification.md).
