# GitHub Copilot CLI (`copilot`)

GitHub's Copilot CLI. Distributed as the npm package `@github/copilot-cli`. The **legacy** integration in our codebase: [`CopilotCliService`](../../../backend/Services/CopilotCliService.cs) predates `CliExecutionServiceBase` and reimplements lifecycle, persistence, reattach, and reaping.

> **Source:** [`backend/Services/CopilotCliService.cs`](../../../backend/Services/CopilotCliService.cs) (does **not** extend `CliExecutionServiceBase`).
> **Tests:** Coverage lives in higher-level integration tests; unit-level driver tests are sparse — known gap.
> **Contract:** [docs/cli/supported-clis.md §3.3](../supported-clis.md).

## Commit / push boundary

| Question | Answer |
|---|---|
| Does this CLI commit on its own? | **No.** The platform owns the commit boundary. |
| Does this CLI push on its own? | **No.** Push is the runner's job (today: a tracked gap). |
| What if it does? | Regression. Raise an issue and cite [docs/operations/git/commit-push-doctrine.md](../../operations/git/commit-push-doctrine.md). |

Copilot CLI is the most likely of the four to lean on git semantically (it is GitHub's product after all). That is fine for inspection - `git status`, `git diff`, `git log`. What it must never do: `git commit`, `git push`, `git amend`, `git checkout`, `git reset --hard`, or any branch-mutating command. The runner records the commit on the `3-progress -> 4-review` transition; see [docs/operations/git/commit-push-doctrine.md](../../operations/git/commit-push-doctrine.md) and [ADR-0019](../../architecture/decisions/adr-archive.md#adr-0019---platform-owns-the-commit-boundary-2026-05-04).

## Identity card

| | Value |
|---|---|
| Binary | `copilot` |
| Config key | `CliPath` (legacy name; not `CopilotCli:Path`) |

| Output mode used | Plain text (no JSON) |
| Session ids | **Slug** — `taskboard-<jobId>-YYYYMMDDHHmm` (we generate it; Copilot just stores it) |
| Resume flag | `--resume="<slug>"` |
| Fresh-name flag | `--name="<slug>"` |
| Session storage | `~/.copilot/history/<name>.jsonl` (when present) |
| Quota probe | Footer scrape — `Remaining reqs.: ±NN.N%` plus configured plan |

## Why the legacy code path stays

The other three drivers share `CliExecutionServiceBase` (spawn, stream, persist, reap). Copilot reimplements all of it because it landed first and the base class came later. **Refactoring it onto the base class is explicitly out of scope** — pure churn with no behavioural win, and it would risk regressing the persistence/reattach path that is genuinely subtle.

When fixing bugs in Copilot, copy patterns *from* the base class (e.g. UTF-8 forcing, stdin EOF, synthetic Started/Exited lines) without merging the codebases.

## Invocation reference

### Fresh run (build a new session under our slug)

```sh
copilot -p "<prompt>" --allow-all --name="taskboard-<jobId>-<yyyyMMddHHmm>" [--model="<id>"]
```

`--allow-all` auto-approves tool calls (analogous to Claude's `--dangerously-skip-permissions`). The slug is generated by `RunPlanner.BuildSessionName(jobId)`.

### Resume

```sh
copilot -p "<prompt>" --allow-all --resume="<slug>" [--model="<id>"]
```

Copilot tolerates **any non-empty value** via `--resume`. We reject UUIDs (those are Claude/Codex/Gemini ids; passing one would make Copilot start a fresh session and the resume would be lost).

### Anti-patterns

- **Don't** invent a new session naming scheme. The `taskboard-<jobId>-<timestamp>` shape is recognised by the cross-CLI guard (`RunPlanner.IsPlaceholderSessionSlug`) so it can be dropped silently when a job switches CLI from Copilot to a UUID-CLI. A different shape will look like a real foreign session and trigger recovery.
- **Don't** pass a UUID via `--resume`. `IsCompatibleSessionName` rejects UUIDs precisely to prevent this.

## Output handling

Copilot emits **plain text** — no `--json` mode for headless. `TransformReadLine` is unnecessary; the CLI's own output is already in a parser-friendly shape (the activity-log marker convention emerged from Copilot's text in the first place).

The footer line is scraped for usage telemetry by `TryParseUsage`:

```text
Tokens ↑ 38.6k • ↓ 514 • 34.7k (cached)  Changes +47 -4   1 Premium (12s)
```

Three regexes pick out tokens, changes, premium-request count. Update them together if the footer format shifts; the regex is fragile by design (precise enough to ignore agent-emitted text that happens to contain the words "Tokens" or "Changes").

## Authentication

Copilot needs a GitHub token. `HasGitHubToken()` checks two sources:

1. Explicit override (`SetGitHubToken` / `GitHubToken` config key).
2. `gh auth token` via the OS-installed `gh` CLI. Tries `gh` on PATH, then `%LOCALAPPDATA%\gh-cli\bin\gh.exe`, then `%PROGRAMFILES%\GitHub CLI\gh.exe`.

The token is injected into the child process environment as `GITHUB_TOKEN`. We do **not** drive the login flow — if the gh CLI is logged out, `HasGitHubToken` returns false and the side-sheet shows the auth state to the user.

## Model handling — live discovery

[`CopilotModelDiscovery`](../../../backend/Services/CopilotModelDiscovery.cs) drives the interactive `/model` picker over a PTY, scrapes the panel, and returns a `CliModelCatalog`. There is **no hardcoded fallback** by design: stale or guessed model lists are strictly worse than a clear error.

`GetModelCatalog` (sync) and `GetModelCatalogAsync` are both available; the sync wrapper exists for backwards compatibility with older endpoints. New code should prefer the async variant.

When a CLI version bump changes the picker layout, discovery throws — surface the failure verbatim to the side-sheet, do not silently fall back.

## Persistence and reattach

Copilot has its own persistence file (`active-jobs-copilot.json`) and its own reattach path. Unlike the base-class CLIs, Copilot writes a `PersistedExecution` record per spawn. On startup, it tries to *re-attach* to surviving processes (not reap them). This was the correct trade-off when Copilot was the only CLI — orphan reattach is a net positive when there's no Activity Log redundancy on disk yet.

Now that the runtime JSONL log gives us redundancy, the base-class reaper is the better default and the other three drivers use it. Copilot still reattaches because tearing that out would break user expectations on hot-reload during dev. Don't change this without a migration plan.

## Quirks (and what to do about them)

1. **Plan must be set in config.** `Quota:CopilotPlan` (e.g. "Pro"). Copilot doesn't echo plan tier in output, so absolute counts depend on knowing the plan.
2. **Premium-request counter resets on the 1st of the month, 00:00 UTC.** The probe handles this; tests lock the boundary case.
3. **Windows-shell fallback rules in CLI's system prompt.** `WindowsShellFallbackInstructions` is a hardcoded German list of "don't use pwsh.exe-specific syntax" rules. It used to bleed into the agent's behaviour when prompts contained PowerShell instructions. Keep it; if you want to remove, capture a regression case showing the new behaviour is fine first.
4. **CLI path config key is `CliPath` (no prefix).** The other three are `<Cli>Cli:Path`. This is legacy and we live with it.
5. **stdin is not auto-closed.** The base class closes stdin to skip Claude's 3 s warning; Copilot does not, because it doesn't have that warning. Don't add an auto-close — Copilot may genuinely want stdin in some flows we haven't tested.

## Quota probe

[`CopilotQuotaProbe`](../../../backend/Services/Quota/CopilotQuotaProbe.cs) scrapes the footer (`Remaining reqs.: ±NN.N%`) and combines with the configured plan to derive absolute counts. The reset cadence is monthly (UTC 1st 00:00) for premium, and the probe computes `ResetAt` accordingly.

## Common tasks

### "Copilot session not resuming after backend restart"

1. Confirm `job.json` has the `taskboard-...` slug. If empty, the previous run never persisted it (look for a crash before `MonitorProcessAsync` ran).
2. Confirm `IsCompatibleSessionName` accepts the slug. UUIDs are rejected — that's correct, Copilot never produces UUIDs.
3. Confirm the spawn argument is `--resume="<slug>"` (with `=` and quoted) — see `CreateCliStartInfo`.
4. Confirm `~/.copilot/history/<slug>.jsonl` exists. If not, Copilot's history was rotated; the resume will start fresh.

### "Footer scraping silently failing after a CLI update"

1. Capture a real footer line from `cli-output.log`.
2. Update `TokensRegex` / `ChangesRegex` / `RequestsRegex` to match the new format.
3. Add a fixture row in the regex tests if they exist.

### "Model discovery returned an error"

1. Run `copilot` interactively and trigger `/model` by hand.
2. Compare the new panel layout to the parser in `CopilotModelDiscovery`.
3. Update the parser; do not add a hardcoded fallback list.

### "Auth check is failing on a freshly-installed Windows machine"

1. Confirm `gh auth status` works.
2. If yes, confirm the path probe finds the right `gh.exe` (the three candidates under § Authentication).
3. If `gh` is installed via a non-standard path, set `GITHUB_TOKEN` explicitly via env or the `GitHubToken` config key.
