1. Konzept & Zweck

Der Agent Message Bus ist ein append-only JSONL-Event-Store, der alle relevanten Ereignisse aus dem System an einem zentralen Ort sammelt: Entscheidungen des Orchestrators, Advisory-Meldungen des Supervisors, Interventionen, Lifecycle-Events von Jobs sowie Token-Verbrauch pro Turn.

Der Bus ist kein primärer Schreibpfad. Kanonische Writer (z.B. cli-output.log, observations.jsonl) schreiben zuerst — der Bus-Emit folgt best-effort nach. Wenn der Bus-Write scheitert, verliert das System keine Daten, nur Sichtbarkeit.

Metapher: Stell dir den Bus wie ein Audit-Log vor. Alle Subsysteme berichten dorthin, was sie tun. Die Frontend-UI liest nur aus dem Bus — sie fragt nie direkt beim Orchestrator oder Supervisor nach.

Wofür ist der Bus gedacht?

Observability

Live-Überblick was gerade passiert: welcher Agent arbeitet, wie viele Tokens verbraucht, welche Entscheidung wurde getroffen.

Debugging

Nachvollziehen warum ein Job fehlgeschlagen ist — Timeline aus Entscheidungen, Interventionen und Fehlermeldungen.

Cost Tracking

Token-Verbrauch je Job, je Modell, je Tag aggregierbar — ohne in Raw-Logs zu suchen.

Unified Timeline (geplant)

Bus + ProjectChat + OrchestratorChat in einer einzigen chronologischen Ansicht.

Performance Tracking (geplant)

Latenz pro Modell-Turn, Context-Window-Auslastung — Kapazitätsplanung und Bottleneck-Analyse.

5. Grenzen & Lücken offen

LückeAuswirkung
Kein SignalR-Push UI muss pollen — kein Live-Update ohne Polling-Interval. busMessageAdded im Spec, nicht in JobHub.cs verdrahtet.
Kein Token-Aggregation-Endpoint Man kann nicht schnell "gesamt je Modell heute" abfragen. Die Rohdaten sind da; es fehlt nur ein Rollup.
Kein Context-Window-Tracking Unklar wie groß der Kontext war, was drin war, wie nah man am Limit ist.
Kein Latenz-Tracking Kein TTFB, keine Gesamtdauer je Turn — kein Anhaltspunkt für Rate-Limiting oder Kapazitätsplanung.
Kein Unified Timeline Model Bus, ProjectChat und OrchestratorChat sind drei separate Systeme mit drei verschiedenen Shapes. Korrelation ist manuell.
Kein SSE/Stream-Endpoint Kein /api/bus/{project}/stream — nur Polling möglich.
Kein Workspace-weiter Index Suche über alle Projekte ("alle Nachrichten mit 'timeout'") nicht möglich. Nur per-Projekt.
Participant-Graph nicht berechnet Schema unterstützt replyToId / correlationId für einen Graphen, aber kein Service baut ihn auf.

6. Neue Anforderungen

6a. Token-Usage-Aggregation

Ziel: Schnell den Token-Verbrauch nach Participant, Modell oder Tag aufaddieren — ohne alle JSONL-Files selbst zu parsen.

Alle Daten sind bereits als kind:token-usage-Nachrichten im Bus. Es fehlt nur ein Rollup-Pass über die In-Memory-Projection.

Vorgeschlagener Endpunkt:

GET /api/bus/{project}/token-aggregate?groupBy=model|participant|day&since=...&until=...

Response:
{
  "byModel": [
    { "model": "claude-sonnet-4-6", "input": 1240000, "output": 85000, "cacheRead": 6720000, "cacheWrite": 120000 },
    ...
  ],
  "byParticipant": [
    { "participantId": "orchestrator", "input": 800000, ... },
    ...
  ],
  "byDay": [
    { "date": "2026-05-11", "input": 1240000, ... },
    ...
  ]
}
Schema-Änderung: Keine — die Daten sind bereits vorhanden.

6b. Context-Window-Tracking

Ziel: Wissen, wie groß der Kontext war, was drin stand, wie nah man am Limit ist — per Turn.

Claude gibt beim API-Call zurück wie viele Tokens verbraucht wurden. Durch die Differenz aus cache_read_input_tokens und input_tokens lässt sich ableiten wie viel vom Kontext gecacht war. Claude gibt außerdem optional den Context-Usage-Prozentsatz in der CLI-Ausgabe aus.

Vorgeschlagenes neues Feld auf AgentMessageTokens:

"contextWindow": {
  "totalSize":            200000,    // Modell-Limit in Tokens
  "used":                 87432,     // tatsächlich verbraucht (input + cacheRead)
  "remaining":            112568,    // totalSize - used
  "systemPromptTokens":   12000,     // geschätzt aus Cache-Write beim ersten Turn
  "conversationTokens":   71000,     // Konversations-History
  "filesLoadedCount":     14,        // aus CLI-Output parsbar (ToolUse: Read)
  "largestFiles": ["path/to/file.ts (4200 tok)", "..."]
}
Schema-Änderung: Neues optionales contextWindow-Objekt in agent-message-tokens.schema.json. Das Feld ist optional — rückwärtskompatibel.

6c. Latenz-Tracking

Ziel: Wissen wie schnell ein Modell antwortet — Time-to-First-Byte (TTFB) und Gesamtdauer je Turn. Besonders wichtig bei Aufgaben, wo Reaktionszeit kritisch ist.

Der Runner (CLI-Output-Parser) kennt den Zeitpunkt des CLI-Inputs und kann den ersten Token auf stdout tracken.

Vorgeschlagenes neues Feld auf dem AgentMessage-Envelope:

"latency": {
  "requestedAt":   "2026-05-11T13:30:00.000Z",    // CLI-Input gesendet
  "firstTokenAt":  "2026-05-11T13:30:02.300Z",    // erster stdout-Byte
  "completedAt":   "2026-05-11T13:30:15.700Z",    // CLI-Exit
  "ttfbMs":        2300,                           // firstToken - requested
  "totalMs":       15700                           // completed - requested
}
Schema-Änderung: Neues optionales latency-Objekt in agent-message.schema.json. Rückwärtskompatibel — bestehende Nachrichten haben das Feld nicht.

Anwendungsfälle:

  • Rate-Limiting erkennen: TTFB plötzlich > 10s deutet auf Throttling hin
  • Modell-Vergleich: Sonnet vs. Haiku — wie unterscheidet sich TTFB bei gleicher Task-Art?
  • Kapazitätsplanung: Durchschnittliche Turn-Dauer bestimmt wie viele parallele Jobs möglich sind
  • Debugging: Warum hat ein Job 45min gebraucht? — Timeline aus Latenz-Daten

7. Roadmap (Priorität)

  • 1

    Token-Aggregation-Endpoint

    Quick Win — Daten sind da. Nur ein Rollup-Pass über In-Memory-Projection. Kein Schema-Change. Neuer GET-Endpoint in BusEndpoints.cs.

  • 2

    SignalR busMessageAdded

    Verdrahte JobHub.cs mit AgentMessageBusStore.AppendAsync. Push nach jedem Write. Dann entfällt Polling im Frontend.

  • 3

    Latenz-Feld

    Günstiger Schema-Extension. Runner trackt requestedAt / firstTokenAt / completedAt. Hoher diagnostischer Wert.

  • 4

    Context-Window-Feld

    Hängt von CLI-Output-Parsing ab. Claude gibt Context-Prozentsatz aus — muss zuverlässig geparst werden. Schema-Extension auf AgentMessageTokens.

  • 5

    Unified Timeline Model (TypeScript)

    Adapter-Schicht über Bus + ProjectChat + OrchestratorChat → gemeinsames TimelineEntry. Ermöglicht eine einheitliche UI-Ansicht.
