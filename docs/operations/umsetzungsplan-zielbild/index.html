2Leitplanken — deine Entscheidungen

Ausführungsmodell & Isolation

  • Container-Default für die lokale Ausführung; bei Neuinstallation Container ab Installer vorausgewählt. Host-direkt/Misch bleibt Opt-out.
  • Isolation gilt dem Coding-Agent — nicht den Sourcen: alle von Projekten verwendeten Sourcen dürfen gesehen werden, Nachbarrepos zu sehen ist gut und richtig.
  • Worktree-Modell bleibt. Jedes Projekt hat einen Git-Checkout, darin die Worktrees je Karte.

Autonomie: Self-Push & Tokens

  • Agenten pushen selbst — wichtig und praktisch: autonom laufen, keine Daten verlieren. Sie brauchen Git-Tokens + CLI-Tokens.
  • CLI-Tokens brauchen evtl. regelmäßige Auffrischung — das geht vermutlich nur über die lokale Umgebung.
  • Perspektivisch kein SSH-Tunnel mehr dafür — jedenfalls nicht über Task-Server etc.; alles per API-Zugriff. → das Konzept muss hier erweitert werden (§5).

Images (E3)

Gepflegte Basis-Images pro Komponente (Task-Server, agent-host, Studio …), damit ein docker-compose up alles Benötigte startet.

Phase 1 — Container-Default koordinierter Batch

Der execution-model-shift, jetzt mit deinen Leitplanken. Zusammenhängend, weil Spawn-Pfad + Image + Installer + Isolation ineinandergreifen.

  • Container-Spawn-Pfad als Default für die lokale Ausführung (CLI im Container, Isolation vom Container statt CLI-Sandbox).
  • Basis-Images pro Komponente (E3) + docker-compose up startet Task-Server + agent-host + Studio zusammen. Verzahnt AGT-2334 (Installer) und AGT-2305 (docker compose up).
  • Installer = Container-Default: Neuinstallation wählt Container sofort vor (AGT-2334).
  • Repo-/Worktree-Sicht im Container: pro Projekt ein Checkout + Worktrees; Nachbarrepos sichtbar (bewusst). Der „the hard part" aus der Distributable-Analyse: Repo-/Credential-Erreichbarkeit im Container → gelöst über den lokalen Mount + die Tokens (§2, §3).
  • Self-Push scharf: Agenten pushen selbst mit Git-Token; CLI-Token vom lokalen Environment injiziert.

Verifikation im selben Container + Container-Def als agent-gepflegtes Repo-Artefakt (E6)

Wenn der Gate (Build+Test) im Container läuft, bekommt jedes Projekt sein Build-Tooling — deklariert in einem Dockerfile im Projekt-Repo (Source of Truth, versioniert wie csproj/package.json). Das gebaute Image ist ein Sidecar-Artefakt (Registry/Cache, keyed by Dockerfile-Hash) — Definition im Repo, Image daneben, Rebuild nur bei Änderung. FROM Basis-Image (E3) + projekt-spezifisches Toolchain.

  • Wer pflegt: ein Agent (neue Rolle „Umgebungs-Pflege") schreibt/aktualisiert das Dockerfile (Toolchain verstehen = LLM-Arbeit); docker build selbst ist deterministisch (Pipeline-Step).
  • Workflow: Onboarding → Agent erzeugt initiales Dockerfile → committet → Image gebaut+gecacht → Coding und Gate spawnen ins selbe Image → bei Toolchain-Änderung (z. B. Build schlägt fehl) aktualisiert ein Agent das Dockerfile → Rebuild.
  • Konsequenz: hermetische, reproduzierbare Verifikation (Coding = Gate-Umgebung); der Container-Def wird ein First-Class-Projekt-Artefakt neben Wiki/Dossiers.

Phase 2 — Verteilte Plattform Epics als koordinierte Changes

  • AGT-2129 (Control-Plane): Task-Server als Control-Plane + Remote-Execution — der Distributed-Platform-Epic. Reihenfolge: 2230 (Task-Server = zentrale Config: Projekte/Identitäten/Kapazität) → 2277 (Control-Plane auf Hetzner) → 2278 (Hosted-Wiki-Publish).
  • CAR-Migration (2370→2371→2372→2373): Runner + Backend-Exec auf CodingAgentRunner, Parity-Suite, Doppelpfade weg. 2370 überlappt mit P0 (Runner-v1) — dort beginnen, hier abschließen.
  • AGT-2132 (Release & Deployment): gepaarte, versionierte Releases (Task-Server + agent-host + Studio), Protokoll-Version im Handshake. Nutzt die Tranche-0.4-Release-Pipeline.
  • AGT-2130 (Architektur-/Qualitäts-Ebene): Projekt-Graph, Style-Guides, Analyse — eigener Strang, nach der Plattform.

Spawn-Pfad-Konvergenz auf CAR — von deinen Entscheidungen verstärkt, nicht geändert

Heute gibt es drei Spawn-Pfade (Backend-Process.Start, Remote-Runner, CAR-CliRunEngine). Container-Spawn, Mount/Isolation, Token-Injektion und Image-Wahl müssten sonst dreimal gebaut werden — und würden driften (die Nacht-Lektion). Ein Pfad (CAR) legt all das an eine Stelle. Deine Entscheidungen sind damit die Spezifikation des konvergierten CAR-Pfads: CLI im bypass-Modus in einen Container spawnen (Isolation = Container-Grenze), Projekt-Checkout + Nachbarrepos mounten (breite Sicht bewusst), Git-+CLI-Tokens injizieren, Basis-Image der Komponente (E3) nutzen. → Die CAR-Kette 2370→2371→2372→2373 bekommt dadurch schärfere Abnahmekriterien, keine geänderte Richtung.

Phase 3 — SSH-Tunnel ablösen & Token-Refresh Konzept + Task

AGT-2262 (SSH-Gate durch saubere Remote-Gate-Lösung ersetzen) ist der Einstieg. Zielbild: keine Steuerung mehr über den SSH-Tunnel — alles per API zwischen Studio/Task-Server und agent-host. Der offene Knoten: die CLI-Token-Auffrischung braucht die lokale Umgebung — ohne Tunnel muss der Refresh anders zum (evtl. entfernten) agent-host kommen. Konzept dazu in §5.

5Offene Konzept-Punkte

Token-Refresh ohne Tunnel (der Knoten)

Git-Token: unproblematisch (langlebig, im Container-/Host-Secret). CLI-Token (Claude/Codex-Auth) braucht evtl. regelmäßige Auffrischung, und die läuft heute über die lokale Umgebung + Tunnel. Wenn der Tunnel wegfällt und alles API-basiert ist, muss der Refresh-Weg neu gedacht werden — Optionen zu skizzieren: (a) ein schlanker lokaler „Token-Broker" am Host, der frische CLI-Tokens per authentifizierter API an den agent-host reicht; (b) der agent-host refresht selbst über eine hinterlegte Auth; (c) Token-Injektion beim Container-Start + periodischer Re-Injection-Job. Zu entscheiden.
