Async Validation & the Test Staging Lane

A design proposal for a plausible-sounding intuition: tests are slow and run for every card, so move validation off the critical path. The evidence says the payoff is throughput, not cost - and that reshapes what is worth building. This workbench states the design, the trade-offs, and a concrete decision.

Decision in one paragraph

Do not build LLM-based test selection: it spends the expensive resource (tokens) to save the cheapest one (CPU). Do build a per-SHA gate cache that skips re-testing an unchanged tree - it removes most of the redundant validation with no new architecture and pays off regardless. Treat the staging lane and test-integration branch as measure-first: they only pay off if batches are usually green, and a red batch forces a bisection that can erase the gain. The whole exercise buys throughput on the shared runner, not money.

§1The idea in three building blocks

The proposal is usually stated as one thing, but it separates into three parts with very different cost/benefit profiles. Keeping them apart is what lets us accept one and reject another.

1a - Deterministic test scoping

Run only new tests and tests that touch the changed module, instead of the full suite per card. The catch is the word "smart": deciding relevance with a model spends tokens, the one resource worth saving. The whole building block survives only if the decision stays deterministic (§5).

1b - A staging lane

A lane that collects cards whose coding and review are finished but which are not yet integrated. They move on batched, once their combined changes pass the gate together, rather than each card forcing a synchronous full gate run of its own.

1c - A test-integration branch

A dedicated branch where the batched validation happens, decoupled from the coding worktree. The open question is what happens after green: fast-forward to develop, or integrate straight into develop and skip the branch entirely (§6).

§3The real lever: retry serialization

If cost is not the argument, throughput is. Two structural facts make the gate a throughput bottleneck on the shared runner:

  • The gate takes a machine-wide lock (BuildTestGateRunner.MachineGateLockPath). While one task tests, every other waits. This is the same serialization documented in verteilte Ausführung §5.
  • Most of that serialized time is redundant. A batched run that validates N finished cards once replaces N×(1+retries) individual runs of overlapping code.

So the mechanism to copy is the one Agent Studio already uses for integration pushes: IntegrationPushQueue/IntegrationPushWorker move the push off the request path. The proposal is the same move, applied to validation instead of push.

§4Design: staging lane and test branch

§5Deterministic scoping, not an LLM

Building block 1a is worth keeping only without tokens. It is feasible from static signals that already exist at gate time:

  • Changed files → affected test projects via a maintained folder/project mapping (a change under backend/Features/Pipeline/** selects backend.Tests filtered to Pipeline*). Pure git diff plus a lookup table, zero tokens.
  • New test files always run (A-status in the diff).
  • Full-suite fallback when the change set spans modules - often the case in a batch, which makes scoping less critical in batch mode than for a single card.

The pattern is not new: QS-28 ("skip-if-fresh") already skips unchanged review units deterministically via hashes. This is the same idea applied to tests.

§6Integrating toward develop

The open branch question, with a clear trade-off:

OptionUpsidePrice
A - straight to develop (no test branch)Simple; develop is always the source of truth.The gate stays per-card, so the 84% retry lever is not pulled. Effectively the status quo.
B - batch on integration/test, then FFOne suite run per batch pulls the throughput lever; red batches keep develop clean.Blame assignment on a red batch: which of N cards failed? Needs bisection or single-card fallback.

The number that decides option B

The bisection case can eat the gain: if a five-card batch goes red, in the worst case you need up to five further individual runs to find the culprit - slower than per-card testing would have been. B's net benefit hinges directly on the batch green rate. High green rate (cards already individually review-green) → B wins clearly; frequent red batches → it loses. This is the one quantity to estimate from existing data before committing to B.

§7Recommendation and slicing

Reject  LLM-based test selection. Anti-economical - expensive tokens to save cheap CPU. Keep only the deterministic diff→project mapping.

Build  Per-SHA gate cache. Bind the gate result to the tested tree SHA; an identical SHA skips the run. Removes most of the redundant re-testing with no architectural change - the largest lever for the smallest effort.

Measure first  Staging lane + test-integration branch. Build only after estimating the batch green rate from existing data.

Proposed order

  1. Measure. From pipeline data, estimate the batch green rate and the same-SHA re-test rate. Decides whether option B gets built.
  2. Per-SHA gate cache. Skip re-testing an unchanged tree.
  3. Deterministic scoping. diff→test-project mapping as a gate filter, zero tokens.
  4. Staging lane + integration/test. Only on a green light from step 1.

§8Open questions

  • Batch green rate - how often are N individually review-green cards test-green together? Blocker for option B.
  • Same-SHA re-test rate - how often is exactly the same tree re-validated on a reissue? The ceiling on the cache's benefit; expected high given ~3.65 gate runs per task.
  • Scope-mapping upkeep - who keeps the folder→test-project map current? A stale map yields falsely-green gates; consider hanging it on the PipelineSteps config.
  • Lock granularity - does the machine-wide lock stay, or become per-integration/test? Finer means more real parallelism but more resource pressure.

Closing decision decision-ready

This workbench recommends spawning two feature cards now - the per-SHA gate cache and the deterministic test scoping - and one research card to estimate the batch green rate, which gates whether the staging lane and test-integration branch are built at all. LLM-based test selection is recorded as explicitly rejected. No card is created until an operator confirms through the normal task mutation path.
