Operating model · Agent fencing

Worker agents do the work. The platform owns Git history.

This is the simplest safe writing model for agents with different maturity levels. A worker may edit files in its assigned worktree. It never decides when those edits become repository history.

Status: current operating rule Updated: 24 July 2026 Visual: separate agent-fencing diagram

§1 · What

One writer for Git history

Worker agents never commit or push.

They edit files and produce evidence. After review, the platform creates the commit, records the exact SHA, and pushes it. This keeps the lifecycle decision and the Git record under one authority.

Worker agent

May inspect Git and change assigned files. May not create, amend, switch, merge, tag, stash, commit, or push history.

Platform

Reviews the result, decides the lifecycle transition, creates the commit, stamps its SHA on the task, and pushes through the managed path.

If a worker tries to write history, the command guard blocks known mutating Git verbs. The runner also compares the repository HEAD before and after the run. A detected change becomes agent-git-violation: the result is quarantined for human review, evidence is preserved, and the run is not silently accepted or integrated.

§2 · Why

Trust is graded, not binary

Models do not have one shared maturity level. They differ by model, CLI, task shape, prompt, and runtime environment. A model can be strong at implementation and still be unreliable at process boundaries. “Trusted” must therefore mean “supported by observed evidence for this use,” not “allowed to do everything.”

Fencing gives every model the same hard Git boundary. Trust then changes how closely work is supervised, not who may author history.

§3 · Strategy

Evidence-driven oversight

  1. Record trust per model.Token Economy card TE-13 defines a per-model capability and trust record backed by runs, violations, and source evidence.
  2. Sample normal work.A high-trust, high-capability orchestrator reviews some routine runs so silent drift still has a chance to be found.
  3. Review on signals.Increase scrutiny when a guard fires, HEAD changes unexpectedly, the diff does not match the task, evidence conflicts, or recovery repeats.
  4. Classify and escalate.The orchestrator explains whether the signal is benign, a process violation, or uncertain. Uncertain or violating work stays quarantined and goes to an accountable human.

Trust may change sampling frequency. It never grants a worker permission to commit or push.

§4 · Evidence

Incidents are learning opportunities

These are real July 2026 cases, not hypothetical warnings. The task keys render as live task references in the Wiki.

AIP-7

agent-git-violation · gpt-5.6-sol
What happened
The worker advanced HEAD by one commit before the platform-owned commit step. Review then found that the committed diff belonged to the unrelated sidecar-metadata pattern, not the requested process-actor pattern.
What caught it
The runner’s before/after HEAD check raised agent-git-violation. Exact-diff code review then exposed the attribution mismatch and prevented clean acceptance.
What we learned
Topical research is not proof that the recorded commit belongs to the task. Writer identity and exact diff provenance must both be checked.

AIP-10

agent-git-violation · gpt-5.6-terra
What happened
The worker advanced HEAD by one commit before the platform-owned commit step. Its reviewed diff contained the unrelated sidecar-metadata pattern rather than the requested prompt-management entry.
What caught it
The same before/after HEAD check raised agent-git-violation. Exact-diff review classified the change set as incoherent and kept it out of the normal acceptance path.
What we learned
A prompt rule is useful but insufficient. A command guard, HEAD-delta detection, exact-diff review, and fail-closed recovery are all required.

Token Economy shared-checkout collision

TE-13 · remediation AGT-2300
What happened
For local-folder projects, a non-Git task-storage RootPath could disable worktree provisioning even when RepositoryPath named the real repository. Two admitted runs could then share one in-place checkout and observe each other’s HEAD and diff.
What caught it
Task identity, branch state, and the reviewed diff disagreed. That provenance mismatch exposed the collision instead of treating the visible HEAD as task evidence.
What we learned
Isolation must be resolved from the authoritative repository, not from task storage or slot count. Every coding run needs its own worktree, while commit and push remain platform-owned.

§5 · Open proof point

Violation probability per model

Not proven yet

The desired metric is violating eligible runs / all eligible runs for each exact model and CLI. The known incidents provide numerator evidence, but the historical denominator and detection coverage are not yet complete enough for a defensible rate.

TE-13 owns this proof point. Any published rate must include sample size, observation window, CLI, detection version, and confidence. Until then, the system should show “insufficient evidence,” not invent precision.
