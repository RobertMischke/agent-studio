TL;DR — die fünf Kernaussagen

  • Evidenz ist heute Konvention, kein Vertrag. Es gibt keine einzige, unveränderliche Antwort auf „Welchen Code hat dieser Run produziert?“ — Reviews raten (Run-SHAs, sonst Branch-Fallback). Ziel: ein Attempt-Record mit Result-SHA, den Grade-Step, Gate, Merge und UI ausschließlich konsumieren.
  • Der Remote-Runner schreibt in eine andere Branch-Welt (runner/<id>/<key>) als die, die reviewt wird (task/<slug>). Ohne automatische Integration entstehen Phantome — Grade D war jeweils korrekt.
  • Mehrdeutigkeit wird fail-closed, nie optimistisch: unbekanntes Ergebnis → Quarantäne mit konservierter Evidenz, niemals „vermutlich fertig“.
  • Verifikation wird hermetisch: Gates laufen auf der exakten Result-SHA in einem isolierten Worktree, Timing läuft auf virtueller Zeit — Testurteile hängen am Code, nicht am Maschinenzustand.
  • Der Grade-Step bleibt. Er ist die Nutzer-Wahrheitsanzeige („war der Code da?“). Die Härtung ändert nur, welchen Diff er garantiert bekommt.

Und wenn ein Agent trotzdem schreibt?

Die ehrliche Antwort zuerst: Agenten lassen sich nicht vollständig fencen. Ein CLI-Agent läuft mit echten Prozessrechten in einem echten Checkout — er kann in den Haupt-Checkout wechseln, Branches anlegen, die API rufen oder pushen. Härtung heißt hier nicht „unmöglich machen“, sondern Blast-Radius klein, Abweichung sichtbar, Wirkung neutralisierbar — auf vier Ebenen:

§6Grade-Step

Festlegung

Der Code-Review-Grade ist die Nutzer-Wahrheitsanzeige: „War der Code da, und taugt er?“ Er wird nicht abgeschafft und nicht abgeschwächt. Die Grade-D-Urteile der Phantom-Phase waren fachlich richtig — sie haben das Integrationsloch überhaupt erst sichtbar gemacht.

Was sich ändert, ist ausschließlich seine Eingabe:

  • Heute: Rate-Kaskade (Abb. 3) — Run-SHAs, sonst Branch-Fallback. Im Normalfall richtig, im Sonderfall systematisch falsch, und das Urteil kann nicht zwischen „Code fehlt“ und „ich habe auf das falsche Universum geschaut“ unterscheiden.
  • Ziel: Der Grade-Step diffed resultSha gegen baseSha aus dem Attempt-Record — garantiert das, was der Versuch wirklich produziert hat. Ein D heißt dann beweisbar: die Arbeit fehlt wirklich.
  • Neues drittes Verdikt: Ist kein gültiger Attempt-Record da, sagt der Step das explizit („Scope unauflösbar — kein Attempt-Record“) statt zu raten. Auch das ist Nutzer-Information: es unterscheidet „schlechte Lieferung“ von „kaputte Evidenzkette“ — zwei völlig verschiedene Handlungsanweisungen.

Das Muster über allen Einträgen

Jeder Vorfall hatte dieselbe Tiefenstruktur: Mehrdeutigkeit wurde optimistisch aufgelöst (fehlendes Sentinel → „done“, unklarer Diff-Scope → raten, Prosa-Checkliste → Urteil) und Wahrheit lag an mehreren Orten gleichzeitig. Die gesamte Härtung ist die Umkehrung genau dieser zwei Eigenschaften: fail-closed bei Mehrdeutigkeit, ein Vertrag als einzige Quelle.
