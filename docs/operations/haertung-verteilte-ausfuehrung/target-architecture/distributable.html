The Distributables D1–D5 signed off 25.07.

What actually ships, what a “binary” is here, how it is installed, started, updated and rolled back. Elaborates the open decision from distributable.md (AGT-2277 parked until this is signed off). Actor model: Target Architecture.

1 · The three distributables (plus the libraries)

Everything that runs is delivered by exactly three packages. Each package is versioned, built by CI from a tag, and installable without a repo checkout. The npm libraries are the fourth deliverable but ship through the npm registry, not through an archive.

agent-orchestratorcontrol plane · one archive, two binaries
  • task-server (binary)
  • orchestrator-engine (binary)
  • two systemd units (.service)
  • config contract: server.env, engine.env
  • store migrations — idempotent, run on start
  • backup unit + timer (store + security state)
  • Caddy site template (edge, 80/443 only)
  • install.sh / update.sh / rollback.sh
runs on: the control-plane host (Hetzner VM — or any Linux box, incl. a local one)
agent-hostexecution · one binary per host
  • agent-host (binary)
  • Coding and Review systemd role units as installed
  • config: runner.env plus operator-owned /etc/agent-host/profile.conf
  • work dirs: runner-work/ per project, worktree per run
  • salvage snapshotting and Linux cgroup resource policy
runs on: every runner host (agent-runner-01, future hosts) — never on the control-plane host
agent-studioUI · static web bundle
  • dist/ (compiled Angular bundle)
  • no process of its own — served by the edge
  • pinned library versions (e.g. coding-agent-chat 0.3.x)
  • offline indicator against the Task API
served by: Caddy on the control-plane host (or any static host / CDN later)
task server engine runner studio libraries → npm registry (separate channel)
Why the control plane is ONE archive with TWO binaries: Task Server and Orchestrator Engine are separate processes with separate lifecycles (restart matrix), but they are versioned and deployed together — the Engine is the only API client that must always match the server’s API version exactly. Splitting the archive would create a compatibility matrix with no benefit; splitting the processes is what buys the restart safety.

2 · What “binary” means here

A self-contained .NET single-file executable for linux-x64: no .NET runtime installation on the host, no DLL folder, one file per process. Each binary answers --version (the stamped release version + git SHA) and reads exactly one env file. Today’s OrchestratorApi.exe is the unsplit ancestor of the two control-plane binaries — it currently contains task server, engine and studio serving in one process. The split is the extraction work, not a rewrite:

Target binaryToday lives inCarries overStays behind
task-server OrchestratorApi.exe (one process) store, Task API, leases/epochs, provenance, management & recovery endpoints, wiki/doc serving anything that calls an LLM or spawns a CLI
orchestrator-engine review/council pipelines, post-processing, gate dispatch, completion judge — as a pure API client direct store access (goes through the API instead)
agent-runner agent-runner (already its own daemon) unchanged — it is the model the others follow —

8 · Robert’s review (25.07.) — answers & open discussion

8.1 Naming: agent-runner collides, host level missing

Agreed. The name clashes with the Coding Agent Runner library (CAR, PROJ-011) and does not say “this is the per-host daemon”. Candidates: agent-host (recommended: it is the thing that represents a host — claims work, cuts worktrees, runs CLIs), orchestrator-host, runner-host. The binary exists today as runner/AgentRunner.csproj → published to /opt/agent-runner — so this is purely a naming decision, not new code.

8.2 Does agent-orchestrator require Docker/Linux? What about macOS?

No Docker requirement anywhere. All binaries are self-contained .NET executables published per target (linux-x64 first-class; osx-arm64 and win-x64 are ordinary additional publish targets). systemd units are the Linux integration, not a prerequisite — macOS would use launchd, Windows a service wrapper. Practical support matrix (proposal): control plane linux-x64 first-class; host daemon linux-x64 first-class, osx-arm64 supported (needs git + the agent CLIs installed), Windows dev-only. Docker appears only as the evaluation channel (§6) and possibly the local installer (§8.8).

8.3 Where do orchestration flows live? (alignment with the other target pictures)

Three layers, consistent with actors.md and orchestrator-plan.md:

LayerLives inExamples
Flow definitions (data)Task Server store — project settings, pipeline steps, task-type-aware pipelineswhich steps, which models, which gates per task type
Flow executionOrchestrator Engine — reads definitions via the API, drives council/review/post-processing/gate dispatchreview pipelines, completion decisions, reissue budgets
Episodic orchestration (LLM)Sentinel/Companion sessions per orchestrator-plan.md — pure API clients on topincident handling, day planning, operator dialogue

So: the Engine executes flows, it does not own their definitions — those are server data and therefore editable through the normal API (see §8.7).

Implemented 25.07.: orchestrator-engine ships the five bounded API polling loops above. The Task Server persists versioned flow definitions, definition-snapshotted runs, stage results, leases, and monotonic fences under /api/v1/orchestration/*. An Engine process restart leaves the run on the server; lease expiry makes it claimable with a higher fence. During the transition, Orchestration:ExecutionMode is exactly Monolith or Engine, and Engine mode does not register the legacy review/post-processing hosted loops.

8.4 Versioning

Every binary answers --version (release + git SHA). The control-plane archive versions as one unit (task-server + engine always ship together — they are the tightest compatibility pair). Host daemon and Studio version independently. Compatibility is enforced at runtime via the protocol handshake that already exists (POST /api/v1/protocol/compatibility): an incompatible host daemon is refused with a clear reason — never silent 409s (the 25.07. lesson).

8.5 Update story — agreed, needs build-out

The symlink/rollback shelf (§3) is the skeleton. Tranche 0 adds: drain-before-update (stop claims, let leases finish or kill-on-lease-loss per AGT-2320), health-gated restart (new version must pass /readyz within N seconds or auto-rollback), and rolling host updates (one host at a time once there are several). These become explicit acceptance criteria of the tranche-0 cards.

8.6 Fresh install & who owns Caddy

Fresh install: install.sh is the same script — creates user + directories, writes config from template (prompting for origin/credentials), installs units; the store initialises itself through the same migration path on first start (migrations are code inside the task-server binary, not a separate tool — see §8.9). Caddy is host infrastructure, not part of our package: our archive ships only the site config template; install.sh offers to install and enable the distro’s Caddy service. Alternative kept open: Kestrel terminates TLS itself and Caddy becomes optional — decision deferred to the deploy card of AGT-2277.

8.7 Configuration must stay agent-editable

Two config layers, cleanly split (this also matches “Konvention statt Settings”):

LayerWhereChanged by
Bootstrap — listen URL, store path, credentials, host identity/etc/agent-orchestrator/*.envhost operator only; rarely changes; never by agents
Operational — projects, pipelines, caps, models, flow definitionsTask Server store, via the public APIUI, operator and coding agents — exactly as today

So yes: everything agents steer today stays editable — it lives in the store, not in shipped files. The env files only hold what the process needs before it can reach the store.

8.9 Store migrations / backup are not separate things

Reworded to avoid the impression of extra components: migrations are code in the task-server binary (run idempotently at startup — nothing to operate). Backup is one systemd timer invoking the task-server’s own backup subcommand; the “verified restore path” is a test of that subcommand, not a product. The §1 package table lists them as archive contents, not as runnable units of their own.

8.8 D5: a single guided installer

Goal: local use with one command, no source checkout, no neighbour repos (AGT-2305’s “one-command onboarding” as a first-class target). The implementation keeps the two channels deliberately separate:

Implemented 28.07. (AGT-2334): agent-orchestrator-setup is one self-contained Linux x64 executable published beside the three release archives. Its guided paths are Demo, native Single Machine, Multi Machine Control Plane, and Agent Host join. Docker is checked and used only for the isolated demo. Native repository execution uses the host filesystem, Git, and the host-owned Codex or Claude login. The Control Plane prints a protected aosj1.* join token; each host consumes it without putting the secret in a command-line argument, starts its systemd service, and waits for exact Task Server registration. The token honestly follows the current separated Task Server bearer contract: encoded rather than encrypted, reusable until credential rotation, and never described as one-time.

8.10 D5: token requirements and guided onboarding

The guided installer line (AGT-2334) includes a Create token step before credential storage. Its implementation stays on the installer card. The step links to the Linux runner token requirements and presents these exact GitHub choices:

  • Fine-grained PAT, preferred: choose the organization that owns the repository as resource owner, limit access to assigned repositories, and grant Contents: Read and write plus Workflows: Read and write.
  • Classic PAT, compatibility fallback: grant repo plus workflow and complete organization SSO authorization when applicable.
  • A PAT belongs to its creating user, not to the organization. Prefer a dedicated machine account; organization policy may require owner approval.
  • With credential.https://github.com.useHttpPath=true, store and verify the credential for both https://github.com/OWNER/REPOSITORY and https://github.com/OWNER/REPOSITORY.git.

The wizard waits for the runner startup result and explains ready, ready-no-workflow-scope, and read-only. Only read-only blocks claims. The middle state links to the permission checklist but does not try to predict whether a card will touch .github/workflows. Rotation updates and verifies both URL entries before the old token is revoked.

9 · Runner-host resource governance

On Linux, agent-host owns the resource controls in every Coding and Review systemd unit it installs or updates. Slot counts are admission decisions, not capacity units: a single slot can fan out into many compiler and test processes. systemd/cgroup v2 is therefore the hard host boundary, while the central host-capacity controller adjusts admitted slots through AIMD.

RoleCPU quota derived from nprocCPU / I/O weightMemory
Codingall logical CPUs100 / 100uncapped by default
Reviewone third, minimum one CPU30 / 30uncapped by default

The only explicit override surface is /etc/agent-host/profile.conf. Existing manual resource drop-ins are adopted into missing profile values and then replaced by directives in the managed main unit. Windows enforcement through Job Objects is out of scope and requires a separate card. Full contract: runner-host resource governance.
