Recommendation

Approve the defense-in-depth variant as one launch package. Run the real Task Server in a startup-locked public-demo profile that rejects every execution admission path. Pair it with a replay-only Runner that has no claim scope, CLI, repository, deploy key, secret mount, or general outbound network access. Publish only a server-enforced read-only visitor surface from a dedicated demo VM. Build the instance from the existing pinned seed, extend that one seed with the Wiki and Dossier gallery, prove the generated datastore is scrubbed, and replace the whole runtime from a versioned release bundle on reset.

Launch invariant

A browser control, a manual Runner mode, or a replay flag is not an execution boundary. The Task Server must deny claims and starts even if a caller bypasses Angular, forges a Runner request, moves a card, or compromises the replay process. If the server cannot prove that lock at startup and through its route matrix, the public demo does not start.

Important distinction

The ADR-0056 dev guard is suitable for local development, not sufficient for a hostile network. RunnerMode: manual, AutoCommit: false, and Runner:Role = test-subject reduce accidental pickup. Recommended topology

Hard server lock coverage

The implementation should expose a startup-only deployment profile, backed by one pure execution-admission policy. That policy is evaluated at every boundary below and returns the same typed execution-disabled denial. It is not a mutable project setting and has no management or browser toggle.

  • Local pickup and any local direct-start path.
  • Current and legacy remote coding claims, lease acquisition, and replay of an existing claim.
  • Review claims, gate execution, post-processing, and host-orchestrator work.
  • Continue, steer, extend, reissue, retry, resume, and scheduled automation that could spawn a process.
  • Project Chat, task Chat, ad hoc agents, preview commands, repository operations, and any diagnostic endpoint that invokes a tool.
  • Future execution endpoints by a route or feature registration guard that fails the public-demo build when a new execution capability lacks a policy test.

The server may accept the narrow replay event scope only for known fixture task keys, the current replay epoch, monotonic sequence numbers, and a pinned trace digest. Replay events are always labeled simulated and cannot write task prompts, decisions, files, Git state, or lifecycle transitions outside the declared scene.

Scrub proof, not a scrub claim

The source note in the committed pinned-seed.json is useful provenance, but a public deployment needs machine-readable evidence over the rendered output. The gate should produce demo-seed-scrub-report.json beside the release bundle with:

  • seed schema, generator version, fixed time base, content digest, product compatibility range, and replay trace digest;
  • generated file counts by class and the exact temporary root scanned;
  • zero unreviewed matches for secret patterns, entropy, private keys, tokens, emails, URLs, IPs, absolute Windows or Unix paths, user-home fragments, hostnames, repository remotes, and source project names;
  • an allowlist for deliberately synthetic model names, task keys, and fixture commit hashes, with a deterministic derivation note for every hash;
  • OCR and metadata results for every image, plus confirmation that no source screenshot is shipped;
  • two independent generations with a clean recursive diff and identical manifest digest;
  • human review identity, time, reviewed digest, exceptions, and approval. A changed byte invalidates the approval.

Raw exports, intermediate redaction files, source screenshots, and scanner exception samples must never enter the repository, CI artifact, demo VM, or task result bundle. Real data may inspire the final prose, but the committed fixture is an allowlisted reconstruction.

§7Reset, seed versioning, and product updates

One versioned release unit

A demo release pins four compatible artifacts together: frontend and Task Server image, pinned seed, replay trace, and deployment policy. The manifest records each digest and the supported seed/product schema range. Rollback changes the whole unit, not one component.

demoRelease: 2026.08.1
productImage: <immutable digest>
seedSchemaVersion: 1
seedDigest: <sha256>
replayTraceVersion: 1
replayTraceDigest: <sha256>
deploymentProfile: public-demo-readonly
scrubReportDigest: <sha256>

Reset cycle

  1. Replay cycle: derive the visible replay offset from a fixed 12-minute trace. On reconnect, the server projects the current cycle position. The canonical seed is not rewritten for animation.
  2. Runtime replacement: recreate the ephemeral runtime volume from the approved seed on every deploy and restart, on operator request, and on a six-hour schedule. Six hours is a backstop for bugs and unexpected writes, not a substitute for read-only authorization.
  3. Atomic cut: generate into a new isolated volume, verify seed and scrub digests, start the candidate, probe browse and deny paths, then switch the proxy. Never delete and rewrite the datastore underneath a running Task Server.
  4. Failure behavior: keep the previous healthy bundle active if generation, migration, scrub verification, claim-denial probes, or smoke tests fail. Do not partially update content.
  5. Retention: rotate access and denial logs aggressively. Preserve aggregate security metrics, not visitor payloads or an indefinitely growing copy of public requests.

When the product moves

  • Every product release runs a compatibility job that generates the seed twice, starts the real Task Server in public-demo mode, opens both projects, checks every lane, Wiki, all six Dossiers, search, artifacts, and SignalR, then probes all execution paths for typed denial.
  • A schema migration updates the generator and seed manifest in one review. It does not import a live workspace or regenerate from an operator machine.
  • Content changes are explicit pull requests against the pinned source. They include a new digest, scrub report, both-theme captures for affected scenes, and a short semantic-change note.
  • AGT-2530 remains the owner of capture reproducibility and pinned provenance. The public instance consumes that integrated contract. It does not maintain a parallel screenshot-only fixture.
  • If current product code cannot read the approved seed, the previous demo release remains online until a fully compatible bundle passes. “Latest” is not more important than “safe and internally consistent.”

§10Scenario principle and candidate pool

The demo is a completed, deployed snapshot

A scenario is a versioned input package that has crossed the complete Agent Studio path. It begins with a Dossier, is decomposed into cards through the built-in Orchestrator and its context chats, receives bounded scripted steering, runs through coding and review, deploys a real application, and closes with a Result Dossier. The public demo receives a scrubbed, pinned projection only after those facts exist.

Truth rule

A scenario is publishable only when the deployed output, immutable release digest, deployment check, evidence inventory, and complete token ledger are present. A repository diff, a replay animation, or prose that says the app was built is not a result. If deployment is missing or unavailable at capture time, the Result Dossier status is incomplete and the scenario is not promoted into the public demo.

Candidate 1: SVG Pelican Benchmark

A compact visual benchmark inspired by the familiar pelican-on-a-bicycle SVG challenge. The opening Dossier asks for one asset-free, responsive web page whose central illustration is a hand-authored SVG pelican riding a bicycle. The scene must remain recognizable at desktop, mobile, and thumbnail sizes; expose its SVG source; include an accessible description; and use no raster fallback, generated image, external font, or remote asset.

The deployed result is a small comparison gallery: rendered scene, source view, three viewport captures, automated SVG checks, and a blind rubric card. It tests spatial reasoning, vector structure, frontend execution, visual polish, responsive behavior, and the ability to turn an unusual brief into a finished public artifact. Its small scope makes it the calibration case for the harness and cost controls.

Candidate 2: The Deep Blue

A short browser game about how a programmer feels when the task named “Programming” disappears from the board. The player starts at a familiar desk, watches the task dissolve into a blue interface, and dives through layers made from fragments of specifications, tests, commits, and conversations. Mechanics stay simple: move, dive, surface, collect four fragments, and choose what remains valuable when routine implementation is automated. The story is reflective, not a claim that the profession has ended.

The deployed result must be independently playable in six to ten minutes, work with keyboard and touch, retain progress locally, offer reduced-motion and mute controls, and reach a real ending. All art and sound are local and license-recorded; sound is optional. The benchmark tests narrative synthesis, game-state logic, interaction design, visual identity, performance, accessibility, tests, and deployment. This is the strongest standalone marketing artifact and the most expensive recommended case.

Candidate 3: Shift Ledger, a ToDo with an operational handoff

The LOB candidate turns an ordinary ToDo list into a shift-handoff ledger for a small service desk. A work item is not complete when a checkbox is clicked. It moves through Draft → Owned → Ready for handoff → Accepted, carries an owner and due-by time, requires a short outcome receipt, and can be rejected back to the prior shift with a reason. A compact audit timeline answers who promised what, what changed, and what evidence crossed the handoff.

The deployed application ships with synthetic morning and evening shifts, saved filters for “mine”, “at risk”, and “awaiting acceptance”, an overdue view, keyboard-friendly forms, and a deterministic data reset. The twist is legible to anyone who has handed work to a colleague, while state transitions, validation, persistence, audit history, filters, and role boundaries create a credible LOB benchmark rather than generic CRUD.

Additional candidate: Receipt Rescue

A familiar expense-inbox application that groups synthetic receipts into a trip, highlights duplicate or policy-suspicious items, asks for missing context, and produces a review packet. It tests document-like fixtures, exception workflows, confidence disclosure, and auditability without requiring private data or a live OCR service. Its main weakness is benchmark leakage: the task can become a conventional form-and-table build unless the fixture and exception logic remain demanding.

Additional candidate: Last Stop

A transit disruption explainer for one fictional route. The visitor selects a station and time; the application explains the changed route, replacement leg, accessibility constraint, and expected arrival with a clear timeline. It tests temporal state, map-like visualization, and plain-language explanation against a deterministic timetable. It is recognizable and useful, but its marketing identity is weaker than The Deep Blue and its domain rules need careful fixture design.

Additional candidate: The Tiny Museum

A curator workbench for assembling a five-object digital exhibition from a pinned catalog, writing a room label, and publishing a shareable mini-gallery. It combines selection, sequencing, responsive presentation, and editorial constraints. It is visually attractive and inexpensive, but subjective curation makes cross-model quality scoring less stable, so it belongs after the first benchmark wave.

§11Benchmark framework and Result Dossier

The question and the unit of comparison

The primary question is: “With how many tokens can I solve which problems?” The unit of comparison is one caseVersion × route × replicate run that begins from the same opening Dossier and baseline commit and ends in one of five terminal benchmark states: passed, failed, capped, infra-invalid, or incomplete. Only a passed run has a deployed, verified output. Capped, failed, and incomplete runs remain first-class evidence; infrastructure-invalid runs remain cost evidence but are excluded from quality ranking.

Two experiment modes must not be mixed

Whole-stack comparisonThe declared routing bundle across coding, review, orchestration, and documentation.Scenario, script, runtime, cap, evaluator, and deployment target.What does a realistic end-to-end project run cost and deliver?

The first controlled matrix compares the eligible core routes in the canonical Model Routing Policy: Luna/medium, Terra/medium, and Sol/medium. Sol/xhigh is not added merely to make a larger chart; it is included only for a case whose risk score or hard floor requires it, or as a separately approved research arm. Mini/high remains eligible for bounded supporting decisions and is never treated as a coding contender. Explicit benchmark routing is recorded as such, and quota or price never lowers a correctness floor.

Controlled run protocol

  1. Freeze: publish the case version, opening Dossier digest, script digest, evaluator digest, repository baseline, runtime image, deployment adapter, route bundle, and token caps before the first run.
  2. Randomize: randomize route order within each case to reduce time, host-load, and warm-cache bias. Run each route on the same host class with a clean worktree and isolated deployment namespace.
  3. Start in product: open the preserved Dossier in Orchestrator Chat and play the fixed operator script. Cards must be created through the Orchestrator and Task API.
  4. Execute: capture every model call, card transition, prompt hash, context receipt, attempt, steer, review finding, test result, commit, and deployment event under one correlation id.
  5. Enforce caps: apply category and total budgets at safe call boundaries. Permit at most one semantic reissue. Never erase a costly failed attempt and restart it under the same run id.
  6. Deploy: publish into an isolated immutable release slot. Record URL, digest, timestamp, and availability probe. A passing local build without this proof cannot pass the case.
  7. Evaluate blind: run deterministic checks first, then have reviewers score screenshots and behavior without model or token labels. Critical failures override the numeric score.
  8. Close the Dossier: generate the narrative portion, capture its documentation tokens, then use a deterministic renderer to inject the final ledger and content digests. This avoids an unmeasured self-referential final edit.
  9. Replicate: after a single-run calibration block passes harness checks, collect three replicates per route. Publish median, range, pass-at-cap, and every individual Result Dossier.

Complete historical archive

Every terminal run writes a content-addressed archive manifest. The logical layout is cases/<caseVersion>/runs/<runId>/ with the opening Dossier reference, script, context receipts, rendered prompt manifest or approved prompt bodies, task/card snapshots, token receipts, pipeline and session events, review evidence, test logs, screenshots, release manifest, availability probe, Result Dossier, and checksums. Secret-bearing provider internals are never archived; required redactions are declared in the manifest.

  • Runs are append-only. A retry is another attempt inside the same run; a clean replacement after infrastructure invalidation receives a new run id.
  • Failed, capped, incomplete, and infrastructure-invalid runs remain visible. A website filter may focus on passed runs, but the default cohort summary reports every terminal status.
  • Comparison is permitted only across the same case, case version, experiment mode, evaluator version, and budget. Any runtime or script drift is a new cohort.
  • Three replicates are the minimum for a comparative claim. One run is a demonstrator, not a model qualification result.

§12Cost model and hard caps

What the existing evidence says

The Async Validation evidence basis measured 2,396 attempts across 847 tasks. Retry compute was 66.7% of total compute, a conservative floor because attempt history is capped. The core coding step was 66.8% of compute and 98.1% of recorded input-plus-output tokens. Review aspects carried about 1.9% of those tokens, while deterministic tests carried none. This leads to two budget rules: cap and reserve the coding category explicitly, and do not spend model tokens to optimize deterministic test CPU.

The proposed budgets are experiment guardrails, not forecasts or targets. They deliberately reserve space for orchestration and for a measured Result Dossier that historical pipelines did not produce as part of each benchmark. Unused category budget cannot be transferred into Coding.

Budget behavior

  1. Measure all four dimensions. Input, output, cache-read, and cache-write tokens count toward category and total caps using the Studio aggregation convention. Cache is cheaper on many routes, but it still consumes context and remains part of the core question.
  2. Warn at 60%. At 60% of a category or total cap, the run records a budget-warning event and the next Orchestrator decision must choose among finish, one bounded reissue, or close as failed. The warning does not silently change the model.
  3. Protect one retry reserve. The first coding attempt should target no more than 65% of the Coding cap, leaving 35% for at most one semantic reissue. If the first attempt consumes that reserve, no semantic reissue is admitted. This is the direct control on the historical retry tax.
  4. Keep support ring-fenced. Review, Orchestration, and Documentation each stop at their own cap. A large Coding run cannot consume the tokens needed to evaluate and report itself, and an overactive reviewer cannot reopen Coding indefinitely.
  5. Stop at a safe boundary. At 100%, do not dispatch another model call. Finish deterministic receipt collection, mark the run capped, and publish whatever evidence exists. Do not kill a filesystem write or deployment transaction mid-operation.
  6. Count invalid spend. Infrastructure-invalid calls stay in the batch spend ledger even though they do not enter quality ranking. A replacement starts from a clean namespace with a new run id and needs new budget approval.

Batch ceiling and staged approval

One route across all three cases is capped at 880k tokens. A one-replicate comparison block across Luna/medium, Terra/medium, and Sol/medium is therefore capped at 2.64M tokens. The full three-replicate block is capped at 7.92M tokens and must not be scheduled until the one-replicate calibration shows complete attribution, stable evaluators, working deployment, and no systemic cap failure. Each additional route adds another 880k per replicate and requires an explicit operator decision.

Tokens are the stable admission currency. Before scheduling, TokenEconomy calculates the API-equivalent dollar ceiling for the exact route and timestamp, with separate input, output, cache-read, and cache-write assumptions. The operator sees both numbers and approves the lower of the token cap and any workspace spending ceiling. Subscription quota is shown separately and is never presented as an API invoice. A missing model price blocks a dollar comparison but does not erase token evidence.

Calibration and cap revision

Keep the proposed caps for benchmark version 1. After three valid replicates per route, compare median consumption and tail behavior. A future case version may lower a cap when at least 80% of valid runs pass below 75% of it, or raise it when more than one otherwise-promising route caps at the same declared acceptance step. Never change a cap inside a cohort, and never interpret “used the full budget” as evidence of quality.
