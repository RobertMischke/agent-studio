A browsable demo with no execution authority

A public Agent Studio scene with two credible mock projects, a real Task Server, live navigation and SignalR, a replay-only Runner, and Dossiers across their full lifecycle. The instance can show execution evidence, but it cannot claim, start, continue, or complete real work.

Recommendation

Approve the defense-in-depth variant as one launch package. Run the real Task Server in a startup-locked public-demo profile that rejects every execution admission path. Pair it with a replay-only Runner that has no claim scope, CLI, repository, deploy key, secret mount, or general outbound network access. Publish only a server-enforced read-only visitor surface from a dedicated demo VM. Build the instance from the existing pinned seed, extend that one seed with the Wiki and Dossier gallery, prove the generated datastore is scrubbed, and replace the whole runtime from a versioned release bundle on reset.

Launch invariant

A browser control, a manual Runner mode, or a replay flag is not an execution boundary. The Task Server must deny claims and starts even if a caller bypasses Angular, forges a Runner request, moves a card, or compromises the replay process. If the server cannot prove that lock at startup and through its route matrix, the public demo does not start.

Important distinction

The ADR-0056 dev guard is suitable for local development, not sufficient for a hostile network. RunnerMode: manual, AutoCommit: false, and Runner:Role = test-subject reduce accidental pickup. The public demo additionally needs a server execution lock, restricted visitor authorization, a scrub attestation, and infrastructure separation.

Recommended topology

Hard server lock coverage

The implementation should expose a startup-only deployment profile, backed by one pure execution-admission policy. That policy is evaluated at every boundary below and returns the same typed execution-disabled denial. It is not a mutable project setting and has no management or browser toggle.

  • Local pickup and any local direct-start path.
  • Current and legacy remote coding claims, lease acquisition, and replay of an existing claim.
  • Review claims, gate execution, post-processing, and host-orchestrator work.
  • Continue, steer, extend, reissue, retry, resume, and scheduled automation that could spawn a process.
  • Project Chat, task Chat, ad hoc agents, preview commands, repository operations, and any diagnostic endpoint that invokes a tool.
  • Future execution endpoints by a route or feature registration guard that fails the public-demo build when a new execution capability lacks a policy test.

The server may accept the narrow replay event scope only for known fixture task keys, the current replay epoch, monotonic sequence numbers, and a pinned trace digest. Replay events are always labeled simulated and cannot write task prompts, decisions, files, Git state, or lifecycle transitions outside the declared scene.

Apply the same project filter to REST, search, and SignalR. Anyone can obtain public read authority, so it does not prevent scraping. It only constrains reachable data and methods. Rate limits and content minimization carry the abuse defense.
Instance and data separation Dedicated demo VM, demo-only data volume, separate service identities, no shared TaskRepository, no mount from the website or production Task Server, no private WireGuard peer, and no route to productive Runner hosts. Cloud-account, hypervisor, DNS, or operator credential compromise can affect several systems. Separate projects/accounts and least-privilege deployment credentials can reduce that remaining common mode.
Pinned scrub gate Allowlist reconstruction from any real source, never redaction in place. Scan the fully generated datastore and images for secrets, high entropy, emails, URLs, absolute paths, hostnames, IPs, usernames, repository names, remotes, and unapproved commit identifiers. Review semantic content separately. Scanners miss context-sensitive or visual disclosures. Human review, OCR, image metadata stripping, and a second independent review are still required before public release.

Disposable operations Immutable release bundle, short log retention, no backup of runtime drift, atomic restore from the approved seed, and alerting on any write outside replay namespaces or any execution-denied request spike. Reset limits persistence, not the impact before detection. A compromised release artifact will return after reset until the artifact is revoked.

Scrub proof, not a scrub claim

The source note in the in-flight pinned-seed.json is useful provenance, but a public deployment needs machine-readable evidence over the rendered output. The gate should produce demo-seed-scrub-report.json beside the release bundle with:

  • seed schema, generator version, fixed time base, content digest, product compatibility range, and replay trace digest;
  • generated file counts by class and the exact temporary root scanned;
  • zero unreviewed matches for secret patterns, entropy, private keys, tokens, emails, URLs, IPs, absolute Windows or Unix paths, user-home fragments, hostnames, repository remotes, and source project names;
  • an allowlist for deliberately synthetic model names, task keys, and fixture commit hashes, with a deterministic derivation note for every hash;
  • OCR and metadata results for every image, plus confirmation that no source screenshot is shipped;
  • two independent generations with a clean recursive diff and identical manifest digest;
  • human review identity, time, reviewed digest, exceptions, and approval. A changed byte invalidates the approval.

Raw exports, intermediate redaction files, source screenshots, and scanner exception samples must never enter the repository, CI artifact, demo VM, or task result bundle. Real data may inspire the final prose, but the committed fixture is an allowlisted reconstruction.

§7Reset, seed versioning, and product updates

One versioned release unit

A demo release pins four compatible artifacts together: frontend and Task Server image, pinned seed, replay trace, and deployment policy. The manifest records each digest and the supported seed/product schema range. Rollback changes the whole unit, not one component.

demoRelease: 2026.08.1
productImage: <immutable digest>
seedSchemaVersion: 1
seedDigest: <sha256>
replayTraceVersion: 1
replayTraceDigest: <sha256>
deploymentProfile: public-demo-readonly
scrubReportDigest: <sha256>

Reset cycle

  1. Replay cycle: derive the visible replay offset from a fixed 12-minute trace. On reconnect, the server projects the current cycle position. The canonical seed is not rewritten for animation.
  2. Runtime replacement: recreate the ephemeral runtime volume from the approved seed on every deploy and restart, on operator request, and on a six-hour schedule. Six hours is a backstop for bugs and unexpected writes, not a substitute for read-only authorization.
  3. Atomic cut: generate into a new isolated volume, verify seed and scrub digests, start the candidate, probe browse and deny paths, then switch the proxy. Never delete and rewrite the datastore underneath a running Task Server.
  4. Failure behavior: keep the previous healthy bundle active if generation, migration, scrub verification, claim-denial probes, or smoke tests fail. Do not partially update content.
  5. Retention: rotate access and denial logs aggressively. Preserve aggregate security metrics, not visitor payloads or an indefinitely growing copy of public requests.

When the product moves

  • Every product release runs a compatibility job that generates the seed twice, starts the real Task Server in public-demo mode, opens both projects, checks every lane, Wiki, all six Dossiers, search, artifacts, and SignalR, then probes all execution paths for typed denial.
  • A schema migration updates the generator and seed manifest in one review. It does not import a live workspace or regenerate from an operator machine.
  • Content changes are explicit pull requests against the pinned source. They include a new digest, scrub report, both-theme captures for affected scenes, and a short semantic-change note.
  • AGT-2530 remains the owner of capture reproducibility and pinned provenance. The public instance consumes that contract after integration. It does not maintain a parallel screenshot-only fixture.
  • If current product code cannot read the approved seed, the previous demo release remains online until a fully compatible bundle passes. “Latest” is not more important than “safe and internally consistent.”

Approve S1 through S6 as the public read-only launch package, with S2 as the non-negotiable gate. S1 and S2 can proceed in parallel after AGT-2530 settles. S3 and S4 build on the denial contract. §9Decision request

This dossier is decision-ready. Approval is requested for the following package:

  1. Execution architecture: hard server denial plus replay-only Runner.
  2. Visitor surface: shared read-only launch, no public task mutations.
  3. Hosting: one dedicated disposable demo VM, separate from the website, productive Task Server, and productive Runners.
  4. Content: extend the one AGT-2530 pinned seed with the specified Wiki and six-state Dossier gallery.
  5. Operations: one immutable compatibility bundle, deterministic 12-minute replay, replacement on deploy/restart/on demand and every six hours, with atomic rollback.
  6. Launch gate: scrub attestation, execution-denial matrix, public endpoint inventory, external probes, and reset rehearsal must all pass before DNS is enabled.

Evidence basis: ADR-0056; the pinned screenshot-system decision; current AGT-2530 pinned seed and repeatability artifacts as in-flight evidence; AGT-2558 human-review state; WEB-17 ready state; networked security profile; and the dedicated Task Server VM separation rationale. This dossier changes no runtime, seed, card, hosting, or security configuration.
