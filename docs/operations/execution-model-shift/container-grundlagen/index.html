AWarum Isolation überhaupt — das Problem

Ein Coding-Agent ist ein Programm, das eigenständig Befehle ausführt: Dateien ändern, Shell-Kommandos laufen lassen, Netzwerk nutzen. Heute läuft dieser Agent direkt auf dem Host, im Maximal-Modus (--sandbox danger-full-access). Das bedeutet wörtlich: keine Grenze. Der Agent kann jede Datei des Hosts lesen und schreiben, auf alle dort liegenden Zugangsdaten zugreifen, beliebige Prozesse starten.

Für den Betrieb heute ist das handhabbar (vertrauenswürdige CLIs, dein eigener Rechner). Für das Produkt-Versprechen „sicher/isoliert" — und für den Fall, dass jemand fremde Repos oder weniger vertrauenswürdige Agenten laufen lässt — ist „keine Grenze" die schwache Stelle. Container schließen genau diese Lücke.

BWas ein Container eigentlich ist

Ein Container ist kein virtueller Computer (keine VM). Es ist ein normaler Prozess auf demselben Betriebssystem — aber das OS spannt drei Grenzen um ihn:

  • Namespaces — der Prozess sieht nur sein eigenes Dateisystem, seine Prozessliste, sein Netzwerk. Was außerhalb liegt, existiert für ihn schlicht nicht.
  • cgroups — Grenzen für CPU, RAM, IO (das nutzen wir heute schon für die Review-Drossel).
  • Capabilities/Seccomp — welche Kern-Systemaufrufe erlaubt sind.

Der entscheidende Punkt: Der Agent bleibt innerhalb des Containers voll autonom (danger-full-access bleibt Konzept) — aber „alles", was er tun darf, ist jetzt nur noch das, was im Container liegt. Autonomie und Isolation sind entkoppelt.

1Frage: Mount-Strategie — was sieht der Agent vom Dateisystem?

Der Agent muss am Code arbeiten. Der Code liegt aber außerhalb des Containers, auf dem Host. Ein Volume-Mount blendet ein Host-Verzeichnis in den Container ein — wie ein Fenster durch die Grenze. Die Frage ist: wie groß machen wir dieses Fenster?

KriteriumA · Großer MountB · Selektive Mounts
Sicherheitschwächer — Container sieht Nachbar-Repos + Secretsstark — Container sieht nur seine Aufgabe
Einrichtungeinmal, dann fertigje Task ein Mount berechnen (Orchestrator muss wissen, welches Repo)

Passt zum Claimschwächt „isoliert" abträgt „isoliert" glaubwürdig
Empfehlung: B (selektiv). Wenn „isoliert" ein Marketing-Kern werden soll, muss die Isolation echt sein — ein Container, der alle Nachbar-Repos sieht, ist nur halb isoliert. Der Mehraufwand ist überschaubar: Das Board weiß pro Task ohnehin, welches Repo (die project-Zuordnung), also ist der Mount-Pfad ableitbar. Konvention statt Konfiguration.

2Frage: Credential-Weg — wie kommt der Agent an Git/Tokens, ohne sie zu besitzen?

Der Agent muss pushen, Pakete ziehen, evtl. das LLM-CLI authentifizieren — er braucht Zugangsdaten. Aber Tokens sind das Sensibelste überhaupt. Die Frage: reichen wir die Tokens in den Container (er hält sie), oder halten wir sie außerhalb und lassen den Container nur durch einen Vermittler zugreifen?

KriteriumA · PassthroughB · Proxy
SicherheitToken im Container exfiltrierbarToken verlässt den Host nie
Bau-Aufwandgering (Mount/Env)höher (kleiner Proxy-Dienst, z.B. Git-Credential-Helper über Socket)
WiderrufToken rotierenProxy sperren — sofort, ohne Container-Neubau
Passt zum Claimschwächt „sicher" abträgt „sicher" glaubwürdig
Empfehlung: B (Proxy) als Zielbild, A als Startpunkt. Der Proxy ist die saubere Antwort, aber echter Bau. Pragmatisch: mit A starten (Passthrough, read-only wo möglich, kurzlebige Tokens), den Proxy als Härtung nachziehen. So blockiert die Sicherheits-Ambition nicht den ersten funktionierenden Container-Flow.

3Frage: Image-Herkunft — woraus wird der Container gebaut?

Ein Container startet aus einem Image — einer Vorlage, die das Mini-Dateisystem und die installierten Programme enthält (hier: die CLIs codex/claude, node, git, das .NET-Runtime). Die Frage: liefern wir ein fertiges Basis-Image aus, oder baut es jede Maschine beim ersten Lauf selbst?

Empfehlung: A (Basis-Image) für das Download-Erlebnis. Der D5-Meilenstein ist „Download + super-easy Onboarding". Ein fertiges Image macht den ersten Container-Start zu Sekunden statt Minuten — das ist der Wow-Moment. B bleibt der Fallback für Offline-/Air-Gap-Situationen. Praktisch: beides anbieten, A vorwählen. Das Image-Bauen wird Teil der Release-Pipeline (die gerade gelandet ist).

4Frage: Rollout-Tempo — für wen ist Container ab wann der Default?

Container-Isolation ist das Zielbild — aber die Repo-/Credential-Reibung (Fragen 1+2) ist der „hard part". Die Frage: schalten wir Container sofort als Default für alle Neu-Installationen, oder erst als Opt-in, bis die Reibung nachweislich weg ist?

Empfehlung: Opt-in zuerst, Default danach. Der Installer zeigt Container als empfohlene Option, aber der harte Reibungspunkt (Mount+Credentials in fremden Umgebungen) muss erst im echten Betrieb bewiesen sein. Sobald ein paar echte Läufe sauber durch den Container gehen, wird Container die Vorauswahl. Kein Big-Bang.

CZusammenschau — wie die vier zusammenhängen

Die vier Fragen sind nicht unabhängig. Die ersten zwei (Mount, Credentials) sind die Sicherheitssubstanz — sie entscheiden, ob „isoliert/sicher" ein ehrlicher Claim wird. Die zweiten zwei (Image, Rollout) sind die Erlebnis-/Tempo-Fragen — sie entscheiden, wie sich Download & Onboarding anfühlen und wie riskant die Einführung ist.

Die eine Kernentscheidung darunter

Alle vier hängen an einer Grundhaltung: Wie stark ist „sicher/isoliert" das Produktversprechen? Wenn es der Marketing-Kern wird (dein Instinkt zur Container-Richtung), dann lohnen die teureren Antworten bei 1+2 (selektiv + Proxy) — sie sind der Beleg hinter dem Claim. Wenn es „nice to have" bleibt, reichen die einfacheren (großer Mount + Passthrough) und du sparst Bauaufwand. Diese eine Frage beantwortet die anderen fast von selbst.

Dieses Dokument ist Grundlage, keine Festlegung. Sobald du die Richtung (v.a. die Sicherheits-Ambition) und die vier Antworten gibst, schneide ich die konkreten Umsetzungskarten — und die Antworten fließen in die Marketing-/Website-Positionierung (AOW-8) ein.
