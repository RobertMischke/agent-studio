Konzept-Pipeline

Manche Karten liefern kein Code-Diff, sondern eine Entscheidung: ein Design, eine Analyse, ein Vorschlag. Ihr Ergebnis soll ein erstklassiges Dossier-Konzept sein - und ihr Weg dorthin braucht eine andere Pipeline als Build → Test → Merge.

Anlass Design-Karten bouncen in der Code-Pipeline (AGT-2355) Basis Planning/Research-Task-Kinds (2026-05) Status Konzept, entscheidungsreif

1Das Problem

Die heutige Pipeline ist für Coding-Karten gebaut: der Agent ändert Quellcode, es folgt Build, Test, Aspekt-Review, und das Ergebnis wird nach develop integriert. Eine Design- oder Konzept-Karte („finde ein besseres Deck-Icon", „entwirf die Mount-Strategie") hat aber nichts zu bauen und nichts zu mergen. Sie produziert einen Vorschlag, über den ein Mensch entscheidet.

Symptom

AGT-2355 (Deck-Icon) kam zweimal mit NeedsInput zurück und landete in Escalated. Nicht weil der Agent scheiterte, sondern weil die Pipeline für sein Ergebnis keinen Zielort kennt: kein Merge-Ziel, kein Test-Gate, kein Platz für „hier ist mein Konzept, bitte entscheiden".

2Was schon existiert

Wir müssen nicht bei null anfangen. Zwei Bausteine liegen vor:

  • Planning/Research-Task-Kinds (docs/concepts/planning-research-task-kinds-2026-05.md): Kinds mit read-only-Pipeline, deren Agent nur einen Report schreibt (status.md) statt Quellcode zu ändern — plus ein Promote-Flow, der ein fertiges Planning-Ergebnis in eine Coding-Karte überführt (PlanningPromotion).
  • Konzept-Dossier-Konvention: Analyse-Dokumente als Dossier (Ordner + workbench.json + Hausstil-index.html), wie dieses hier.

Die Lücke: Der read-only-Kind landet in status.md — flüchtig, nicht als erstklassiges, im Wiki sichtbares Konzept. Und es gibt kein Gate, das „Konzept fertig, Sichtblick nötig" von „Code fertig, Merge nötig" unterscheidet.

3Die Konzept-Pipeline

Ein Pipeline-Typ, dessen Deliverable ein Dossier-Konzept ist und dessen Gate ein Konzept-Review + Sichtblick ist - kein Build, kein Test, kein Merge.

Was der Konzept-Run konkret tut

  • Legt einen Dossier-Ordner unter docs/operations/<topic>/ an: workbench.json (Registrierung) + index.html (Hausstil, deutsch, SVG wo es hilft).
  • Schreibt das Konzept dorthin — Alternativen, Empfehlung, offene Entscheidungen — statt in status.md.
  • Ändert keinen Produktcode. Der Worktree-Diff betrifft nur docs/.

Der Kern

Bei einer Konzept-Karte ist „Sichtblick nötig" das Ziel, nicht ein Scheitern. Der Outcome-Klassifizierer und die Lane-Logik müssen das als erstklassigen, erfolgreichen Abschluss behandeln — nicht als Eskalation.

6Offene Entscheidungen (Robert)

  • Eigene Lane oder Marker? Bekommen Konzept-Karten eine eigene „Sichtblick"-Lane, oder einen Marker in 5-human-review, der sie von Code-Abnahmen unterscheidet?
  • Wie viel darf der Agent selbst entscheiden? Nur Alternativen vorlegen (immer Sichtblick), oder bei klaren Fällen selbst eine Empfehlung als Default setzen, die nur bei Widerspruch aufgehalten wird?
  • Ein Konzept = ein Dossier, oder Sammel-Dossiers? Kleine Konzepte (Icon) einzeln vs. in ein thematisches Sammel-Dossier (z.B. „Board-UX") einsortiert?

Implementation defaults pending Robert's answers:

  • Lane: reuse 5-human-review and distinguish concepts with a durable concept-sight-review marker. No new lane is introduced.
  • Agent autonomy: the agent may recommend and mark a default, but human sight review remains mandatory before completion or promotion.
  • Dossier cardinality: one concept card produces exactly one Dossier directory. Shared or collected Dossiers are not written automatically.

These are reversible defaults, not final product decisions. Robert's answer supersedes them.
