Decision dossier · AGT-2662 · concept only

Rebase, merge, and bounce steering

Use different Git shapes at different attribution boundaries. Reconcile a failed delivery by rebasing into a fresh fenced generation. Integrate a reviewed delivery by preserving its exact commit objects. Move routine bounce recovery from a live session into a bounded platform rule, and reserve model-authored steers for evidence that is genuinely complex.

Status decision pending Phase decision ready Evidence cut 14 August 2026 Implementation none in this card

Recommendation

Keep the hybrid, make its boundary explicit, and automate the first bounce. A requeue round should rebase the delivery onto the current origin/<integration-branch> because a new RunAttempt, fence, Result Envelope, attribution range, and review subject replace the old generation. Server integration should remain merge-first because it is operating after review and acceptance still needs the reviewed delivery SHAs to be ancestors of the target branch. Use one deterministic platform steer first, one strong-model targeted steer only on a repeat or a complex conflict, then escalate after two recovery rounds in the same operator review epoch.

The decision in one sentence

Invariant: do not rewrite reviewed delivery identity without an exact mapping. Operator choice: which bounded recovery rail authors the next prompt, how many rounds it receives, and whether Batch Gate candidate construction preserves SHAs by merge or pays for replacement mapping.

§1One pipeline, four Git boundaries

“Rebase or merge?” has no single pipeline-wide answer. The relevant question is: which identity has already become evidence at this boundary?

01

Delivery generation

The coding attempt publishes one immutable result ref and one expected head SHA. Its exact BaseSha..ResultSha range becomes commits[].

02

Review subject

Remote Review tests and grades that exact result SHA. A later result is a new subject, not a silent edit of the old one.

03

Integration

The reviewed delivery joins develop. Acceptance later checks current-attempt lineage and Git ancestry, not a narrative merge record.

04

Promotion

The train tests one pinned develop candidate and advances main to that exact SHA. No Git operation may create a new post-gate subject.

A requeue crosses back from stages 2 or 3 into a new delivery generation. That is why it may rewrite commits. Server integration stays within stage 3, after the old objects became acceptance evidence. That is why merge-first is not an aesthetic preference there.

§2Current hybrid and its attribution history

What the current code does

  1. Remote completion fixes the attribution boundary. The Task Server verifies the generation-scoped immutable result ref, then attributes the exact Result Envelope range to the attempt. The current review subject names one ResultSha.
  2. Server integration is merge-first. GitService.MergeRefIntoIntegration first runs a normal merge --no-ff with rerere disabled. A textual conflict gets one mechanical three-way ort/rerere merge. Only if both SHA-preserving paths fail does it try an isolated rebase.
  3. The rebase fallback is conditional. It may proceed only for a linear delivery whose old and new commit counts match one-to-one. The platform persists supersededBySha links before push. A conflict or changed cardinality returns AgentRoundRequired.
  4. Acceptance does no integration work. TaskTransitionService.ValidateIntegratedAcceptance validates that the review subject still belongs to the current attempt and asks TaskIntegrationStatusService whether the active attributed commits, or the exact reviewed result fallback, are ancestors of the effective integration branch.
  5. A requeue creates a new attribution generation. The old delivery commits remain audit history with supersededByAttempt. The new attempt publishes a new fence, a new exact range, and a new single-head review subject after rebasing onto current origin.

AGT-2632 was an attribution correction

The AGT-2563 recovery cut tried rebase before exhausting SHA-preserving merge shapes. When a real replay changed commit cardinality, the integrator correctly refused to invent attribution but left the card waiting for manual recovery. AGT-2632 changed the order to merge, mechanical merge, then mapped rebase, and added one bounded agent round for the ambiguous case. Its delivery commit 1d0cd02adf was itself integrated by merge commit 04dd8166f3 on 12 August 2026, preserving the reviewed source object in develop.

Current-document discrepancy

The older Task Integration and the Worktree/Merge Workflow execution paragraph still says the common runner rebases a behind-base delivery before its normal merge. That sentence predates AGT-2632. The current Pipeline domain map, the 11 August commit, tests, and GitService agree on merge-first. The stale explainer should be corrected in the first migration slice.

§5Batch Gate changes the race, not attribution

AGT-2648 closes a set of reviewed deliveries on a pinned develop base, constructs one candidate, runs one full suite, and publishes only the tested tip. That removes most per-card races against a moving canonical branch. It does not make per-card attribution optional.

Race frequency falls

Several members are assembled against one closed base under one coordinator. A later canonical advance invalidates the batch as stale-base instead of producing several independent behind-base merge attempts.

Content conflicts remain

A member may conflict with the base or an earlier admitted member. That is a real content relationship, not a develop timing accident. The member is ejected and its next generation waits for a later batch.

Exact publication becomes stricter

Every merge or rewrite used to assemble the candidate must happen before the gate. The publisher may only fast-forward the recorded pre-tip to the tested candidate and verify the remote SHA.

AGT-2648 needs an explicit reconciliation with AGT-2632

The current Batch Gate dossier says each member is replayed using mechanical rebase rules with replacement-SHA mapping. That is internally possible, but it reintroduces the mapping burden that AGT-2632 deliberately put behind two SHA-preserving merge attempts. Before implementation, choose one of two explicit batch contracts: recommended: merge each member into the disposable candidate in deterministic order, preserving original delivery SHAs and adding a pre-gate merge commit per member; alternative: retain rebase replay and make the native per-member batch record carry a complete old-to-new replacement set. Do not leave this as an incidental Git implementation detail.

A merge-first batch candidate composes cleanly with candidate-SHA promotion: all per-member merge commits are prebuilt, the full suite tests their final combined tip, develop is fast-forwarded to exactly that tip, and the promotion train may later test and promote the same or a later pinned develop candidate. No post-test merge commit is allowed.

In the batch world, a conflict steer must also respect publication order. If card B conflicts with already admitted card A, rebasing B onto today's origin/develop may not reproduce the conflict while A exists only in the temporary batch. The coordinator should either wait until the green survivors publish and then issue the ordinary current-origin steer, or attach the exact batch candidate/ref and a typed wait condition. A generic session tick must not guess.

§6Bounce steering today

The operational practice on 14 August is broader than any one backend recovery service. On every orchestration tick, the session inspects delivered cards and performs the following work:

  1. Find a review bounce whose computed integration state is conflict-skipped, or an Escalated card that is recoverable and not deliberately held.
  2. Append a STEER section to the card's prompt.md with the current integration branch and a narrow recovery instruction.
  3. Change thinkingLevel to high. This is a routing override for a mechanical correction round, not a claim that a weaker model should handle a semantic conflict.
  4. Move the card back to 2-ready through the application move API, normally at the front of the lane.
  5. On the next claim, the runner creates a fresh attempt and fence. The agent reconciles the existing delivery, reruns the gate, and publishes a new immutable result. It does not redo the feature.
## STEER · Integration recovery

Your delivery could not be merged.
Rebase it onto CURRENT origin/<integration-branch> and resolve conservatively.
Re-run the relevant gate and deliver again.
Do not redo the feature work.

Observed practice: wording varies slightly by card, but the four imperatives are stable: current origin, conservative resolution, gate again, and no feature restart. Escalated non-hold cards use the same return-to-Ready shape. Deliberate holds remain parked.

§7Four automation scenarios

1 · Session orchestrator remains the owner

Benefit: already practiced, flexible, and able to notice several board states at once. Cost: repeated board scans, prompt edits, routing edits, and move calls on every tick. Failure mode: the loop stops with the session, as the 13 August pile-up demonstrated. It also depends on the session consistently excluding deliberate holds and avoiding duplicate steers.

Position: keep only as a temporary backstop and audit comparator.

2 · Platform rule owns the normal bounce

A backend policy consumes a typed current-generation conflict, verifies the task is recoverable and not held, records an idempotent round fingerprint, appends the standard steer through the application-owned continuation boundary, selects supported high without crossing a routing floor, supersedes the delivery, and moves the card to Ready. No model is needed. AGT-2544 proves the pattern for an envelope failure; AGT-2632 and the recovery endpoint supply most conflict-specific primitives.

Position: recommended default rail for round 1.

3 · Guardian writes a targeted steer

A strong model reads the exact failure class, conflicted files, merge/rebase diagnostics, attributed diff, latest gate evidence, original requirement, prior steer, and current target SHA. It writes only the next recovery instruction. Pure policy validates the output and owns the lane action. This generalizes AGT-2654: a classifier names concrete defects, one precise steer is appended, and durable evidence prevents restart from replenishing the retry.

Position: round 2 or immediate use for intrinsically complex evidence.

4 · Batch Gate becomes the integration owner

Closed candidate construction makes per-card races with a moving develop uncommon. Routine stale-base bounces largely disappear. Steers remain for genuine base/content conflicts, cross-member interactions, ambiguous attribution, or a member ejected from red isolation. The coordinator supplies the exact failed candidate context and waits for survivor publication when current origin does not yet contain the conflicting predecessor.

Position: eventual operating context, not a replacement for bounded steering.

The canonical model routing policy says an environmental failure or stale base should not cause model promotion. It also says high is supported but is not a default core-task rung. Therefore the session's high downgrade should become an explicit, logged recovery recipe, validated against the selected model's supported ladder and never allowed below a correctness floor. The guardian analysis itself should default to Sol/medium for bounded but ambiguous synthesis. Use Sol/xhigh only when the evidence touches a hard-floor concern such as fencing, distributed authority, security, or plausible data loss.

Two rounds per operator-owned review epoch

  1. Round 1, deterministic: for an eligible first conflict fingerprint, append the standard current-origin steer, normalize thinking to supported high subject to floors, supersede the current generation, and queue at the front of Ready.
  2. Round 2, targeted: when the new delivery produces the same or a semantically related conflict, invoke the strong guardian once. Persist its evidence fingerprint and targeted steer before requeue.
  3. Exhaustion: a third eligible conflict in the same review epoch reaches Escalated. Do not keep reporting the problem while silently renewing the loop.
  4. New operator epoch: an explicit operator requeue may open a new bounded opportunity. Automatic moves never reset the epoch.

The proposed cap of two is an operator choice, not a correctness invariant. It gives the common case a free deterministic repair, gives one difficult case a reasoned repair, and then stops. It is consistent with the repository's broader rule that loop budgets are durable and that models classify or author bounded output while code owns actions.

§10Operator decisions

Decision set ready for review

  1. Hybrid Git policy: approve rebase for fresh delivery requeue generations and merge-first for reviewed server integration.
  2. Automatic ownership: approve Scenario 2 as the default first-recovery rail, owned by the backend rather than the session.
  3. Guardian threshold: approve Scenario 3 for a repeat fingerprint or immediately complex evidence, with Sol/medium as the normal analysis floor.
  4. Loop budget: approve two automatic recovery rounds per operator-owned review epoch, template then targeted, followed by Escalated.
  5. Routing recipe: approve a supported high correction route for mechanical rounds, while preserving model-policy hard floors and re-scoring semantic conflicts.
  6. Batch reconciliation: amend the AGT-2648 implementation contract to choose member-level merge-first candidate construction, or explicitly fund and test native replacement mapping if rebase replay is retained.

Recommended answer: approve all six. The first five turn a fragile repeated session task into a bounded, auditable product rule without giving a model lane authority. The sixth prevents Batch Gate from accidentally reopening the attribution ambiguity that motivated AGT-2632.
