Accepted architecture · AGT-2662 · Scenario 2 implemented by AGT-2683

Rebase, merge, and bounce steering

The pipeline should preserve attributed delivery commits when it integrates, but it should refresh a bounced delivery by rebasing before the next fenced review. The apparent inconsistency is a stage boundary, not one Git policy applied twice.

Status accepted Phase implemented Evidence cut 26 August 2026 Implementation AGT-2683

Recommendation

Keep the hybrid and make its boundary explicit. A fresh agent recovery round rebases its delivery onto current origin/<integration-branch>, records a new fenced result and reruns review. Canonical integration tries SHA-preserving merge first. Promotion advances main only to the exact tested candidate SHA. Move routine conflict bounces from session labor into one deterministic backend round; invoke a strong guardian only after repetition, contradictory evidence, or a genuinely semantic conflict.

Scenario 2 accepted and delivered

AGT-2683 moved deterministic acceptance and conflict requeue into a default-on backend HostedService. It rechecks current Git integration before completion, respects operator and concept holds, persists a restart-safe conflict budget, and escalates after the configured limit. The session orchestrator is now an observer for eligible cards. The Batch Gate and strong guardian remain separate pending decisions.

§1One attribution lens

The governing object is not a pretty branch graph. It is the relationship among the delivery evidence, the reviewed subject, and the canonical branch:

  • Acceptance evidence: active, non-superseded task.json commits[] entries and, when attribution is empty, the current immutable review result.
  • Review subject: one fenced result ref and one expected head SHA. The branch must still resolve to that SHA when it is fetched for integration.
  • Integration truth: every active attributed commit is an ancestor of the configured integration branch. Pipeline receipts and badges cannot manufacture this fact.
  • Promotion truth: the tested candidate SHA is the SHA published to main. A merge, squash, or rebase after the gate creates a different and therefore untested subject.

Preserve identity at integration

The original delivery SHAs are already named by Grades, Evidence, Records, review subjects, and commits[]. Prefer operations that keep those objects reachable.

Renew identity on requeue

A recovery run is a new attempt. It may rewrite the old delivery because the fresh fence and attribution pass record the replacement result before review.

Never mutate after the gate

The candidate-SHA train permits only exact publication. New history after a green gate invalidates the receipt.

Merge-first does not mean merge-only

The current server code still contains a tightly guarded rebase fallback. The decision is that SHA-preserving paths are attempted first and attribution ambiguity fails closed. Calling the implementation simply “merge” would hide this recovery path; calling it “rebase integration” would hide the now-primary preservation rule.

History that changed the answer

The first 10 August recovery cut rebased a behind delivery before trying a merge. That was mechanically safe only when it could rewrite commits[] with an exact replacement map. In practice, rewriting the objects before proving that preservation was possible made acceptance attribution fragile. The 11 August AGT-2632 amendment reversed the order: preserve first, map only as a fallback, refuse when the map is not exact. The acceptance guard and rollback behavior turn that historical lesson into an invariant.

The invariant forces part of this answer. An unrecorded squash or rebase cannot be canonical integration under the current acceptance model. The platform must either preserve delivery SHAs or atomically replace their evidence identities before publication. Given that choice, merge-first is the lowest-risk operation. A cardinality-preserving mapped rebase remains a legitimate bounded fallback, which is exactly the current mechanical integrator’s rule.

Main is not another reconciliation stage

Once a develop candidate is green, the promotion train may wait while develop advances, but it publishes the pinned candidate SHA only if lineage still permits a fast-forward from current main. Creating a new merge, squash, or rebase between the receipt and main would test one object and release another. Exact-SHA publication is therefore forced, not stylistic.

§7How Batch Gate changes the calculus

AGT-2648 proposes a closed, fenced candidate built from several eligible deliveries, one complete suite on the exact combined SHA, and per-member evidence before publication. It reduces develop races because members no longer integrate independently while other full suites run. It does not erase attribution.

A decision still open inside AGT-2648

Mechanical rebase replay makes a compact batch candidate but spends attribution complexity on every member. Prebuilt no-FF member merges preserve original SHAs and make acceptance simpler, at the cost of a more branched candidate. The Batch Gate pilot should measure both construction shapes in shadow mode before making rebase replay permanent. Whichever shape wins, the tested candidate and per-member evidence must be identical to what is published.

§8Bounce steering before the platform rail

Before AGT-2683, the broad operating practice was session-side. On a reviewed card with integration.status = conflict-skipped, the orchestrator:

  1. appends a STEER section to prompt.md: the delivery could not be merged; rebase onto current origin/<branch>; resolve conservatively; rerun the gate; deliver again; do not redo feature work;
  2. changes thinkingLevel to high for the mechanical round rather than spending xhigh by default;
  3. moves the card to 2-ready through the move API; and
  4. applies the same requeue pattern to eligible escalated, non-hold cards.

The next claim creates a new attempt and fence. Its delivery and review re-record current SHAs, so the rebase is not silently substituted underneath old evidence. The operational weakness was ownership: the loop advanced only while the orchestrator session was alive and inspecting every tick. The failure repeated about six times. One observed manual tick reduced 38 Human Review cards to 8 in progress plus 23 Ready cards immediately, proving that the mover belonged in deterministic platform code.

## STEER

Your delivery could not be merged. Rebase it onto the CURRENT
origin/<integration-branch>, resolve the conflict conservatively,
rerun the gate, and deliver again. Do not redo the feature work.

Existing platform seams are narrower than the practice

  • POST /api/tasks/{jobId}/integration/rebase already validates a recoverable conflict-skipped state, saves a focused Steer intent, appends a continuation note, supersedes the current delivery, promotes the card to Ready, and emits a timeline record. It is operator-triggered and does not own the complete automatic rule or thinking downgrade.
  • IntegrationAgentRoundService already starts one automatic pre-Human-Review Steer round when the merge-first integrator returns AgentRoundRequired. It is bounded per operator review epoch. It addresses attribution-ambiguous integration, not every reviewed conflict-skipped card.
  • AGT-2544’s envelope policy already demonstrates deterministic backend requeue: one automatic retry for an incomplete immutable Result Envelope, then typed unverified-delivery escalation.
  • AGT-2654’s visual guardian already demonstrates evidence-driven steering: a bounded classifier names defects, pure policy permits one retry with a precise steer, and repetition reaches Human Review with durable evidence.

Scenario 2 extends and unifies those deployed patterns; AGT-2683 now supplies that rail without introducing another scheduler.

§9Four automation scenarios

Scenario 1: session orchestrator

Supervisor only The model may inspect the board, explain unusual evidence, and alert on held or repeated cases. It is no longer the mover for a typed eligible terminal.

  • Strength: adaptable immediately and able to notice odd context around a card.
  • Cost: repeated board scans and model attention for a deterministic action; every card consumes orchestration labor.
  • Fragility: no durable owner after the session ends. The 13 August pileup is the direct failure mode.
  • Use: deliberate operator intervention outside the allowlist and supervision of platform health.

Scenario 2: platform rule

Implemented default AcceptanceRailHostedService consumes the typed integration status and current task facts every three minutes by default. Git-proven integrated coding cards complete through the existing acceptance guard. When a conflict state is fresh, recoverable, within its durable budget, and not on hold, shared application services append an idempotent template, supersede the failed generation, and queue Ready.

  • No model is needed: branch, result ref, failure code, epoch, attempt, conflict paths, and retry count are already structured.
  • Reuse rather than duplicate: build on the AGT-2544 envelope retry policy, TaskIntegrationRecoveryEndpoints, IntegrationAgentRoundService, OperatorReviewRequeueService, commit supersession, timeline events, and the state machine.
  • Availability: the durable hosted worker owns completion. Backend restart resumes the task-local recovery fingerprint and counter.
  • Boundary: the rule does not resolve content, edit Git, waive a gate, or requeue a hold card.

Scenario 3: guardian writes a targeted steer

Escalation tier A strong model receives the actual failure evidence: conflict files and hunks, old and current bases, active and superseded commits, prior prompts and steers, gate results, card-scoped diff, and invariant warnings. It returns a structured diagnosis and a targeted correction prompt. Pure policy still decides whether that prompt may be executed.

  • Worth the tokens when: a deterministic round repeated; the same conflict recurs after a claimed rebase; the conflict is cross-cutting or semantic; attribution, scope, or gate evidence contradict; multiple deliveries interact; or a human needs a decision packet.
  • Not worth the tokens when: the first failure is a clean, typed stale-base or ordinary content conflict with a known recovery template.
  • Precedent: AGT-2654 proves one evidence-linked automatic Steer with restart-safe receipts. AGT-2557/W15 places the strong analyzer above deterministic inspection and allows A1 rebase-steer through public APIs.
  • Authority: a model may author the explanation and proposed steer, never the lane or Git mutation.

Scenario 4: Batch Gate world

Pending decision A closed manifest and single candidate make per-card develop races uncommon. A moved canonical base invalidates or reconstructs the batch; it does not ask every member’s agent to rediscover the same race. Conflict ejection still creates a bounce only for the member whose content does not compose with the frozen base or an admitted predecessor.

  • The deterministic steer remains the default for one ejected member.
  • The guardian becomes more valuable for cross-member interaction, repeated ejection, or a conflict cascade because it can compare the exact batch order and failing cohort.
  • Batch rollback returns unmirrored members to the existing per-task gate without inventing a coding reissue.
  • The mechanism shrinks but does not disappear: genuine content conflict is irreducible.

§10Thinking level and bounded-round policy

The canonical Model Routing Policy says not to promote a stale-base or environmental reissue and reserves stronger routes for correctness risk and ambiguity. It also states that explicit operator pins win and that quota never lowers a hard floor.

A blanket downgrade is unsafe. A mechanical Git instruction can still touch a security boundary or subtle persistent-state conflict. The backend rule must compute the policy floor first, then apply high only when it does not reduce required capability. The action receipt records old route, selected route, reason, policy version, and whether the card carried an explicit pin.

Operational defaults

  • Round cap: a restart-safe task-local conflict budget, configurable with a safe default of five requeues.
  • Escalation: budget exhaustion reaches 5e-escalated with integration-recovery-exhausted. A guardian remains optional follow-up scope for complex evidence.
  • Service objective: claim or visibly defer an eligible obligation within five minutes. An unavailable worker becomes a platform Problem rather than a quiet card pile.
  • Kill switch: the implemented switch is global; per-project disable remains follow-up scope. Disabling automation leaves typed obligations visible and returns ownership to the session/operator path.
  • Measures: bounce volume, time to new claim, repair rate, repeat rate, guardian-call rate and tokens, human reversal, wrong-scope changes, attribution failures, and cards stranded by unavailable ownership.

Accepted decision

“Preserve reviewed delivery SHAs at canonical integration by trying merge first; permit rebase only in a fresh fenced recovery round or with an exact persisted replacement map. Publish main only at the gated candidate SHA. Move recoverable conflict-skipped bounces and Git-proven acceptance into a deterministic, restart-safe backend rail with a bounded task-local budget. Keep holds and concept decisions human-owned, and escalate when the configured budget is exhausted.”
