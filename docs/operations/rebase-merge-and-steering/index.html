Rebase, merge, and bounce steering

The pipeline is intentionally hybrid. Delivery repair may rewrite a superseded candidate under a new fence. Canonical integration should preserve the accepted delivery objects whenever possible. This page explains why, where the operator still has a choice, and how routine bounce recovery can move from session labor into bounded platform policy.

Status decision pending Phase decision ready Evidence cut 14 August 2026 Implementation none in this card

Recommendation

Keep the hybrid and make its boundary explicit. Use rebase as the default agent-side repair for a superseded delivery, then record a fresh fence, result SHA, commit attribution, gate, and review subject. At server integration, keep AGT-2632's merge-first order: direct merge, then SHA-preserving mechanical merge, and only then a one-to-one mapped rebase fallback. Never squash an accepted delivery under the current evidence contract. Automate routine conflict bounce recovery as a deterministic backend rule; invoke a strong guardian only after the deterministic round fails or the evidence shows a genuine semantic conflict.

Decision requested

Approve the stage-specific Git policy and the steering escalation ladder. This is not approval to change the integrator, task API, prompts, or lane transitions. The implementation slices in §10 remain proposed.

§1Short answer: identity changes meaning by stage

Repairing a delivery

The previous subject is superseded. A new attempt may rewrite commits because the platform records new commit identities and reviews the new exact head.

Integrating a delivery

The accepted subject is authoritative. Rewriting it after review disconnects acceptance evidence from Git ancestry unless an explicit mapping contract replaces that proof.

Publishing a batch

The exact tested candidate is authoritative. Replayed member SHAs are valid only when the batch record maps each accepted result to its replacements before publication.

“Rebase or merge?” therefore has no pipeline-wide answer. The correct answer depends on whether the operation is creating a new review subject, preserving an accepted subject, or publishing a separately fenced combined candidate.

The forcing invariant

Under the current acceptance contract, the delivery commits recorded for the current attempt must be ancestors of the integration branch. If integration rewrites those objects without first replacing the evidence with an authoritative map, acceptance becomes ambiguous and must refuse. This is why merge-first is not merely a history preference.

§3The current hybrid, without smoothing over its seams

Server side: merge-first since AGT-2632

GitService.MergeRefIntoIntegration first synchronizes the target, checks whether the exact delivery is already an ancestor, and attempts git merge --no-ff --no-edit. A conflict triggers a SHA-preserving mechanical three-way merge with ort and recorded rerere resolution. Only after both merge routes fail does it try an isolated rebase. That fallback is accepted only for a linear delivery with unchanged commit cardinality and a one-to-one old-SHA to new-SHA map. Otherwise the outcome is AgentRoundRequired.

The historical cause is concrete. AGT-2563 introduced a conflict-free replay path for behind-base deliveries. In AGT-2632 that replay changed delivery commit cardinality. The integrator correctly refused to guess which replacement represented which accepted commit, but the refusal initially parked the card until an operator intervened. AGT-2632 changed the order to exhaust SHA-preserving merge strategies first and added one narrow automatic agent continuation for attribution ambiguity.

TaskTransitionService.ValidateIntegratedAcceptance separately proves that human acceptance is not an integration trigger. For a coding delivery moving from Human Review to Completed, it validates the current review attempt and refuses the move unless current integration status is integrated. Escalated coding cards are likewise accepted only when their latest attributed task commit is an ancestor of the resolved integration branch, absent an explicit operator override.

Agent side: rebase the superseded delivery onto the current target

A requeue round starts from the existing delivery but creates a new authoritative attempt. The steer asks the agent to fetch the current origin/<integration branch>, rebase the delivery, resolve conservatively, rerun the relevant gate, and deliver again without redoing feature work. The old delivery remains superseded history. The fresh run records the new commits, fence, immutable result ref, result SHA, and review subject, so a rewrite is not hidden from acceptance.

This route also fits the review shape: one linear candidate with one expected head SHA and a diff against the current target. Rebase is a default here, not an invariant. A merge of the target into the delivery can be made reviewable, but it introduces a non-linear subject and increases the risk that upstream commits or a broad merge commit enter task attribution. Cherry-pick is reserved for controlled salvage because it reconstructs intent by selection.

Why the hybrid is coherent

Before a new fence, the pipeline is allowed to create a replacement delivery. After acceptance has attached to an exact delivery, integration must preserve that subject or explicitly replace its identity proof. The boundary is authority, not aesthetics.

The operator has a genuine choice between rebase and merge-target-in during delivery repair. The recommendation is driven by review ergonomics, not by the acceptance ancestry invariant, because the repaired delivery receives new evidence either way.

Where the invariant decides, and where taste remains

Forced: do not silently squash, cherry-pick, or ambiguously rebase an accepted delivery. Choice: a provably mapped rebase-fast-forward remains technically valid, and the operator may decide whether its linear history is worth the extra evidence complexity. Recommendation: preserve it as a late fallback, not the primary integration path.

§7How Batch Gate changes the calculus

The AGT-2648 Batch Gate dossier proposes a different integration authority. It closes a manifest on a pinned develop base, mechanically replays each eligible delivery into a temporary candidate, runs one full suite on the exact combined SHA, and publishes only that exact green tip. Every replacement SHA maps back to its original delivery SHA. A conflict ejects only that member to the rebase-steer path.

This makes per-card merge commits optional inside the future batch path, but it does not make attribution optional. The native batch record must bind task key, attempt, delivery epoch, original result SHA, replacement SHA set, membership digest, base SHA, tested candidate SHA, gate profile, and integration receipt. The current five-class historical integration record is not sufficient authority by itself.

QuestionPer-card integration todayBatch Gate world
What is the gated subject?The exact merge result for one delivery.The exact closed combined candidate.
How is attribution proven?Accepted delivery objects remain ancestors, or a one-to-one mechanical rebase map is persisted.Each original delivery maps to its replayed replacement set in the fenced batch manifest and receipt.
What if develop moves?Synchronize before serialized merge; a new result must be gated.Mark the green run stale-base, rebuild on the new base, and run the suite again.

Batch Gate therefore reduces develop races and routine per-card rebases, but only after its native evidence contract exists. Until then, merge-first remains the safer production answer. Even after Batch Gate, genuine content conflicts still need a replacement delivery round; the coordinator must not resolve product semantics centrally.

§8Bounce steering today: two mechanisms with different coverage

The session-side operating practice

On each orchestration tick, the session inspects bounced review cards. When integration is conflict-skipped, it appends a STEER section to prompt.md, changes the card's thinking level to high for the bounded repair round, and moves the card to 2-ready through the move API. Escalated cards that are not explicit holds are requeued in the same family of sweep. The practical steer is:

Your delivery could not be merged. Rebase it onto CURRENT origin/<integration branch>, resolve conservatively, rerun the relevant gate, and deliver again. Continue from the existing work; do not redo the feature.

This works while the orchestrator session is alive and attentive. It is model-authored control-plane labor on every tick, duplicates state classification already available to the backend, and can append inconsistent wording or miss a lane. On 13 August 2026 the session stopped overnight and 17 cards accumulated. That observation is operational evidence supplied with AGT-2662, not a controlled benchmark.

The narrow AGT-2632 backend continuation already present

IntegrationAgentRoundService handles one narrower case. When pre-human-review remote integration returns AgentRoundRequired because direct merge, mechanical merge, and safe mechanical rebase could not preserve attribution, it persists a steer intent, appends a continuation note, supersedes the delivery commits, moves the Auto Review card to the top of Ready, and records a timeline event. RemoteIntegrationContinuationPolicy allows one automatic agent round per operator review epoch, then leaves repeated ambiguity for Human Review.

The operator endpoint POST /api/tasks/{jobId}/integration/rebase separately packages the fenced ref, exact result SHA, integration branch, steer intent, supersession, Ready move, and timeline record for recoverable failures in Human Review or later. It is deterministic but remains operator-triggered.

Current-state conclusion

The platform already knows how to persist and bound one attribution-ambiguity continuation and exposes a one-click rebase recovery endpoint. The broader conflict-skipped and escalated-card drive-to-conclusion loop is still session-owned in practice. Scenario 2 is an extension and consolidation, not a greenfield invention.

Thinking-level policy

The current session practice lowers a strictly mechanical reround from xhigh to high. That is reasonable when the task scope, accepted intent, conflict files, and verification are already bounded; a stale base or environmental retry does not justify promotion under the model routing policy. Automation must still retain the card's model tier and correctness floor. A conflict involving security, fencing, data loss, or distributed authority must not be downgraded merely because it arrived through the rebase path. If the conflict needs new product judgment, it is no longer a mechanical round and should move to the guardian or human branch.

AGT-2544 supplies the closest recovery precedent. Every coding terminal now owes a complete immutable result envelope. A first consecutive envelope failure becomes Failed/delivery-failed and returns to Ready with salvage context; a second reaches Escalated as unverified-delivery. The platform owns the counter and the durable evidence, so a server restart does not reset the obligation or require a model to rediscover it. Scenario 2 should use that same shape for integration recovery: typed terminal, current-attempt identity, one automatic return, then visible escalation. AGT-2563 and AGT-2632 supply the Git-specific classifier and recovery primitives below that envelope pattern.

When a guardian is worth the tokens

  • The same failure fingerprint survives one deterministic rebase round.
  • Conflict paths cross subsystem or contract boundaries and the correct resolution is not “take ours” or “take theirs.”
  • The integrator reports attribution ambiguity, changed cardinality, or non-linear delivery history.
  • The gate is red after Git reconciliation and the next instruction must separate a product regression from an infrastructure failure.
  • The prior steer was incomplete, contradictory, or would cross a hard correctness floor.

A guardian is not justified for a first stale-base bounce with a complete typed failure, one current attempt, no hold, and a deterministic verification command. In that case the model would paraphrase state the backend already knows.

§10Recommended migration slices

  1. Make the current loop observable. Add a read-only recovery projection that reports eligible conflict-skipped and non-hold escalated cards, current attempt epoch, failure fingerprint, prior recovery rounds, hold reason, and proposed route. Shadow it against the session sweep without moving cards.
  2. Consolidate deterministic mutation. Extract a pure recovery policy and one application service around the existing integration recovery endpoint and IntegrationAgentRoundService. Atomically persist the templated steer, supersede the current delivery, apply a policy-safe thinking adjustment, move to Ready, and append timeline evidence. Reuse the Task API boundary; do not write task folders from an external orchestrator.
  3. Add restart-safe bounded ownership. Persist a recovery record keyed by task, attempt epoch, and failure fingerprint. Default budget: one deterministic automatic round. Duplicate ticks are no-ops. Holds, stale attempts, missing envelopes, and non-recoverable failure classes remain untouched.
  4. Add the guardian exception lane. After the deterministic round repeats, build a compact evidence packet and ask a strong model for a targeted steer in a parseable contract. The backend validates scope and route, then queues at most one guardian-authored round. A repeated same-fingerprint failure reaches Human Review.
  5. Integrate with Batch Gate. When AGT-2648 is implemented, let member ejection emit the same typed recovery request. Do not auto-steer stale-base batch runs as content conflicts; rebuild the batch. Track how many steers remain genuine content conflicts.
  6. Retire the session sweep. Remove it only after restart drills, idempotency tests, shadow parity, and a soak window show that no eligible cards depend on a live orchestrator. Keep manual API recovery as a visible operator override.

Proposed bounded ladder

Round 0: merge-first mechanical integration. Round 1: deterministic platform rebase steer. Round 2: targeted guardian steer only when evidence merits it. Then: Human Review with the full attempt chain. New operator intent or a materially different failure fingerprint starts a new review epoch; a process restart does not.
