Decision dossier · AGT-2662 · concept only

Rebase, merge, and bounce steering

The pipeline has two different identity moments. Before a new delivery fence, history may be reconciled onto the current work line. After review has fixed an attributed Result SHA, integration should preserve that identity. The same boundary explains which conflict bounces can be automated without asking a model.

Status decision pending Phase decision ready Evidence cut 16 August 2026 Implementation none in this card

Recommendation

Keep the hybrid, but define it by the evidence boundary. Rebase a bounced delivery onto current origin/<integration> before the new fenced attempt settles. Integrate the reviewed Result SHA with a direct no-fast-forward merge first. Permit a platform rebase only as a bounded fallback with an exact, transactional old-to-new SHA map. Replace session loop-tick labor with one deterministic platform bounce; use one evidence-reading guardian round only after a repeated or genuinely complex content conflict, then stop for human review.

Confirm the evidence-boundary rule, the two-round maximum of one deterministic steer plus one guardian steer, and whether the pending Batch Gate design should assemble members merge-first rather than rebase-first. The dossier does not change Git history, task state, model settings, or pipeline behavior.

§1The attribution lens

“Rebase or merge?” is not one repository-wide style question. It is a question about which identity the next gate must prove. The pipeline has two stages with different evidence owners:

Before a fresh delivery

The next fenced attempt will record a new BaseSha, ResultSha, immutable result ref, run attempt, and attributed commits[]. Rewriting the candidate is allowed because the new evidence names the rewritten objects.

After exact-subject review

review-subject.json fixes one attempt and one expected Result SHA. Acceptance and integration status then rely on those attributed objects being ancestors of the integration branch.

At release

The promotion train fixes one candidate SHA, gates that exact object, and publishes that same SHA. Any rewrite or new merge after the gate invalidates the receipt.

§2Current hybrid, stated precisely

2.1 Agent-side bounce rounds rebase before the new fence settles

The operator’s current loop-tick steer tells the delivery agent to fetch and rebase its existing card work onto current origin/<integration branch>, resolve content conservatively, rerun the gate, and deliver again without redoing the feature. That is compatible with attribution because the restarted attempt receives a fresh fence and its final Result Envelope names the new base, new head, new immutable ref, and new commit range. Exact-subject Remote Review then sees one expected head SHA.

This is not a claim that the Runner automatically rebases every requeue. GitWorkspace.PrepareAsync fetches current origin state and resumes a retained salvage branch when one exists. The explicit steer grants the delivery agent the reconciliation work. The new fenced completion is what makes that rewritten result canonical.

2.2 Server-side integration is merge-first since AGT-2632

The current mechanical integrator synchronizes the integration ref, verifies the fetched remote delivery head equals the reviewed Result SHA, and then follows this order:

  1. If the delivery is already an ancestor, return AlreadyMerged.
  2. Try git merge --no-ff --no-edit <result-sha> with rerere disabled. Success preserves every delivery SHA.
  3. After a real direct conflict, try one normal three-way ort merge with only previously recorded rerere resolution. It may not invent a semantic resolution.
  4. Only then try an isolated, rerere-disabled rebase. It is admissible only for a linear delivery with the same commit cardinality and an exact old-to-new mapping.
  5. If mapping is ambiguous or conflict remains, return AgentRoundRequired. Do not guess attribution.

MergeIntoDevelopRunner persists every accepted rebase replacement through RecordMechanicalRebaseOnFolder before push. If that attribution write fails, it rolls the integration branch back. Therefore merge-first does not mean merge-only; it means identity-preserving integration gets first claim, and a rewrite is valid only when attribution moves transactionally with it.

2.3 Acceptance is an ancestry guard, not an integrator

TaskTransitionService.ValidateIntegratedAcceptance first rejects a stale review attempt, then asks the integration projection whether the current delivery is integrated. If not, it returns typed IntegrationFailed and leaves the card in Human Review. It does not fetch, merge, rebase, or repair. TaskIntegrationStatusService derives integrated, partial, or conflict-skipped from target-branch ancestry of active attributed commits, with the reviewed Result SHA only as an empty-attribution fallback.

2.4 Why AGT-2632 changed the order

AGT-2632’s first fenced delivery was 72e67b3a…. The same change was later replayed as 1d0cd02a… and merged into develop by 04dd8166…. The files arrived, but the originally reviewed object did not become an ancestor. This is the exact failure mode: rebase rewrites object identity; task.json commits[] and the review subject still name the old identity; acceptance sees no ancestry; an integrator without a proven replacement map must refuse rather than infer ownership from similar content.

The current rule in one sentence

Rewrite before the new evidence fence; preserve after it. When the platform itself must rewrite after review, it must carry an exact replacement proof and roll back if that proof cannot be persisted.

Where the operator has a real choice

The platform does not require rebase as the only way to construct a new attempt. Cherry-pick is legitimate when branch history is contaminated and the agent proves the full card diff. Merging develop in is technically possible, but conflicts with the current linear delivery and exact-range review contract. Choosing it would require a deliberate review-scope contract change, not a stylistic preference.

§7Batch Gate changes frequency, not identity

The AGT-2648 Batch Gate dossier closes a manifest of eligible, already reviewed deliveries, builds one temporary candidate, runs the full suite once, and publishes only the exact green tip. This removes most per-card races with a moving develop, but it does not remove attribution requirements.

What becomes easier

  • All admitted members share one frozen batch base and deterministic order, so a later card does not repeatedly chase each earlier card through separate gate windows.
  • One exact candidate SHA naturally composes with the promotion train. The train may gate its own pinned candidate while batch construction is isolated, but canonical publication still needs the shared ref-mutation lease.
  • A conflict ejects one member and the remaining candidate can continue. The bounced member receives the base, predecessor, conflicted files, and batch identity as targeted evidence.

The pending design choice exposed by this lens

AGT-2648 currently proposes rebase-style mechanical replay for every member with replacement mappings. The attribution lens supports a simpler alternative: use the current merge-first primitive while constructing the temporary candidate. Each member’s reviewed Result SHA remains an ancestor, each merge is an explicit membership boundary, and the final merge tip is still the exact candidate tested and published.

Batch constructionBenefitCostRecommendation
Merge-first per memberPreserves review identity, needs no routine replacement map, and reuses immediate-integration semantics.One merge commit per admitted member and a non-linear candidate graph.Prefer under current evidence
Rebase-first per memberLinear candidate and compact first-parent history.Every member changes identity after review; mapping, supersession, and rollback become mandatory even on the green path.Choose only for explicit linear-history policy

Whichever construction is chosen, no merge, squash, or replay may happen after the full gate. Publication must fast-forward the canonical ref to the tested batch candidate. Genuine content conflicts still leave the batch and enter the bounce-steer policy described below.

§8Bounce steering today

The broad operational path is currently session-side orchestration. On each loop tick, the orchestrator looks for a review bounce whose integration projection is conflict-skipped. It then:

  1. appends a STEER section to the card’s prompt.md telling the agent that the delivery could not be merged, to rebase onto current origin/<branch>, resolve conservatively, rerun the gate, deliver again, and not redo feature work;
  2. sets thinkingLevel to high for the mechanical round instead of spending xhigh by habit;
  3. moves the same card back to 2-ready through the move API; and
  4. applies the same requeue shape to escalated cards that are not explicit holds.

This is manual orchestrator labor, not a durable backend rule for every projected conflict-skipped card. It ends when that session ends. On 13 August 2026 the session stopped overnight and 17 cards accumulated. The current AGT-2662 prompt also contains the same loop-tick conflict steer twice, a small but direct example of tick-level append fragility.

A narrow automatic rail already exists

AGT-2632 implemented IntegrationAgentRoundService for AgentRoundRequired. It durably saves a steer intent, appends the continuation note, marks the current delivery generation superseded, queues the card at the front of Ready, emits a timeline event, and allows exactly one automatic round per operator review epoch. This is Scenario 2 in narrow form, not proof that every broad conflict-skipped case is already automated.

§9Four automation scenarios

Scenario 1: session orchestrator remains the owner

StrengthNo backend change and flexible operator judgment.
CostOne inspection, prompt append, thinking mutation, and move call per card per tick. The same deterministic sentence spends orchestration attention repeatedly.
Failure modeSession death stops the rail; duplicate appends and missed cards are possible; the 13 August pile-up is the observed result.
UseKeep as manual override and migration fallback, not as the default owner.

Scenario 2: deterministic platform rule

The backend reacts to a typed, current-attempt integration failure, not merely the broad display string conflict-skipped. The projection can include conflict, attribution ambiguity, and some integration errors; environmental failures, stale attempts, missing refs, red gates, operator holds, and policy refusals need different actions.

For an eligible first bounce, one transaction should:

  1. verify current attempt, review epoch, delivery generation, and retry budget;
  2. persist an idempotent pending steer with branch, current integration SHA, delivery SHA, conflicted files, and recovery instruction;
  3. append the continuation note once and mark the old generation superseded;
  4. select high for the mechanical round only when that does not cross the model-routing correctness floor; stale-base recovery is not a semantic reissue and must not trigger an automatic stronger tier;
  5. move the card to the front of 2-ready; and
  6. emit one timeline receipt containing the rule version, evidence identity, prior and selected route, counter, and next terminal.

This generalizes three existing patterns rather than inventing a workflow engine: AGT-2544’s durable Result-Envelope retry obligation and two-attempt breaker, AGT-2563/2632’s integration recovery and exact replacement attribution, and the current continuation-note plus pending-intent boundary.

Default recommendation

Scenario 2 owns the first eligible bounce. It is deterministic, session-independent, cheap, and auditable. Start with exactly one automatic deterministic round per review epoch, matching the narrow AGT-2632 breaker already in code.

Scenario 3: guardian writes a targeted steer

A strong model is justified when the first current-base round still conflicts, when several files encode a cross-subsystem semantic choice, when the same conflict fingerprint repeats, or when failure evidence contradicts itself. The guardian reads the exact delivery diff, integration diff, conflict stages, gate receipts, previous steer, attempt chain, and any batch predecessor that introduced the conflict. It writes only the targeted recovery instruction.

The platform still decides whether a round is allowed and performs the mutation. This follows AGT-2654’s visual-QA pattern: a model classifies rich evidence and names defects; pure policy owns the one retry and terminal hand-off. It also fits the AGT-2557 Watcher target: strong analysis is reserved for exceptions that deterministic recipes cannot resolve.

Route the guardian against the canonical model policy. A compact, bounded conflict bundle can use a strong Sol/medium-class analysis. Distributed authority, credible data-loss risk, or unbounded cross-system evidence keeps the Sol/xhigh floor. The current operator’s high downgrade remains appropriate for the mechanical execution round only; token economy never overrides a correctness floor.

Scenario 4: Batch Gate world

Batching makes stale-base develop races uncommon because members are assembled against one closed base in one authority window. Most “your base moved while another card gated” bounces disappear. What remains is more meaningful:

  • a member conflicts with the batch base;
  • a member conflicts with an already admitted predecessor;
  • a later delivery generation supersedes the manifest member; or
  • the member’s attribution or evidence cannot be mapped into the tested candidate.

The same policy survives with a smaller trigger rate. Scenario 2 requeues a first genuine content conflict with batch identity and predecessor evidence. Scenario 3 is reserved for a repeated conflict or a conflict whose correct resolution depends on understanding both cards. Supersede is not a content steer: it invalidates membership and waits for the new current delivery.

§10Recommended operating policy and migration

Target policy

  1. Round 0, platform integration: merge-first; recorded mechanical merge; exact mapped replay fallback.
  2. Round 1, deterministic bounce: for eligible current-attempt content conflict or attribution ambiguity, append a current-base template, preserve prior generation, use proportionate reasoning, and requeue once.
  3. Round 2, guardian bounce: only after the conflict repeats or crosses the complexity threshold. The guardian writes a targeted steer from actual evidence; platform policy owns the move.
  4. Terminal: a third eligible arrival, unavailable guardian, contradictory evidence, exceeded budget, or explicit hold goes to Human Review with the complete attempt chain. No further automatic requeue.

The final maximum is therefore two automatic bounce rounds per operator review epoch, of which only one may use a guardian. Roll out with one deterministic round first. Add the guardian round only after the first slice’s receipts show a meaningful repeated-conflict cohort.

Boundaries and unresolved evidence

  • No controlled cohort yet measures how many first deterministic bounces succeed, how often a guardian would add value, or whether two automatic rounds are better than one. The migration starts with one and measures.
  • conflict-skipped is a UI projection, not a sufficient action trigger. The implementation slice must publish and consume typed failure causes.
  • AGT-2648 is decision-pending. Recommending merge-first batch construction here is an attribution-driven amendment for operator choice, not a statement of implemented Batch Gate behavior.
  • The current model policy does not make high a blanket core-task default. This dossier records the operator’s mechanical-round practice and constrains future automation with the policy’s risk floors.
