Decision dossier · AGT-2661

Local-first telemetry layer across organization applications

A shared event seam for local product usage and operations, with Agent Studio as the management layer that observes, groups, and prepares bounded action.

Status: decision pending Phase: decision ready Evidence cut: 2026-08-14 Scope: concept only

Recommendation

Approve a hybrid local bus: every product first appends a privacy-filtered event to its own local JSONL outbox; an Agent Studio collector validates, deduplicates, and records selected events; an optional local HTTP notification reduces latency; the existing Agent Message Bus and SignalR path carry only the operator-facing projection. Events never mutate tasks directly. Versioned rules create a Watcher case, and existing Task API and continuation authorities perform any approved action.

01Decision and boundaries

The decision is not whether every log line should enter a new central system. It is whether organization applications should share a small, durable telemetry contract and a controlled route from evidence to orchestration. The proposed route is local, append-first, replayable, and independent of cloud services.

Approve

  • A normalized PortfolioTelemetryEvent envelope at the collector boundary.
  • Per-application JSONL outboxes as the durable ingress.
  • Agent Studio as the cross-product management and decision surface.
  • Pure, versioned rules that open cases and call existing authorities.
  • A Quality Studio reliability pilot before portfolio rollout.

Do not approve

  • A cloud analytics dependency or mandatory internet connection.
  • Turning every ILogger or browser console record into a bus event.
  • Direct producer writes into Agent Studio bus files or task folders.
  • Automatic implementation work from a single warning or error.
  • Moving product analysis cores or domain truth into Agent Studio.

The existing ProductRuntimeEvent and AgentMessage contracts remain intact. This dossier proposes an adapter and consumption layer; it does not change a wire contract, schema, backend, or product emitter.

03Event model and privacy

A telemetry event is a completed fact about local product usage or operation. It is not a command, task mutation, free-form log message, or full diagnostic bundle. Producers describe what happened. The collector normalizes the fact. Consumers decide whether a pattern deserves attention.

Four deliberately separate records

RecordAuthorityPurpose
ProductRuntimeEventCurrent Agent Studio runtime schemaDetailed project or job runtime observability. Existing contract remains unchanged.
PortfolioTelemetryEventProposed collector input/output contractMinimal cross-application envelope with source, category, severity, actor class, context references, privacy classification, and stable fingerprint.
AgentMessageCurrent Agent Message BusSelected human-readable observation, problem, decision, action, or evidence projection for the Activity surface.
WatcherCaseGuardian policy layerDeduplicated, stateful interpretation of one event pattern, with rule version, evidence window, action receipt, and terminal outcome.

Structured logging as the seam

Log level alone is not an emission policy. The adapter promotes only records with a stable event name or numeric EventId, a declared category, and an allowlisted field set. Plain message-only records stay in the product log. This avoids converting diagnostics into a second, noisier application protocol.

Source levelDefault destinationPortfolio behavior
TraceLocal log onlyNever promoted by default. Available only in an explicit diagnostic evidence bundle.
DebugLocal log onlyNever promoted by default. Sampling requires a time-bounded operator setting.
InformationLocal logOpt in only for a declared usage, lifecycle, delivery, or performance event. A successful request log is not sufficient.
WarningLocal log and normalized outbox when structuredCollected and grouped. It does not create a card until a versioned threshold is met.
ErrorLocal log and normalized outbox when structuredCollected immediately and evaluated against cluster and known-recovery rules.
Critical or fatalLocal log and normalized outboxOpens one acute case immediately; action still passes through policy and authority checks.

For .NET, the mapping is direct from LogLevel. Browser console.log and console.error are not a contract; a host adapter emits a named event beside the console record. Existing sources such as GitProcessTelemetry can be adapted at their structured scope boundary rather than parsed from rendered log text.

Local-first privacy posture

Allowed by default

  • Stable application, component, version, event, category, and severity.
  • Pseudonymous correlation, run, session, project, and task references.
  • Durations, counters, status, bounded error type/code, and retryability.
  • Local artifact references after path normalization and containment checks.

Never in the portfolio envelope

  • Secrets, tokens, cookies, authentication headers, or environment values.
  • Prompt, response, chat transcript, source code, diff, raw input, voice, audio, screenshot, or attachment content.
  • Full stack traces, absolute home paths, user names, email addresses, device identifiers, or IP addresses.
  • Raw exception messages when they can contain project or user content.

No cloud endpoint is required or enabled. Producer outboxes live in application-data directories, not source repositories, unless an existing product contract explicitly owns a committed domain ledger such as Quality Studio usage records. “Git-friendly” here means text, versioned, diffable, and recoverable, not that raw operational telemetry should be committed.

The proposed retention default is seven days for acknowledged producer outbox rows and thirty days for selected central events. Derived cases, decisions, cards, and review evidence follow their existing product retention. Both windows remain local and configurable; changing them is an explicit policy decision.

04Bus architecture options

All three options can stay local. They differ in durability, coupling, and what happens while Agent Studio is stopped.

CriterionA · Files + collectorB · Local pushC · Hybrid
Offline operationCompleteUnavailable when backend is down unless each producer adds storageComplete
DurabilityAppend and replayDepends on receiver and retry protocolAppend and replay; acknowledge after collector receipt
Live latencyFile-watch or polling latencyImmediateImmediate when available, eventual otherwise
Producer couplingSchema and local path conventionSchema, route, authentication, and backend lifecycleSchema and outbox required; route optional
Cross-process safetyOne writer per app outbox; collector owns central appendReceiver serializes writesSame clear single-writer boundaries
Existing fitMatches runtime, bus, runner, prompt, and Quality Studio ledgersMatches current HTTP and SignalR experience but not disk authorityMatches both patterns without making SignalR durable

Recommended hybrid topology

  1. Each application owns one local outbox below its application-data root. It is append-only, day-partitioned JSONL, one writer, and safe while Agent Studio is stopped.
  2. The Agent Studio management layer registers allowed source roots and stores a checkpoint per source file. It validates schema and privacy, normalizes fields, and deduplicates by event ID.
  3. The collector appends accepted facts to a central local telemetry receipt log, partitioned by source application and date. Quarantined rows remain local with a reason and never enter rules.
  4. An optional loopback HTTP call carries the event or a wake hint. Success means the central append is durable. A failed call changes nothing because the outbox remains replayable.
  5. Only events useful to an operator or case are mirrored to the existing Agent Message Bus. SignalR fans that projection to Agent Studio. It is not producer ingress or storage.
  6. Cross-host installations may use the existing authenticated Task Server channel, but no cloud service is required. The local single-host path remains the baseline.

Applications must not append directly to logs/bus/. The current store owns append serialization and its in-memory projection; external writes would weaken ordering, live invalidation, and ownership. Applications also must not create task folders directly.

05Orchestrator consumption

Consumption follows the Guardian model from the Global Orchestrator Watcher dossier, AGT-W15 with source task AGT-2557: observe globally, identify a bounded case, inspect evidence, authorize only an allowlisted action, and record the result. The visual QA steered-retry path from AGT-2654 is the working precedent: durable evidence enters a classifier, a pure policy permits at most one steer, the existing continuation path acts, and exhaustion goes to Human Review.

Initial rule catalogue

PatternPilot defaultOrchestrator behaviorHuman surface
Repeated usage friction Same app, semantic event, feature/route, and major version in at least five distinct sessions over fourteen days Open or update one friction case. Prepare one feature-candidate card with counts, trend, affected versions, and redacted evidence references. Do not start implementation. Activity observation; card enters Backlog or Preparation with needs-decision when product intent is unclear.
Error cluster Same source and fingerprint in at least three distinct runs or sessions within thirty minutes Open one problem case. Apply a known, allowlisted recovery only if its breaker permits; otherwise prepare one healing card through Task API. Acute Activity problem; persistent alarm while open; decision item if action is not allowlisted.
Fatal local failure One structured fatal event Open an acute case immediately, collect bounded diagnostic references, and stop automatic action unless an exact mechanical recovery is already approved. Persistent alarm and decision-required.
Performance regression Declared operation exceeds its versioned budget in three consecutive windows with at least twenty samples Prepare an analysis card with baseline, current percentile, sample size, versions, and correlation references. Activity advisory; no acute banner unless the operation blocks work.
Telemetry quality failure Schema rejection, missing correlation, or noisy event above its per-source budget Quarantine the row and update one observability-maintenance case. Never recursively emit the collector failure through the same path. Collector health panel and one maintenance card after threshold.
Security signal Any allowlisted security event Redact first, open a restricted decision case, and require an operator. No automatic feature or healing card from raw security content. Restricted needs-decision item.

Case and action safeguards

  • The case key is sourceApp + ruleId + fingerprint + versionBoundary. Each action has a durable idempotency key and receipt.
  • Rules count distinct sessions or runs, not raw row volume. Test fixtures and known automation actors are excluded unless a delivery rule opts in.
  • A live case absorbs matching events. A resolved case has a cooldown and reopens only on a new threshold window or application version.
  • Card creation goes through the normal Task API, with owning project, source application, rule version, evidence window, and reproduction references. No task-directory write is allowed.
  • Model analysis may summarize or classify bounded evidence. A pure policy decides whether the output can cause action, matching the Watcher capability ladder and visual QA precedent.
  • Feature and healing cards are prepared work. They do not enter automatic execution merely because telemetry created them.

Existing consumers are not hypothetical

AGT-W15 supplies the global case lifecycle and authority ladder. AGT-2654 supplies the first bounded evidence-to-steer consumer with durable verdicts, a one-retry breaker, and Human Review fallback. The telemetry layer generalizes their input seam; it does not replace their policies.

06Agent Studio as Ops Hub

CI/CD control, promotion evidence, Actions hygiene, runtime alarms, telemetry, and orchestration are already converging on Agent Studio. This should be an explicit product position: Agent Studio is the organization management layer and operator console for product delivery and health. In the target architecture, the Task Server and Orchestrator backend own collection, policy, and durable mutation; the Agent Studio UI remains the client and control surface.

Agent Studio management layer ownsEach product continues to own
Application registry, stable source identities, adapter registration, schema catalogue, and compatibility reportingDomain concepts, feature semantics, and the decision about which named facts are meaningful
Collector checkpoints, validation, privacy enforcement, event-ID deduplication, central local receipt log, and retention policyIts local outbox, raw diagnostic logs, domain databases/files, and evidence content
Cross-product Activity, alarms, Watcher cases, needs-decision queue, trend summaries, and links to product evidenceProduct-specific analysis and presentation: Quality Studio review and grading, Chat rendering, Token Economy pricing and benchmarking, Voice Lint rules
Versioned event-to-case rules, action allowlists, circuit breakers, action receipts, and calls to existing Task API or continuation routesImplementation of a recovery or feature after the normal task lifecycle authorizes it
CI/CD and promotion-train visibility, workflow hygiene signals, candidate/deployment receipts, and cross-product readiness viewsGitHub Actions or another runner as the execution authority, repository workflows, release artifacts, and product deployment mechanics

Management layer, not a monolith

Quality Studio does not become an Agent Studio feature. Its review-run store, findings, reports, hierarchy, and analysis core remain authoritative. Coding Agent Chat does not gain an Agent Studio dependency. Token Economy core stays deterministic. Voice Lint owns lint semantics. Agent Studio receives only governed events and evidence references, then manages cross-product attention and work.

Operational boundaries

  • CI/CD: Agent Studio observes and coordinates the promotion train, candidate state, deployment receipts, and workflow hygiene. It does not become a new build runner or bypass repository protections.
  • Telemetry: Agent Studio owns portfolio collection and case policy. Products own event semantics and local diagnostic detail.
  • Alarms: Activity is the durable narrative; persistent banners are reserved for acute, current operator impact. A historical warning does not remain a banner.
  • Orchestration: The bus carries facts and projections. State machines, Task API, runner continuation policy, and operator decisions remain the only mutation authorities.
  • Failure isolation: Agent Studio telemetry about its own collector uses a separate bounded health channel so a collector error cannot amplify itself.

07Pilot and rollout

Start with Quality Studio and one category: reliability. It already has stable structured failure events, durable review-run identifiers, append-only records, and an existing path that hands findings to Agent Studio tasks. The pilot can therefore test the shared seam rather than first inventing a library transport.

The pilot does not export current .quality/usage records, add usage analytics, or auto-run the prepared healing card. Those are separate rollout decisions.

Rollout order after the pilot

  1. Quality Studio reliability pilot. Prove schema, redaction, buffering, dedupe, case identity, one card, and restart behavior.
  2. Coding Agent Chat friction and reliability. Route existing attachment-unavailable and history-load-failed events through a host-owned outbox. Add repeated-friction candidates only after the host can supply anonymous session identity.
  3. Agent Studio consolidation. Add adapters for selected Product Runtime Events, GitProcessTelemetry, runner failures, prompt-call quality, and acute pipeline alarms. Preserve each canonical ledger and add recursion suppression before dogfooding action rules.
  4. Token Economy website. Add a browser/host adapter for site usage, friction, and performance. Keep pricing, efficiency, benchmarking, and catalogue libraries free of telemetry side effects.
  5. Voice Lint. Include the envelope and outbox in its first executable product slice, then start with reliability before usage events.

Rollout gates

  • No next application until outage replay, event-ID dedupe, redaction fixtures, and one-case/one-card idempotency pass.
  • Every source publishes an event catalogue with owner, category, allowed fields, expected rate, and retention class.
  • Every action rule has a version, threshold rationale, distinct-session rule, cooldown, breaker, human fallback, and removal owner.
  • Event rate and quarantine rate are visible before action rules are enabled. Observe-only is the default rollout mode.
  • A source can disable portfolio emission without losing its ordinary local logs or domain operation.

08Decision packet

The architecture is ready for a decision. Approval should record the following as one coherent boundary, not as permission to instrument every product immediately.

DecisionRecommended answerConsequence
D1 · Durable ingressHybrid, with a per-app file outbox as required spine and local HTTP only as accelerationProducts remain offline-capable and Agent Studio downtime does not lose facts.
D2 · Normalized contractA separate PortfolioTelemetryEvent v1 at the collector boundary, mapped from current product eventsThe current runtime-event and Agent Message schemas keep their narrower authorities.
D3 · Management positionAgent Studio is the Ops Hub and management layer; Task Server/Orchestrator owns collection and mutation policyCross-product operations converge without moving product cores.
D4 · Action authorityEvents open cases; pure rules and existing APIs authorize actionNo bus message or model output directly changes task or product state.
D5 · PrivacyLocal only, allowlisted fields, content excluded, seven-day acknowledged outbox and thirty-day central raw defaultsNo cloud dependency and a bounded raw-data footprint.
D6 · PilotQuality Studio reliability, three matching failures across distinct runs, one healing cardThe first slice proves the whole path without first redesigning a library host.

Decision request

Approve D1 through D6 as the implementation brief. On approval, create separate implementation cards for the event schema and privacy fixtures, file outbox and collector checkpoints, Agent Studio ingestion and bus projection, Watcher rule and Activity case, Quality Studio adapter, and end-to-end failure/replay proof. Keep each card within its owning repository and normal delivery pipeline.

Items intentionally left for implementation design

  • The exact application-data path per operating system and cross-host registration UX.
  • The precise local ingestion route and authentication mechanism for optional push.
  • Whether the central receipt log partitions by source and day or source and month after rate measurements.
  • The first operator UI composition beyond existing Activity, needs-decision, and alarm surfaces.
  • Threshold tuning after an observe-only Quality Studio baseline. The defaults in this dossier are pilot policy, not portfolio constants.

Explicit non-goals

  • A general distributed event platform, cloud warehouse, or replacement for OpenTelemetry.
  • Central collection of source, prompts, transcripts, screenshots, audio, attachments, or full exception detail.
  • Replacing existing runner journals, token receipts, Quality Studio reports, review evidence, or CI provider records.
  • Using telemetry to bypass human product decisions, Task API, pipeline gates, repository authority, or Watcher breakers.
  • Making shared libraries depend on Agent Studio transport or filesystem conventions.
