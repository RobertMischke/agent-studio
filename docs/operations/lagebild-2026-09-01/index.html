Deployment-Regel (verifizierter Rollout)

Wann deployen

Promotion-Zug, sobald develop ≥ 5 Commits vor main liegt oder ein dringlicher Fix wartet (CLI-Self-Heal zählt dazu). Aktuell: develop == main → warten auf die Review-Kette (Schritt 2).

Wie verifizieren (Pflicht seit AGT-2678)

Nach jedem Stable-Rollout: (a) Backend-Prozess hat neue StartTime (alter PID tot), (b) healthz 200 lokal + durch den Tunnel, (c) Frontend 200 über localhost:4011 inkl. Proxy-Durchstich auf echte Daten, (d) beide Runner-Planes neu gestartet und active, (e) Boot-Probe ohne Page-Error. Erst dann gilt der Rollout als erfolgreich.

Gelernte Härtungen (in Memory gesichert)

  • Plumbing-Merges: Exit-Code nie über local var=$(cmd) lesen; vor jedem Push git grep -lE '^<<<<<<< ' als Marker-Probe.
  • Flaky-Gate-Signatur: „N new failures … 0 pre-existing … Baseline (cache hit)" mit wechselnden Teilmengen = Gate-Problem, nicht Karten-Problem.
  • Windows-lokal vs Linux-Gate: lokal immer --filter "Category!=MachineBound"; Datei-Lock-Fails (\\?\C:\…) sind kein Gate-Signal.
  • Steer-Texte branch-aware: QS integriert nach origin/main — nie pauschal „develop rebasen".
