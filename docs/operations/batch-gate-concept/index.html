Decision dossier · AGT-2648 · concept only

Batch Gate: one full suite for a delivery wave

Mechanically assemble all eligible pending deliveries on one fenced temporary branch, test the exact combined candidate once, and publish only a green tip. A red candidate is reduced by bounded halving; conflicts and superseded deliveries leave the batch without blocking its remaining members.

Recommendation

Choose Option A, Batch Gate, as the primary throughput control and pilot it with docs-only deliveries. Keep per-card model review and immutable delivery validation. Move the full build and test suite into one single-flight batch run. Option C, a separate gate host, composes with A when one serialized suite no longer provides enough capacity. Do not use risk classification as the only guard for code-bearing changes.

The approval this dossier requests

Approve the operating contract and a reversible docs-only pilot, including the shared publication lease and native per-member batch evidence. This is not approval to edit the current pipeline yet. Trigger thresholds remain pilot parameters, not permanent product defaults.

§1Decision and boundaries

A Batch Gate is a per-project, per-repository, per-gate-profile transaction. At close time it snapshots every delivery that is eligible for the same full-suite profile. New arrivals wait for the next batch. “All pending deliveries” therefore means all eligible deliveries in that closed snapshot, not unrelated repositories, incompatible test profiles, unfinished attempts, or an unbounded queue that can change while testing.

Per card

Settle the immutable result envelope, validate the attempt fence, perform model review, and record the exact delivery subject.

Per batch

Replay eligible subjects in deterministic order, run the complete gate once on the exact candidate, then publish or isolate.

Never inferred

A lane, review narrative, temporary branch, or historical record alone never means gate-passed or integrated.

Eligibility contract

A delivery enters the closed manifest only when all of these are true:

  • its Result Envelope is settled and names an immutable result ref, result SHA, run attempt, delivery epoch, and fencing token;
  • per-card model review has passed the exact subject, with the build/test aspect recorded as deferred-to-batch, never misreported as not applicable;
  • the card is still the current generation, has no newer attempt, no reissue, and no operator supersede;
  • the project, repository, integration branch, gate profile, and platform version match the other members; and
  • the delivery is not already owned by another batch or an active per-task gate.

The manifest records every eligible key and every exclusion with a typed reason. The coordinator may not silently select an easy subset.

Non-goals

No cross-project mega-batch, no test selection by a model, no weakening of the full suite, no force-push, no post-test merge commit, no reinterpretation of an infrastructure failure as a product failure, and no change to human acceptance. This dossier contains no pipeline implementation.

§2Two real evidence sets, one reconciled conclusion

The proposal depends on two observations made at different scales. Both must remain visible in the decision record.

25 July: per-task economics

The two concept pages added to main on 25 July 2026 were Pipeline Time Economy: where time and tokens actually go and Async Validation & the Test Staging Lane. Across 847 tasks and 2,396 attempts, the first page found that coding carried about 98% of all tokens, while the deterministic test gate carried none; test CPU was estimated at about 0.05% of token spend. The second page therefore rejected batching as a money argument, recommended per-SHA caching, and left a staging branch measure-first because red batches can erase their gain.

The July conclusion was sound at its measured dimension: tests were not the per-task spend bottleneck, and reducing coding retries remained the cost lever. It also identified serialized retry testing as a possible throughput lever. It did not measure four full suites competing with coding on a saturated host.

Reconciled conclusion

Tests are still negligible as a money cost and coding still dominates tokens. Simultaneous full suites are now the host-capacity bottleneck at wave scale. Batch testing targets exactly that concurrency: it reduces four competing suites to one without claiming that test CPU became expensive.

§3Batch construction

Closed manifest and deterministic order

The coordinator creates agent-studio/batch-gate/<project>/<batch-id> from a fetched, immutable develop base. The manifest is durable before Git work starts. Members are ordered by the current integration policy: review-subject.completedAtUtc, then durable enqueue sequence, then task key as a final stable tie-breaker. The order, base SHA, member subjects, and gate profile form a membership digest.

{
  "batchId": "bg-20260811-0042",
  "project": "agent-taskboard",
  "baseSha": "<full develop SHA>",
  "gateProfileDigest": "<full digest>",
  "members": [{
    "taskKey": "AGT-0000",
    "runAttemptId": "<attempt>",
    "deliveryEpochId": "<epoch>",
    "fencingToken": 7,
    "resultRef": "refs/agent-studio/results/...",
    "resultSha": "<full delivery SHA>",
    "modelReviewId": "<review>"
  }],
  "membershipDigest": "<full digest>"
}

Mechanical replay, not conflict resolution by the coordinator

Each member is replayed in a disposable detached worktree onto the current batch tip using the existing conflict-free mechanical rebase rules. Every replacement SHA maps back to its original delivery SHA. A successful replay advances only the temporary batch ref. It does not yet make the card integrated.

If a member conflicts, the replay aborts and removes its worktree without changing the current batch tip. That member receives the typed conflict and file list, is ejected to the existing Rebase & retry steer path, and the batch continues with the next member. This avoids allowing one conflict to poison the branch state. A later member that conflicts against an already admitted predecessor is independently ejected; the coordinator never guesses which content should win.

Conflict cascade guard

If more than 25% of a batch, or three members in succession, conflict during construction, close the candidate with the members already admitted and stop admitting later members. The unattempted tail moves intact to the next batch after rebase-steer catches up. The threshold is a pilot parameter; its failure semantic is “smaller closed batch,” not “resolve serial conflicts centrally.”

§4Build, test, then mirror or isolate

Green path: exact subject, exact publication

  1. Persist a batch-run record before execution: batch id, membership digest, base SHA, candidate SHA, gate profile and digest, host, lease fence, command list, start time, and evidence location.
  2. Run the complete suite once on a clean checkout of the candidate SHA. A pass receipt includes the same candidate SHA and profile digest.
  3. Revalidate every member generation and acquire the project publication lease. Fetch develop and verify its tip still equals the recorded pre-tip.
  4. Publish by fast-forward when the tested candidate descends directly from the pre-tip. A merge topology is allowed only when the merge commit itself was prebuilt and tested as the candidate. Never create a new, untested merge commit after the suite.
  5. Verify remote develop resolves to the tested candidate. Apply the existing auto-main policy only while holding the same ref-mutation authority and only after the batch is green.
  6. Write per-member gate and integration evidence, then release each member to Human Review. Human acceptance remains separate.

If develop moved since the recorded pre-tip, do not merge the green batch into the new tip. Mark that run stale-base, reconstruct on the new base, and run the suite again. This is the cost of preserving the exact-SHA claim.

Per-member evidence and AGT-2543

Each member needs two linked facts, not one batch-wide narrative:

RecordRequired identityFailure semantic
Gate-passed recordTask key, run attempt, delivery epoch, original result SHA, replacement SHA set, batch id, membership digest, base SHA, tested candidate SHA, gate profile digest, batch-run id, verdict, and evidence path.Missing or mismatched identity means batch-gate-evidence-missing. The card cannot be marked gate-passed.
Integration recorddevelop, exact remote tip, the member’s integrated SHA set, and evidence that points to the same batch run and candidate.Push or ancestry verification failure means integration-unverified. The card stays out of Completed.

POST /api/tasks/{id}/integration-records, added on 11 August, can append an idempotent integrated-verified historical classification once a card is in Human Review or later. Its current five-class schema is not a native gate-pass authority, rejects in-flight lanes, and never moves a card or changes Git. The implementation slice therefore needs a native batch-gate record before lane release. After the card enters Human Review, the existing endpoint can append the integration bookkeeping row and retry idempotently if that append fails.

This preserves the AGT-2543 honest-completion invariant: no card reaches Completed, and no UI says gate-passed, unless its current attempt points to a successful batch run, the exact tested candidate, and its complete SHA mapping. Git ancestry remains stronger than bookkeeping. A record cannot manufacture integration.

§5Red path and honest isolation bounds

First classify the red

  • Infrastructure red: host loss, timeout without test verdict, dependency registry outage, disk pressure, or lease loss. Attribute no member. Retry the same candidate once on a healthy gate host. A second infrastructure red pauses the batch for operator visibility.
  • Deterministic suite red: a reproduced failing test or build on the same candidate. Start ordered halving from the same base and gate profile.
  • Flaky red: use the repository’s existing bounded quarantine policy. Preserve both runs. Never convert repeated failure into green by majority vote.

Halving algorithm

  1. Split the ordered member set in half. Reconstruct the first half on the original base and run the same complete gate.
  2. If that half is red, continue with it. If it is green, continue with the complement only under the single-cause assumption. Preserve the green subset as evidence.
  3. At one member, eject that delivery to a per-task gate. If its mechanical replay conflicts, use rebase-steer; if it replays and tests red, attach the failing gate evidence to the card.
  4. Rebuild all survivors in original order and run one complete suite. If still red, begin another isolation cycle or eject the unresolved cohort when the diagnostic budget is exhausted.

The log2(n) limit must not be overstated

For one reproducible, monotone offender, one failing half per level isolates it in at most ceil(log2(n)) diagnostic suite runs after the initial red. Add one final survivor run, so the cycle is at most ceil(log2(n)) + 2 total suite runs including the initial red. That is not a universal bound for multiple offenders or interaction-only failures.

Failure shapeHonest boundFallback
One independent offenderceil(log2(n)) diagnostic runsEject one, then run survivors once.
k independent offendersUp to O(k log n); each new red survivor set starts a new bounded cycle.Stop after the configured total budget and use per-task gates for the unresolved cohort.
Cross-member interactionNo valid logarithmic guarantee. A half can be green while the union is red.Preserve the smallest known failing cohort and send its members to isolated gates or an operator-owned interaction card.
Non-deterministic failureNo offender conclusion.Apply flaky or infrastructure policy; do not steer a member from an unproven association.

The batch coordinator caps each isolation cycle at ceil(log2(n)) diagnostic runs. This gives the operator the requested bounded behavior without pretending all multi-offender cases are logarithmic. An unresolved cohort is a visible fallback, not a batch success.

§6Authority, fencing, supersede, and the promotion train

Lease and restart rules

  • The batch coordinator acquires a durable lease keyed by project, repository, integration branch, and gate profile. Every state write and candidate ref includes its fencing token.
  • Lease loss cancels the suite and forbids publication. A successor may resume only from the durable manifest and a candidate ref whose digest and fence still match; otherwise it reconstructs.
  • Only one batch may be testing or publishing for a repository on a host. Duplicate claims become idempotent observers of the current batch.
  • The project ref-mutation lease is shared with any existing direct integration, auto-main advance, and promotion publisher. It is acquired only for final revalidation and publication, so a long suite does not unnecessarily block read-only preparation.

Superseded mid-batch

MomentRequired response
Before suite startEject the stale generation, reconstruct the branch without it, and record member-superseded. The new generation may join only a later batch.
While suite runsLet the process stop safely, mark its verdict unusable, reconstruct without the member, and rerun. A green result for the old manifest cannot publish.
After green, before publishThe mandatory final membership check fails closed. No mirror occurs.
After verified publishThe batch transaction is complete. Preserve the old generation’s integration history, but never transfer its gate result to a newer attempt.

Integrate-before-review and AGT-2528 / AGT-2603

The existing contract integrates a green Remote delivery before Human Review. Batch Gate keeps that invariant but changes the green predicate and publication unit. AGT-2528’s immediate Remote integration coordinator and AGT-2603’s follow-up state-machine simplification remain the authority model: exact fenced subject, deterministic ordering, visible failure, and no acceptance-side secret merge. The proposed flow is:

settled delivery → per-card model review → batch pending → batch gate and verified mirror → Human Review.

A temporary replay is not the “integrated before review” event. Only verified membership in develop releases the member to Human Review. A conflict may still be reviewed with a visible delivery failure only if the product deliberately retains that current exception path; it is never gate-passed.

Auto-main advance and AGT-2594 candidate-SHA promotion

AGT-2594 made the promotion train test and publish a pinned develop candidate rather than chasing a moving tip. Batch Gate must not race it. The train and batch publisher share the ref-mutation lease for any main or develop mutation. A train may continue testing its pinned candidate while an isolated batch branch is built, but their publish phases cannot overlap. The train never discovers or promotes a temporary batch ref; it promotes only its recorded candidate SHA. If the existing auto-main policy advances main after a green batch, it does so inside the same authority window, never beside the train.

§7Scheduling and the review-plane split

Formation triggers

Recommended starting parameters are deliberately small and configurable:

TriggerPilot valuePurpose
SizeClose at 4 eligible members; hard maximum 8.Capture most concurrency savings without making red isolation too expensive.
TimeClose when the oldest eligible member has waited 15 minutes.Bound quiet-period latency. A lone member uses the per-task gate after the deadline.
Queue pressureClose at 2 or more when the review queue is at least 12 or the load gate is throttling.Drain a wave without waiting for the normal size.

Any trigger closes the manifest. Once closed, it never absorbs new members. Projects remain sequential at the canonical integration boundary even when coding is concurrent.

Host placement and single flight

  • Run the full suite on one gate-capable Linux host with the repository’s required toolchain and a gate-specific resource budget. Coding may continue on other admitted capacity.
  • Enforce one active full suite per physical host and one active Batch Gate per repository. A second project waits unless Option C provides a separate gate host with its own admission budget.
  • Do not start a batch suite while host load is already above the admission threshold. Reserve the gate slot first so coding admission cannot consume its promised capacity.
  • Model reviews remain remote or local review-plane work and do not hold the suite slot.

Explicit plane split

Envelope, attempt fence, result ref, and subject-SHA validationClean checkout of the exact combined candidate

Machine-bound suites retain their separate scheduling contract. Batch Gate does not hide them inside the routine full suite.

§10Pilot, proof metrics, and rollback

Safe first slice

  1. Shadow manifest: for one week or ten eligible docs-only deliveries, form and persist batches without changing routing. Compare membership, supersede, and conflict decisions with the existing per-task path. Do not add extra full suites in shadow mode.
  2. Docs-only authority pilot: route 20 docs-only deliveries in batches of 2 to 4. Their combined candidate still runs the real full suite, proving construction, exact-SHA publication, per-member evidence, restart recovery, and rollback with low product-code risk.
  3. Low-coupling code pilot: only after docs-only evidence meets the go criteria, add one explicitly allowlisted low-coupling feature area. Keep maximum batch size 4.
  4. General decision: compare at least three similar wave windows before changing default routing or increasing maximum size.

Also retain coding throughput, model-review duration, suite duration, CPU steal, memory pressure, batch wait, conflict files, stale-base rebuilds, promotion wait, and fallback count. Cost is reported but is not the success metric.

Rollback

  • Disable Batch Gate per project. Stop forming new manifests.
  • Mark any unmirrored batch abandoned-by-rollback. Keep its manifest, logs, and temporary candidate ref for a bounded evidence-retention period.
  • Return every unmirrored current member to the existing per-task gate using the same immutable delivery subject. Do not reissue coding merely because batching was disabled.
  • A candidate already verified and mirrored is normal Git history. Do not reset or rewrite develop; address any later regression through a normal revert delivery.
  • Retry missing per-member bookkeeping from the durable batch record even after routing is disabled. Rollback must not create incomplete completion evidence.

Operator note (2026-08-18)

Sequencing modification under consideration: the full suite should not run per round at all. Model review and cheap deterministic checks run first on every delivery; the full suite runs only as the FINAL gate once a card appears done (no further round expected) - and there it runs once per batch, not once per card. This composes Option A (batch gate) with the review-first ordering: roughly half of today's suite runs are spent on rounds that die at review or on conflicts and would be eliminated outright.
